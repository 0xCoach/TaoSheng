**本卡只做查询层**（`:shared`），界面由 Claude 同时做（`ui/today/RecordSearchSheet.kt` 等），本卡不改 `ui/`、`MainActivity.kt`。**不改数据库**（不新增表、索引、版本）。与卡 192 并行，互不改对方文件。

## 现状

- `shared/.../search/RecordSearch.kt`：只查 `transcript_lines`（`lines_fts`）和 `memory_events`（`events_fts`），两类合并按时间倒序**总共**取 100 条（`LIMIT`），常见词时原话会把事件挤掉。
- `SearchIndex.kt` 早已给 `memory_items`（待办、约定、备忘、灵感、关键信息、决定、知识）建了 `items_fts` 和触发器，但搜索没用它。
- 单个汉字走 `LIKE` 兜底、多字走 FTS 二元组，再用 `contains` 二次过滤（`RecordSearchRules`），这套规则保留并复用。

## 目标

### 1. 搜索范围

| 类别（`Kind`） | 数据 | 方式 |
|---|---|---|
| 对话 `Line` | `transcript_lines.text` | 现有 FTS |
| 事件 `Event` | `memory_events` 标题、摘要、要点，`deleted = 0` | 现有 FTS |
| 待办 `Todo` | `memory_items`：待办页显示的那几类（请按现有待办页的查询确认，例如 `待办`、`约定`） | `items_fts` |
| 记忆 `Memory` | `memory_items`：其余类别（备忘、灵感、关键信息、决定、知识等，按记忆页实际口径） | `items_fts` |
| 其他 `Other`：寻物 | `things`（名称、别名）、`thing_records`（名称、动作、地点、人、原文；只取用户能看到的状态） | `LIKE` |
| 其他：专题 | `topics.name`（及其关联事件已在“事件”里，不重复） | `LIKE` |
| 其他：回顾 | `reviews.brief`、`sectionsJson` 里的可见文字 | `LIKE` |
| 其他：问问 | `ask_messages.text`（用户和回答都算）、`ask_conversations.title` | `LIKE` |

- `memory_items` 排除 `deleted = 1` 和已合并（`mergedInto IS NOT NULL`）的；**已完成的待办要能搜到**，结果里带完成状态。
- 其余各表按各自页面的“用户可见”口径排除已删除、已忽略的内容；口径以现有页面查询为准，交付说明里逐表写明。
- 小表用 `LIKE` 不建索引；若某表在真实数据量下（按全天录音一年估算）明显偏慢，在交付说明里给出数据和建议，不要自行加索引。

### 2. 返回结构

- 每类**各自**最多 100 条，互不挤占；同时返回每类的**命中总数**（超过 100 也要能知道是“100+”，可以用 `LIMIT 101` 判断，不必精确计数）。
- 支持：按类别过滤（一类或全部）、时间范围（开始/结束毫秒，可空=全部）、分页（按时间倒序的游标或偏移，用于“滑到底加载更早的”）。
- 每条结果至少有：类别、id、时间、标题/正文片段（复用 `snippet` 高亮规则）、跳转所需的定位信息（例如待办/记忆的 `id`、所属事件 `eventId`、回顾的日期、问问的 `conversationId`、原话的 `segmentId`）、待办的完成状态。
- 保留 `RecordSearch.search(query)` 的现有行为作兼容（界面切换完成后由 Claude 删除），新接口另起名字。

### 3. 规则放 `:shared`

查询拼装、类别划分、片段截取都是平台无关规则，放 `:shared/search/`，不引用安卓类，iOS 以后直接用。
