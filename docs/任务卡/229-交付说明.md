# 卡 229 交付说明：本机识别按当前可用模型运行

## 起因

SM8850 用户升级后，设置页同时显示支持 NPU 和旧版的「暂不支持」提示。NPU 模型下载停在 12%，已有 CPU 模型却无法继续本机转写。

## 根因

- 芯片支持说明按新版芯片表生成，下方状态却沿用旧版写进 `local-asr/actual` 的文字。
- 默认选择 NPU。就绪判断只看 NPU 模型，识别入口也在 NPU 模型未就绪时直接报 `ModelMissing`，导致已下载的 CPU 模型未被使用。

## 做了什么

- 将纯函数 `LocalEngine` 放入 `:shared`。设置文案、转写就绪和实际引擎共用同一规则。优先用所选引擎，另一引擎可用时自动接替。两个都不可用时提示需要的模型。
- 启动删除旧 `actual`。模型偏好、下载状态或 NPU 检查变化时重新计算。转写进度和当次回退提示只留在内存，请求结束即清除。备份继续排除旧状态和设备检查结果。
- NPU 首次试用按 App 版本和模型记录结果。已通过后的偶发失败只对本次请求回退 CPU。音频、分人及中断错误沿原路径处理。
- 核对设置页读取的 `localStatus`、向导和上手清单读取的 `ready`，以及转写器的全局和按来源就绪判断。CPU 已就绪时，这些入口允许转写，NPU 下载进度仍可查看。

## 怎么验证的

- `LocalEngine229Test` 覆盖引擎选择和全部状态文案分支，包括 NPU 下载未完成、CPU 缺失时反向回退、芯片未适配和两个模型都不可用。
- `LocalStatus229Test` 用 Robolectric 模拟 SM8850 和 12% 下载进度，检查旧状态删除、CPU 就绪、模型下载完成后重算、临时提示清除及切换引擎后重查。
- 逐行核对 `TranscribeSettings177Test` 金样。第 1 行初始状态由「旧状态」变为「请先下载 CPU 模型」，第 5 行选择 CPU 后的状态由「已选择 CPU 识别」变为同一下载提示。其余各行逐字一致。
- 应用 JVM 测试通过，1,483 个用例中 10 个跳过。共用 JVM 测试 523 个全部通过。
- `:shared:check`、`python3 tools/check_shared.py`、`zsh tools/check_ios.sh` 通过，iOS 共用代码完成真机目标和模拟器目标编译。
- 最终调整临时提示后，转写相关 JVM 测试再次通过，218 个用例中 2 个跳过。更新状态断言的三组设备测试随 `:app:compileDebugAndroidTestKotlin` 编译通过。
- `:app:assembleRelease` 通过，校验生成的 APK 压缩内容无错误。

## 真机需要注意

- 在 SM8850 上保留旧版数据，准备好 CPU 模型，让 NPU 模型保持未下完。升级后打开设置，应显示「NPU 模型还没下载好，先用 CPU 识别」，并能录一段音频转出文字。
- NPU 模型下载完成后，再录一段确认出现试用提示。检查通过后回到 NPU 状态。未适配的芯片应显示 CPU 状态或 CPU 下载提示。
- 真机与实际 NPU 推理待验收。
