## 0. 背景（Claude 已查明并实测）

#58：用户用智谱 GLM Coding Plan（`https://open.bigmodel.cn/api/coding/paas/v4`，模型 `glm-5.3-flash`），“检测”全过，但整理卡在“第 1/8 批 · 等待模型”。
- `NetLlmClient.chat()` 整理类 JSON 请求是非流式、总时限 200 秒（`LlmClient.kt:47` callTimeout 200 / readTimeout 180）。
- 批次 `DigestBatches.MAX_BATCH_CHARS = 40_000`，与模型无关。
- `DigestRunner` 只有 `LlmError.Format` 会 `splitForRetry` 切半；**超时只原样重试同样大的一批**，慢模型永远过不去。截断（finish_reason=length）表现为 Format，会切，但计入格式失败次数。
- GLM-5.3 系列只能思考（官方 `thinking.type` 只收 enabled）。`NetOptions.kt` 对它开思考、max_tokens ≥ 16384。

11-20 用负责人的 Coding Plan 密钥实测（合成会议原话，整理用 JSON 提示，非生产提示词）：

| 批次 | 思考 | 耗时 | 思考字数 | 输出 | JSON |
|---|---|---|---|---|---|
| 12k 字 243 句 | 默认 | 93 秒 | 8413 | 4037 | 可解析 |
| 12k 字 | `reasoning_effort: "low"` | 30 秒 | 237 | 4578 | 可解析 |
| 40k 字 800 句（流式） | 默认 | 159 秒（2 秒首包） | 14773 | 7147 | 可解析 |
| 40k 字（流式） | `reasoning_effort: "low"` | 60 秒（2 秒首包） | 179 | 7238 | 可解析 |

结论：40k 默认思考已逼近 200 秒；真实提示更长 → 超时。`reasoning_effort: low` 智谱接受，快 3 倍、省 3 倍；流式 2 秒即有数据。

## 1. JSON 类请求改流式接收 + 空闲超时

- `NetLlmClient.chat()`（整理、专题、导入纪要、技能、回顾等所有走它的 JSON 请求）内部改为 `stream: true` + `stream_options.include_usage`，累积 `delta.content`；同时累积 `delta.reasoning_content` / `delta.reasoning`（只用于判断“会思考”和进度字数，不进结果）。对外返回值不变（`NetReply`），调用方无感。
- 超时改为：**空闲超时 90 秒**（这段时间没有收到任何字节，含思考内容和 SSE 注释/心跳）+ **总上限 10 分钟**。连接超时保持 15 秒。替换掉原 200 秒总时限（只对这类请求；问问的流式、检测探针保持现状）。
- **不支持流式的服务商**：返回非 SSE（`Content-Type` 不是 `text/event-stream` 且是完整 JSON）时直接按非流式解析；返回 4xx 且正文提到 stream 时，改用非流式重发一次（总上限 10 分钟、读超时 5 分钟），并按“服务商+模型”记住，之后直接非流式。记忆存本机（不备份，按卡 190 的分类登记）。
- `finish_reason` 照常交给 `trace`；流式里取最后一个非空 `finish_reason`。usage 缺失时记 0，不报错。
- 取消协程要立即关闭连接（沿用现有做法）。

## 2. 超时、截断都“切小重试”，不计格式失败

- 新错误种类（可扩展的方式，不要塞进 Format）：`TooSlow`（空闲超时/总上限）、`Truncated`（finish_reason=length 或 JSON 中途截断且 finish_reason=length）。
- `DigestRunner.digest`、`TopicBatches.read`/`TopicProcessingSession.splitRead`、`ImportSummary`：遇到 `TooSlow`/`Truncated` → 和 Format 一样 `splitForRetry` 切两半各自处理；**不计入** `MAX_FORMAT_FAILURES`。切到最小（现有最小行数规则）仍 TooSlow → 按现在的网络类错误处理（稍后重试、记失败原因），不标“已整理”丢原话。
- 卡 217 的专题块：块内已按 2400 字切，`TooSlow/Truncated` 走它现有的拆分路径即可，核对不会因此把整块判失败。

## 3. 每个模型记住合适的批次大小（自适应）

- `:shared` 新增 `LlmBatchBudget`（存取注入；Android 用 SharedPreferences `llm-batch-budget`，**不备份**，登记分类）：键 = 服务商 id + 模型名。
  - 默认上限 = 现在的 40_000 字。
  - 观察到会思考（响应里有思考内容）且用户**没开**“整理前先思考”：起始上限 20_000。
  - 遇到 `TooSlow` 或 `Truncated`：上限减半（最低 4_000），立即对当前批生效（切半）。
  - 连续 5 批成功：上限 ×1.25，不超过默认。
  - 用户换了服务商/模型自然是新键；“检测”成功不改上限。
- `DigestBatches.batches` 增加 `maxChars` 参数（默认不变），`DigestRunner` 用 `LlmBatchBudget` 当前值；`MAX_LINES` 不变。
- 导入纪要/专题的 2400 字切分不受影响（已很小）；只在它们遇到 `TooSlow/Truncated` 时按第 2 节处理。

## 4. 能调低思考强度的就调低（只对实测确认的服务商）

- `NetOptions.applyNetOptions`：`host == "open.bigmodel.cn"`（含 `/api/coding/paas/v4` 等路径）且 `model.startsWith("glm-5.3")`：
  - 用户**没开**“整理前先思考”→ 加 `reasoning_effort: "low"`（实测有效）；
  - 开了 → 维持现状（思考 enabled，max_tokens ≥ 16384），不加 low。
- 其他服务商不新增猜测参数。把“只能思考、可调强度”的规则写成可扩展的表，交付说明里列出以后补充的办法。

## 5. 进度与提示（给界面的数据）

- 流式累积时上报：已收到思考字数、已收到正文字数（`DigestProgress` 现有“等待模型 x 秒”的数据旁边加两个数）。提供给界面的文字由 Claude 改；你提供数据和一个 `:shared` 的格式化函数草案即可（如“模型思考中 · 已收到 3,200 字”/“正在写结果 · 已收到 1,800 字”）。
- 同一服务商连续 2 次 `TooSlow`：失败原因/提示文字为“这个模型较慢，已自动把每批改小，整理会久一点”。不要说成“连不上”。

## 6. 检测里加“整理速度”

- `AndroidDigestSettings.check()` 结果里新增一项 `ModelCheckItem`（feature 名称建议“整理速度”）：发一段约 3000 字的固定合成原话（放 `:shared` 常量，不含真实隐私），按整理的 JSON 要求请求一次，记录耗时、是否思考、输出是否可解析。detail 例：“约 18 秒一批（3000 字），会思考” / “约 6 秒一批，不思考”。失败不影响其他检测项。
- 这项会花一点额度；只在用户点“检测”时跑。
