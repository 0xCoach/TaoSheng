# 收集箱持久化收单与启动事务泄漏修复-交付说明

## 背景

真机（小米 14 Pro / 澎湃 OS）发现：分享图片、文本给「声声不息」，文件复制进私有目录
但 `capture_items` 无行；`dao.insert` 返回正常 id、日志 `receive done count=1`，
独立查库却没有数据——**假提交**。表现为 17:28 起整库（segments/heartbeats/
watchdog/capture）写入冻结，跨进程重启复现。

## 根因（真机二分定位）

`IdeaRepository.fromItem`：`dao.transaction { create() }`，而 `create()` 内部
`withContext(io)`——**挂起事务块里跨调度器挂起**，外层事务被拖成永不提交，
连接池写者连接被占死；后续所有 insert 以 savepoint 形态挂在该外层事务下返回
id，但对外部连接不可见，外层事务不提交即全丢。

二分过程：两块启动协程（ensureSeeded+ideas.syncFromDigest /
decisionRepo+followupEngine）全禁→写恢复；只恢复第一块→复现；再只禁
ensureSeeded+syncFromDigest→恢复；拆 `fromItem` 冗余事务（单 insert 本不需要
显式事务）→全部恢复后写正常。

## 改动（提交 eec2cf45 + 1c39757c）

### CaptureInbox.kt：持久化收单

- `receive` 用 `scope.async(io){…}.await()` 挂应用存活期 scope（Activity 销毁/
  lifecycleScope 取消不丢单），替换原 `withContext(scope.coroutineContext + io)`。
- **spool 先行**：入库前落 `files/capture-spool/*.json` 票。
- **独立连接回读验证**：insert 后用第二条 `SQLiteDatabase` 连接 `WHERE id=?`
  回读——同连接回读会被未提交事务骗；读不到→留票+warn，诚实不报成功。
- **对账自愈**：启动时和每次收单前扫 spool，无去重命中的重插，已有行清票；
  失败留票等下次。
- 诊断日志：action/type/文本数/来源、入库计数。

### ResoundApp.kt：启动写任务串行

- 预热 `database.readSql("SELECT 1")`：打开/迁移事务在**不可取消应用 scope**
  先跑完，避免首个 db 调用方（可能是可取消的 lifecycle/UI flow）在打开事务
  中途被取消造成同类泄漏。
- ensureSeeded → ideas.syncFromDigest → decisionRepo.syncFromDigest →
  followupEngine.scan → captureInbox.reconcile **串行在同一协程**，不再多协程
  并发争抢首连接。`events.collect` 单独协程不变。

### IdeaRepository.kt

- `fromItem` 拆掉 `dao.transaction{ create() }`：单 insert 无需显式事务，且
  内部 `withContext` 在事务块里是危险形态。
- `merge`/`convertToTodo` 的多写事务保留（真原子性需要）。

## 验证

- 真机：强杀→冷启动分享→`receive done count=1`、无池等待、独立查库行在
  （probe10-15 全部落盘）；wedge 期间的假提交经 spool 对账**救回**（id 4-7
  补入），`capture-spool` 清空。
- 单测：`:app:testDebugUnitTest` collect/inbox 全过（含 spool 对账用例）。

## 遗留 / 边界

- **同类风险面**：任意可取消协程（lifecycleScope/flow 采集器）里挂起 dao 调用，
  若在事务中途被取消，仍可能泄漏会话事务——本次收单路径已用应用 scope 免疫，
  其他 UI 写路径未逐个排雷；建议后续统一「dao.transaction 内不调含
  withContext 的挂起函数」规约。
- 线下断网复合测试（断网→分享→恢复）受无线调试通道限制未全自动跑通；
  断网本身不改写入语义（本地库不依赖网络），但严格 E2E 标 NOT_TESTED。
- `local_asr` 进程同期存在但未证实其持库；若后续仍见写锁异常需复查其
  是否接触主库文件。
