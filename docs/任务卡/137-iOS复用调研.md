# 卡 137：iOS 复用调研（只调研，不改代码）

## 背景

负责人近期会启动涛声 iOS 版开发（不是现在立刻开发）。从现在起，所有新开发都要尽量能被 iOS 复用。
同时外设接入正在改造：要做自有协议 TaoEcho（设备分 1～4 级，核心只认 TaoEcho 模型，插件做翻译器），协议和插件逻辑要求平台无关。
本卡要弄清楚：现有代码哪些能直接给 iOS 用、哪些和安卓绑死，以及 iOS 走哪条路线最合适。

## 要回答的问题

1. **现有代码摸底**：按包（`app/src/main/java/app/resound/` 下的 ask、audio、backup、capture、data、devices、digest、importer、transcribe、voiceprint 等）逐个判断：
   - 纯 Kotlin、几乎不碰 `android.*` 的（可直接共用）；
   - 逻辑和安卓混在一起、拆开后可共用的（估算拆分工作量：小/中/大）；
   - 本质依赖安卓、iOS 必须重写的（录音服务、前台服务、无障碍、通知、Room 数据库等）。
   用表格给出，并统计大致代码行数占比。数行数用 `find` + `wc -l` 即可。
2. **两条路线比较**：
   - A. Kotlin 多平台（KMP）：共用逻辑模块 + 两边各自原生界面（安卓 Compose，iOS SwiftUI；或评估 Compose Multiplatform 的 iOS 成熟度）；
   - B. iOS 用 Swift 完全重写。
   比较：工作量、长期维护成本、对现有安卓代码的改动量、风险、构建要求（是否必须 Mac + Xcode）。给出推荐和理由。
3. **关键依赖在 iOS/KMP 上的替代**：Room 数据库（Room KMP / SQLDelight）、OkHttp 等网络、JSON、协程、Silero VAD（onnxruntime 的 iOS 版）、声纹模型、Opus 解码、加密（ECDH/AES/HKDF/ECDSA 验签）、WorkManager 类后台任务、文件存储。每项写清可用方案和成熟度。
4. **iOS 平台硬限制**（只列与涛声相关的，给官方出处）：
   - 后台长时间录音（音频后台模式）能否全天持续、会被系统停掉的情况；
   - 低功耗蓝牙后台（bluetooth-central 后台模式、状态恢复、后台扫描只能按服务 UUID 过滤）；
   - 拿不到蓝牙 MAC 地址、不能指定 MTU、不支持经典蓝牙 SPP（非 MFi）；
   - 无法监听文件夹、无障碍类功能（读其他 App 内容，如微信）基本不可做；
   - App Store 审核对全天录音、录音提示灯可关闭（常灭）等功能的相关条款。
5. **外设模块具体建议**：基于 `devices/` 和 `devices/core/` 现状，以及待合并的 PR #30（录音豆，`gh pr diff 30` 可看），给出“共用模块”的划分：哪些放共用、哪些留平台层，平台层的接口大概长什么样（只写接口清单和职责，不写实现）。
6. **从现在开始的开发约定建议**：为了以后好复用，新代码应遵守哪些规则（例如：业务逻辑不 import android.*、时间/文件/日志通过接口注入等），写成 5～10 条可以直接放进 AGENTS.md 的条目。
