# 卡 226 交付说明：模型卡住不出字时专题也换备用模型；问题记录列出专题每块状态

## 起因
11-23 用户的“培训”专题（10:00–12:02，13 块）整理到 10/13 就停了，3 块没整理成。问题记录显示主模型 VIPDLab DeepSeek-V4-Flash 返回 200 后约 90 秒一个字都没出（chars=0），判为“模型响应超时”。备用的 DeepSeek 官方当时能用，却没被用上。

原因在 `LlmFailover.classify`：整理、专题这类“会自己切小”的调用遇到超时，一律交给调用方切小，不切备用模型。专题切小后还是请求同一个卡住的模型，每次再等 90 秒，最后这一块记为失败。切小只对“在写但写不完”有用，对“服务卡住一个字不吐”没用。

第一轮排查时问题记录里没有专题进度，只能靠用户截图才看清是“3 块没整理成”，不是等转写。

## 做了什么
- **区分两种超时**：`JsonLlmReceive` 记下这次请求有没有收到过正文或思考（心跳、空行不算）。超时时没收到过就标 `silent`，一路带到 `NetLlmException` → `LlmException`（备用模型都失败后抛出的异常也保留）。
- **silent 超时一律换备用模型**：包括整理（`LlmSplitsOnSlow`）和专题（`TopicRequestContext`）。主模型照常冷却 5 分钟，后面的块直接用备用模型，不再先等主模型超时。切换原因写成“模型长时间没有响应”；有输出但太慢的写“模型响应太慢”（原来都写“模型服务出错”）。
- **有输出但太慢、输出被截断**：行为不变，仍交给调用方切小重试。
- **没配备用模型或备用也卡住**：和原来一样，回到切小重试，最后记为没整理成，可点“补上没整理成的 N 块”。
- **问题记录新增“专题进度”**：最近 3 天动过的专题（最多 10 个），列出阶段、已整理/失败块数、在等转写/认人/网络、卡住原因、最近进展时间，以及每块的时段、状态和失败原因。只有固定文案，不导出原话、要点和纪要。专题编号和“大模型响应摘要”里的 `topic=` 对得上。

通用规则，对所有配了备用模型的人生效，没有为某个服务商单独加判断。

## 没做的
- **没有缩短 90 秒的等待**：思考型模型开头可能很久不出字，“整理前先思考”又默认打开，缩短会误伤正常请求；也看不出该定多少秒。有了本卡，卡住时只等一次 90 秒就换模型。
- 没改专题失败分类（`topicFailure` 里超时仍按“容量”切小），避免没配备用模型的人失去切小重试。

## 怎么验证的
- 新增 `SilentTimeout226Test`（4 个）：头之后无字节 → silent；只有心跳直到 10 分钟总时限 → silent；先有思考再卡住 → 不是 silent；先有正文再卡住 → 不是 silent。
- 新增 `LlmFailoverSilent226Test`（5 个）：专题 silent 超时换备用并冷却主模型、下一块直接用备用；整理 silent 超时也换；有输出但慢仍交给调用方切小（整理、专题两种上下文）；截断不算 silent；全部模型都卡住时 silent 标记保留。
- 新增 `TopicDiagnostics226Test`（2 个）：列出块状态和原因，不含原话、要点、纪要，3 天前的不列；没有文件、文件损坏不出错。
- `LlmAdaptive218Test`、`LlmFailover103Test`、`DigestSplitRetryTest`、`TopicAdaptive218Test` 等相关用例全过。`topic` / `digest` / `diagnostics` 三个包共 187 个用例，186 过。
- 唯一失败的 `DigestTiming053Test.manualIntentTravelsWithWorkAndSurvivesSettingsUpdate`（List has more than one element），在未改动的 HEAD 上同样失败，是原本就有的问题，与本卡无关，未处理。

## 没验证的
- 没有真机复现 VIPDLab 卡住的情况，是按问题记录里的现象（200、chars=0、约 90 秒后超时）用合成流测试的。
- 未发版：等下一个预览版一起出。
