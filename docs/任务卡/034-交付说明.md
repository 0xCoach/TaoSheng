- 无目的端基准、基准缓存丢失/损坏、满 7 天、数据库版本或页设置变化、增量 ZIP 超过完整 ZIP 的 50% 时生成完整包。阈值比较包含文件差异和头信息，以本次实际压缩归档大小计算。
- 私有基准位于 `files/backup-base/<完整包名>.db`，旁边保存完整清单。云端和本机分别记录当前基准，成功上传/写入后才原子更新；新套提交后清理无引用缓存，正常最多保留两套基准。两端分别生成完整包，因此各保留自己的基准。
- 文件名使用 `resound-full-<时间>-<随机>.zip(.enc)` 和 `resound-inc-<时间>-<随机>__<基准时间>-<基准随机>.zip(.enc)`。列表直接从文件名解析 `full` / `baseName`，无需额外请求旁注文件。
- 清理保留最新 N 个恢复点及其完整依赖；云端只清理 `Resound-Backup/`，本机只清理匹配规则的英文备份，延续旧中文备份保护。计数为目录中实际恢复点数，包括被依赖保留的完整包；字节数为这次实际归档大小。
- AES 整包加密沿用原实现。更换/关闭口令后两端重新开套；备份途中更换口令，旧口令生成的包不会成为新口令的基准。

## 快照方式与本机数据估算

原 `VACUUM INTO` 会重新排页。依据下面的实测，生产快照改为保留页布局的 Android SQLiteDatabase 复制：在源库 IMMEDIATE 事务期间复制主库和 WAL，释放事务后在隔离副本上由 SQLite checkpoint 合并 WAL，再转为 DELETE journal。完整与增量使用完全相同的方法，保留 page_size / auto_vacuum；没有直接复制活跃库后就将其当成完整快照。现有并发写入一致性测试通过。

仅使用 `resound-local-lab/private/` 已有副本，在临时目录复制主库及已有 WAL 后测量，未改原文件、未输出业务内容、未上传。可用副本都在 2026-10-23，并没有跨日的同版本实测样本：

- `snapshot/capture.db`：20:13 的副本，数据库版本 8，174 条 segments。
- `identity-20261023/capture.db`：22:17 的副本，数据库版本 8，226 条 segments。
- 23:20 的另一个副本已是版本 9，不用于同套差异比较；生产逻辑在此情形必须出完整包。

在前两份真实副本上分别用桌面 SQLite `VACUUM INTO` 和 `sqlite3.Connection.backup` 生成快照，逐页比较，并用 ZIP/Deflate level 6 打包数据库、页补丁及对应格式清单。以下是数据库部分的估算，不含设置、声纹等附属文件，也不是 Android 实际导出的精确体积：

| 场景 | 当前库大小 | 变化页 / 当前页 | 完整 ZIP | 增量 ZIP | 增量/完整 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 两份历史副本，VACUUM | 552,960 B | 125 / 135 | 201,043 B | 197,281 B | 98.1% |
| 两份历史副本，保留页布局 | 569,344 B | 96 / 139 | 175,476 B | 126,620 B | 72.2% |
| 后一份真实库的副本，仅更新 3 行 attempts | 569,344 B | 1 / 139 | 175,497 B | 1,553 B | 0.9% |

结论：选择保留页布局的方法；这组历史副本仍超过 50%，按方案应生成约 175 KB 的完整数据库包。轻量更新的受控场景约 1.6 KB / 175 KB，但不能将其宣称为真实“每晚大小”。真实每晚大小取决于当天转写、事件和文件变化，还需负责人隔夜采样；不能从约两小时的副本线性外推整晚。桌面在线备份用于比较布局，Android 实际使用上面说明的受锁保护复制及 WAL 合并。

## 恢复步骤

1. 用户选择完整包或增量包；加密时按原流程输入口令。
2. 增量从同一云端目录或授权本机目录自动取得 `baseName`，只需要这两份文件。
3. 解密并验证完整包，检查基准数据库 SHA。丢失、损坏或 SHA 不符提示“这份增量对应的完整备份已损坏或丢失”。
4. 在隔离目录应用页补丁、截断/扩展到当前总页数，检查结果 SHA，再应用文件差异与删除清单，校验最终完整内容。
5. 继续原来的 Room 迁移/校验、恢复前本地快照、暂存、关闭数据库、重启替换与密钥清空流程。任何前置校验失败都不替换正在使用的数据。
6. 旧英文/中文完整 ZIP 和加密备份继续通过原完整内容验证路径恢复。
