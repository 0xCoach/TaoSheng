## 卡 175 的数量差异

结构文件不记录这些手写触发器，只按 schema 建出的库并不是历史版本实际首次打开后的库：

- 起点 v1～v17：升级会经过 `10→11` 或 `17→18`，搜索 install 恰好会补齐 10 个；再经 `26→27`、`28→29` 和打开回调，得到 15 个。
- 起点 v18～v26：跳过两个搜索 install 入口，缺搜索 10 个；寻物迁移仍会执行，加导入与待整理缓存，共 5 个。
- 起点 v27～v32：连寻物迁移也跳过，缺搜索 10 个和寻物 3 个；只有 `onOpen` 补建的导入、待整理缓存，共 2 个。

本卡“只建 schema”的 v18 / v27 对照组分别复现 5 / 2 个，并断言具体缺失名单，也验证新增原话不会进入 `lines_fts`。同版本加上真实历史回调后，升级得到完整的 15 个。这解释了夹具差异，不能据原夹具的数量认定手机已有缺口。

## 用户影响、是否回填与修法建议

本次未发现正常升级的触发器缺口，因此**不需要给用户回填索引，也不为夹具差异改产品代码**。v10 及更早版本首次进入 v11 时，已有 `SearchIndex.install(backfill = true)` 一次性回填三张新建 FTS 表；后续升级保留其索引，v17→v18 恢复触发器时不重复回填。

如果以后实库另有损坏或非正常建库证据，缺失的实际影响如下，不能把这些假设当成此次已发生的事故：

| 缺失类别 | 可能影响 |
|---|---|
| 搜索增删改 | 新原话、事件、待办/条目可能没有索引，编辑后的旧词可能残留；删除后 FTS 行可能残留，最终是否返回还受原表关联和删除过滤约束 |
| 搜索事件/条目更新、删除及 `search_event_hidden` | 对应 embedding 未按改动或软删除失效，语义索引可能过期 |
| 导入删除联动 | 删段后旧纪要可能未撤销、修订号和重转写状态未更新、最后一段删除后导入记录未清理 |
| 寻物来源清理 | 已删原话/事件的待确认发现可能残留；已确认记录可能保留失效的来源 ID |
| 待整理缓存清理 | 来源原话已删除，缓存回复仍可能留下，后续恢复存在引用失效来源的风险 |

若届时确证缺失，优先考虑将现有搜索 `install(backfill = false)` 和寻物 `install` 加到 `onOpen`，沿用 `CREATE TRIGGER IF NOT EXISTS`，不加版本。但补触发器只覆盖以后的写入，不能自动修复已漏掉或过期的 FTS 数据。一次性修复应在同一写事务内：确认缺失 → 安装触发器 → 清空相应 FTS 表 → 按原表当前全量行、主键 rowid 和现有分词 SQL 重建 → 校验后提交；失败回滚，下次仍可重试，避免并发写入造成窗口。不能仅追加调用当前 `backfill = true` 当成完整的幂等修复，因为该分支没有清理原有过期行。已确认“触发器齐全但索引损坏”的情况需要单独的修复完成标记或显式维护操作。embedding 失效和来源清理若也受影响，应另行评估，不能仅以 FTS 回填冒充全部修复。
