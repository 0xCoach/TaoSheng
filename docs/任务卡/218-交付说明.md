1. JSON 调用与服务商差异

NetLlmClient.chat 保持 NetReply 不变，内部请求 stream=true 和 include_usage。累积 content，仅统计 reasoning_content/reasoning 字数，不保存或返回思考正文。SSE 最后一个非空 finish_reason 交给 trace；缺 usage 按 0 处理。

连接 15 秒；任何字节（包含注释、心跳和未结束的行）均刷新 90 秒空闲计时。一次逻辑请求包含路径探测及兼容回退，共用 10 分钟总上限。协程取消通过 execute 作用域关闭响应。手动待办、寻物已有业务层 20 秒取消仍保留。

非 SSE 完整 JSON 直接解析。4xx 正文提到 stream 时只回退一次，非流式读取空闲上限 5 分钟；按服务商 id + 模型名记忆到 llm-stream-support。仅记能力，不记正文/密钥，不备份。普通完整 JSON 兼容响应不自动登记“不支持流式”。问问的 SSE/工具实现和原有轻量检测探针维持原行为。

只有官方 open.bigmodel.cn 的 glm-5.3*，在未开“整理前先思考”时加 reasoning_effort=low；开启时维持原有 enabled 和输出额度。其他服务商不增加猜测参数。以后扩充 NetOptions 的 FIXED_THINKING_RULES 时，需先确认官方域名、模型前缀及实际支持的强度值，并补对应请求体测试；协议字段不同的服务商应另外实现自己的选项分支，不能照搬 GLM 参数。问问、旧探针不启用新降强度规则。

2. 拆小与预算

新增 TooSlow、Truncated，均可稍后重试；它们在备用服务切换之前交回业务拆分，不计入 MAX_FORMAT_FAILURES。整理沿用现有 splitForRetry 最小行数规则；最小批仍失败时保留未整理原话，不 markDigested。子批保留独立请求身份、在途凭据与缓存恢复，已有已付费缓存优先重放。

LlmBatchBudget 放在 shared，通过 LlmAdaptiveStore 注入存取；Android 使用 llm-batch-budget。按服务商 id + 模型名分开：默认 40k、观察到思考且用户未主动开启时初始化 20k、慢/截断减半到最低 4k、连续 5 次业务成功后增加 25%，最高 40k。用户从开启思考切到关闭时也应用已观察到的能力；一旦初始化完成，后续可以正常增长。当前轮后续批次重新读取预算，MAX_LINES 不变。不可再分的单条原话允许超过学习预算，但仍受原 40k 绝对上限约束。

同一服务商连续两次 TooSlow 的失败原因使用“这个模型较慢，已自动把每批改小，整理会久一点”。正常成功或其他模型错误中断该连续计数。

当前基线已无 TopicBatches：卡 217 的 TopicProcessingSession/TopicBlockGenerator 处理专题，已接入原有拆分路径，保留成功子块检查点。专题仍按 2400 字分块；普通导入实际仍走旧的 18k ImportChunks（任务卡对此的描述与基线有差异），本卡保留原切块大小，仅为有/无 session 的导入都补齐自适应错误拆分。

两个新增偏好文件均登记在 PreferenceBackupPolicy.excluded；安卓系统备份原本关闭，应用备份也不会导出它们。

3. 给 Claude 的界面接入点

- DigestProgress.reasoningChars / contentChars：当前请求累计接收字数。每次请求（包括拆分后的子请求）归零；原来的 done/total 仍按落库进度更新。
