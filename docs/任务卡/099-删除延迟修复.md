# 099：删除延迟回归修复

## 原因

- 用户反馈 0.2.15 右滑两次和长按多选都删不掉，手机停在“正在处理 0 / 1”。随后事件数从 203 变成 202，确认是严重延迟。
- 设备数据库诊断抓到七天节奏基准查询：单次约 4.3 秒，完整事务约 21.7 秒；读取完整原话并逐句执行媒体事件重叠子查询，大结果分页反复执行 SQL。
- 查询来自 `3384ee0`；`858c1bb` 修复批量删除读写冲突时增加 `@Transaction`，把已有慢查询放入与删除共享的事务调度，造成性能退化。此前小样本手势和删除测试未覆盖该真实数据规模。
- 初步怀疑的“原话找不到录音条目”没有证据支持，不作为本次根因或修复项。

## 修改

- 七天统计改为时间、事件类型和人物字段的轻量快照，不加载原话正文、语音输入上下文等大字段。
- 同一短事务读取一致快照；媒体区间匹配、分组、中位数计算放到事务外。媒体按开始时间排序，用前缀最大结束时间和二分查询匹配，保持跨日、部分重叠即整句排除及严格边界语义。
- 合并排队的失效通知；历史区间快照相同不重复匹配和统计。今天变化仍触发轻量快照检查，不声称完全没有数据库查询。
- 同一事件正在删除时复用结果，防止重复排队；单条与批量删除显示等待前一项、等待音频、等待数据、删除记录、清理录音等阶段。
- 添加分阶段耗时诊断，仅记录阶段和耗时，不记录原话、路径或事件 ID。
- 数据库版本、Contract 和统计口径不变；没有直接撤销一致性保护，也没有新增索引或数据库迁移。

## 验证

- 小米 14 Pro 独立 validation 包合成测试通过，独立内存数据库、14,000 条原话、2,800 个历史事件，另有 20 个当天事件供删除。测量前安装生产搜索/寻物触发器并填充搜索索引；测试不读取用户数据库或调用模型。

- 新旧统计结果一致；本地另外覆盖窗口外媒体与跨窗口长句、跨日媒体、重叠/相邻媒体、失效事件、历史修改后刷新、重复删除合并及阶段清理。
- 0.2.16-preview.1（53）Release 构建和签名验证通过，覆盖安装到手机。真实历史数据只读测试通过：以前一天、当天为截止日期的两个七天窗口分别 164 ms、369 ms，包含快照读取与计算。
- 用户随后明确反馈“测试下来没问题”，完成实际删除体验复测。
- 测试组件与本轮独立 validation 包已卸载，主应用重新打开，录音前台服务已恢复。未替用户试删真实记录。
