## 专题中的 QuickAction 约定

| 状态 | 入口顺序 | Pause / Resume 的实际含义 |
|---|---|---|
| Running | 记一下、暂停专题、结束专题 | Pause → `topics.pause()` |
| Paused | 继续专题、结束专题 | Resume → `topics.resume()` |
| 无专题、聆听中 | 按上次时长暂停、开始上次类型专题 | Pause → `capture.pause(lastPauseMinutes)` |
| 无专题、已暂停 | 现在恢复、开始上次类型专题 | Resume → `capture.resume()` |
| 无专题、停止/不可用 | 开始聆听、开始上次类型专题 | StartListening → `capture.start()` |

专题操作优先于普通聆听动作，不把“暂停专题”解释成暂停全天录音。开始专题仍沿用仓库行为：录音关闭或覆盖停录时段时给出对应提示，不额外暗中打开录音。`通话 / 访谈` 的快捷入口去掉空格，成为“开始通话/访谈专题”。

## 体检规则与事实口径

问题按任务卡顺序，Critical 在前，最多 3 条。缺通知权限也归“录不了音”（当前录音控制器要求通知权限）；手动暂停、冷启动尚有效的已保存暂停和停录时段均不提示“录音没开”。余额未知/查询失败不会被当成余额耗尽，零或服务端 unavailable 才是 Critical；低余额提醒沿用现有人民币阈值，非 CNY 不与人民币提醒线比较。只提示已开启的备份通道的失败。

守护原始日志映射为纯数据 `HealthWatchdogEvent(at, type, detail)`，规则如下：

| 事件 | 是否算异常中断 |
|---|---|
| Killed | 是；同次恢复前排除停录时段后形成的多条缺口合并一次 |
| ServiceStopped | 仅 detail 含现有 fail() 的“等待手动恢复，保留未正常停止标记”算；“用户正常停止”和原因未知的旧日志不算 |
| MicBusy | 非“通话中”且连续超过 5 分钟算一次；正好 5 分钟不算。包含其他 App 占麦及持续的输入异常；连续重开记录不重复计数 |
| Recovered | 不单独算；结束本次重启去重区间 |
| ServiceStarted、BootRestart | 不单独算；作为新运行区间边界 |
| Paused、Resumed | 不算（含手动暂停、停录时段） |
| MicReleased、InputSwitched | 不算，只关闭前面的占麦区间 |

异常 ServiceStopped 后的 Killed 不再重复算。占麦按 MicReleased/暂停/服务边界等闭合，未闭合时仅在当前确为 MicBusy 时延长到现在，防止把陈旧日志当成一直占麦。占麦事件按开始时刻归日；Killed 按守护日志发现时刻归日（原日志本来就是重启时补记）。所有日期均按当前设备时区换算，未知旧事件类型不计。

`interruptionsToday` 在历史尚未加载时为 null，加载后计算今日次数。`stableDays` 为今天自然日编号减最近一次异常日编号（昨日中断 → 1，今日中断 → 0）；没有可识别的历史异常时返回 null，不拿安装日期臆造稳定天数。若日志被清除，则同样无法推定更早历史。

`nextBackupAt` 使用现有 `BackupScheduler` 的实际规则：每天本地时间 **03:10**。取今天尚未到的 03:10，否则取明天 03:10；日期转换由 Android 使用设备时区完成，纯规则只挑未来候选，跨夏令时不直接加 24 小时。云端或本机自动备份任一开启才返回，否则 null。这是计划估计，不是执行承诺：WorkManager 可能延后，云端还需网络。本卡不改变备份调度，也不把它显示成不存在的“今晚 22:00”。界面建议写“凌晨 03:10 左右，或条件满足时”。
