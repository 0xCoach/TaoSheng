# TaoEcho 录音设备协议 0.1（内部草案）

> 状态：**内部草案，未对外发布，随时可改。** 发布 1.0 前至少要有一家外部厂商按本规范做通。
> 许可：规范文本 CC BY 4.0；参考代码（参考固件、自检工具）MIT。
> 维护：涛声（TaoSheng）项目，GitHub 组织 `taoecho-app`。
> 日期：2026-11-11

## 0. 一页看懂

- **TaoEcho 是什么**：录音设备（录音卡、吊坠、录音豆、DIY 板）和手机 App 之间的通信规则。按它做的设备，涛声不用写任何代码就能接入（设备分级里的 **2 级**）。
- **传输**：只用低功耗蓝牙（BLE）。设备当外设，手机当中心。不用经典蓝牙（iOS 不支持）。
- **结构**：一个固定的 TaoEcho 服务，下面 4 个通道：命令、回复与事件、实时声音、文件数据。
- **三层功能**：
  1. **基础层（必须）**：握手（版本、设备身份、功能清单）、绑定、错误码；再加“实时声音”或“离线文件”至少一种。
  2. **标准可选层（有才声明）**：电量、录音控制、灯光、存储、按键、对时、识别我、诊断。
  3. **厂商扩展层**：用开关 / 数值 / 多选一 / 只读状态四种通用格式描述，App 自动画界面。
- **七条硬规则**（第 2 节）：安全保存后才能删；命令带编号；以设备确认为准；读不到就说未知；声音带时间；只认一部已绑定手机；版本只增不改。

用词约定：**必须** = 不做就不算合规；**应该** = 强烈建议，有正当理由可不做；**可以** = 自选。

## 1. 设计目标

1. **厂商好做**：只用 BLE GATT，消息格式是简单的二进制，单片机几 KB 代码能实现；不要求 JSON、不要求加密库以外的第三方库。
2. **跨平台**：安卓、iOS、以后的鸿蒙用同一套规则。凡是 iOS 做不到的（拿 MAC 地址、指定 MTU、经典蓝牙、后台按名字扫描）协议一律不依赖。
3. **录音不丢**：离线录音在 App 确认“安全保存”之前，设备绝不删除、绝不覆盖。
4. **不编造**：读不到的值报“未知”；命令结果以设备回报的实际状态为准。
5. **能演进**：老设备在新 App 上照常工作，新设备在老 App 上至少能用基础功能。

不在 0.1 范围：Wi-Fi 传输、固件升级（OTA）、LE Audio、多手机同时连接、设备端转写。留扩展位，以后加。

## 2. 七条硬规则

| # | 规则 | 具体要求 |
|---|---|---|
| R1 | **安全保存后才能删** | 设备只有收到 App 的 `FILE_CONFIRM`（第 7.4 节）后，才可以删除或覆盖该录音。“蓝牙已发出”“App 已收到”都不算。存储满时必须停止新录音并发事件，不得覆盖未确认的录音。 |
| R2 | **命令带编号** | 每条命令带 2 字节编号，回复带同一编号；失败返回统一错误码（第 9 节）。 |
| R3 | **以设备确认为准** | 改变设备状态的命令（录音、灯光、设置），回复里必须带**执行后的实际状态**，不能只回“收到”。 |
| R4 | **读不到就说未知** | 每个数值都有“未知”取值（第 4.3 节）。设备不得用 0 或上次的值冒充当前值。 |
| R5 | **声音带时间** | 实时声音和离线文件都要能换算到真实时间（第 6.3、7.2 节）。 |
| R6 | **只认一部已绑定手机** | 一台设备同一时间只绑定一部手机；未绑定或非绑定手机的命令一律返回 `NOT_BOUND`，不得收发录音（第 5 节）。 |
| R7 | **版本只增不改** | 同一个大版本内，只能新增命令、字段、能力；不得改变已有字段的含义。不认识的字段必须忽略（第 10 节）。 |

## 3. 蓝牙结构

### 3.1 服务与通道

设备**必须**提供 TaoEcho 主服务，并**必须**在广播包里带上主服务编号（iOS 后台只能按服务编号搜设备）。

| 名称 | 编号（UUID） | 属性 | 用途 |
|---|---|---|---|
| TaoEcho 主服务 | `92b00000-fd76-4fa1-b8b5-4b3450b4dc80` | — | |
| 命令 CTRL | `92b00001-fd76-4fa1-b8b5-4b3450b4dc80` | 写（带回应） | App → 设备：命令 |
| 回复与事件 EVT | `92b00002-fd76-4fa1-b8b5-4b3450b4dc80` | 通知 | 设备 → App：回复、事件 |
| 实时声音 AUDIO | `92b00003-fd76-4fa1-b8b5-4b3450b4dc80` | 通知 | 设备 → App：声音包（第 6 节） |
| 文件数据 FILE | `92b00004-fd76-4fa1-b8b5-4b3450b4dc80` | 通知 | 设备 → App：文件内容（第 7 节） |

- 只有声明了实时声音能力的设备才需要 AUDIO 通道，只有声明了离线文件能力的才需要 FILE 通道。
- 四个通道都**必须**要求加密连接才能读写（见第 5 节）。

### 3.2 复用蓝牙官方服务

| 服务 | 要求 | 说明 |
|---|---|---|
| 设备信息 DIS `0x180A` | **应该**提供 | 厂商名、型号、固件版本。App 以 TaoEcho 握手结果为准，DIS 用于系统层显示和兼容老工具。 |
| 电池 BAS `0x180F` | **可以**提供 | 只能表示一块电池；多块电池（如录音豆 + 充电盒）用 TaoEcho 电量能力（第 8.1 节）。 |

### 3.3 包大小（MTU）

- 设备**必须**能在任何协商出的包大小下工作（最小 23 字节）。iOS 不允许 App 指定包大小。
- 设备**应该**支持至少 185 字节，以保证实时声音的吞吐。
- 命令和回复超过一个包时按第 4.2 节分包。

### 3.4 广播

- **必须**：广播主服务编号。
- **应该**：广播名以可读型号开头（如 `Acme-Rec-1234`），末尾 4 位用设备序列号后 4 位，方便用户分辨同款多台。
- **可以**：广播里放厂商数据，App 不依赖它。

## 4. 消息格式（CTRL / EVT 通道）

### 4.1 消息头（8 字节，全部小端）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `ver` | 消息格式版本，0.1 固定为 `0x01` |
| 1 | 1 | `kind` | `0x01` 命令、`0x02` 回复、`0x03` 事件 |
| 2 | 2 | `id` | 命令编号（App 自增，0 保留不用）；回复带同一编号；事件为 0 |
| 4 | 2 | `op` | 操作码（附录 A） |
| 6 | 2 | `len` | 后面内容的总长度（字节），最大 4096 |
| 8 | len | `body` | 内容，TLV 格式（4.3 节） |

回复的 `body` 第一个字段**必须**是 `status`（TLV 标签 `0x00`，1 字节错误码，`0` 表示成功）。

### 4.2 分包

一条消息超过单包长度时，切成多个包依次发送，每个包前面加 1 字节分包标记：

- bit7 = 1 表示“这是该消息的第一个包”；bit6 = 1 表示“最后一个包”；bit0–5 是包序号（0–63 循环）。
- 不超长的消息也要带这 1 字节（值为 `0xC0`），这样收方逻辑统一。
- 收方发现序号不连续，丢弃整条消息；命令方超时后重发（同一编号）。设备收到重复编号的命令**必须**返回上次的回复，不得重复执行。

### 4.3 内容格式：TLV

`body` 由若干字段组成，每个字段 = 标签（1 字节）+ 长度（2 字节，小端）+ 值。

- **不认识的标签必须跳过**（这是版本兼容的关键）。
- 数值类型：无符号整数按长度 1/2/4/8 字节小端；有符号用补码；文本 UTF-8；布尔 1 字节（0/1）。
- **未知值**：数值字段用全 `0xFF`（如 1 字节电量 `0xFF` = 未知），布尔字段用 `0xFF`。也可以干脆不带这个字段，含义相同。
- 列表：同一个标签重复出现多次；结构体：值本身又是一段 TLV。

### 4.4 超时

- 命令的默认等待时间 3 秒；文件类命令 10 秒。超时后 App 可以重发一次（同一编号），仍失败就断开重连。
- 设备处理慢的命令**应该**先回 `status=BUSY_RETRY`，并在完成时发对应事件。

## 5. 连接、握手与绑定

### 5.1 流程

```
App 扫描（按主服务编号）→ 连接 → 系统加密配对（第一次）→ 订阅 EVT
  → HELLO（交换版本与功能清单）
  → 未绑定：BIND（设备上按键或闪灯确认）→ 保存绑定凭证
  → 已绑定：AUTH（出示凭证）
  → 正常使用（订阅 AUDIO / FILE，按功能清单操作）
```

### 5.2 HELLO（握手，`op 0x0001`）

App 发：自己支持的协议版本范围（最低、最高，如 `0.1`–`0.3`）、App 名称和版本。

设备回：

| 标签 | 字段 | 说明 |
|---|---|---|
| 0x01 | `proto` | 双方共同支持的最高版本，如 `0x0001`（0.1） |
| 0x02 | `device_id` | **设备序列号**，出厂固定、终身不变、全球唯一（建议 厂商前缀 + 序列号，≤32 字节）。**App 用它认设备，不用蓝牙地址**（iOS 拿不到地址）。 |
| 0x03 | `vendor` | 厂商名 |
| 0x04 | `model` | 型号 |
| 0x05 | `fw` | 固件版本，结构体：部件编号（1 字节，与 8.1 节电池部件编号一致：1 主机 / 2 充电盒…）+ 版本文本。多个部件（如录音豆主机和充电盒）就重复出现多次 |
| 0x06 | `hw` | 硬件版本文本（可选） |
| 0x07 | `caps` | 功能清单，重复出现，每个是一个能力结构（5.3 节） |
| 0x08 | `bound` | 布尔：当前是否已绑定某部手机 |

### 5.3 功能清单

每个能力 = 能力编号（2 字节）+ 能力版本（1 字节）+ 能力参数（TLV，可选）。

| 编号 | 能力 | 层 | 参数举例 |
|---|---|---|---|
| 0x0001 | 实时声音 `audio.live` | 基础（与文件至少一种） | 支持的声音格式列表、默认格式 |
| 0x0002 | 离线文件 `files` | 基础（与实时至少一种） | 是否支持从中间续传、校验算法、满了的策略 |
| 0x0101 | 电量 `battery` | 标准可选 | 电池部件列表（主机 / 充电盒 / 其他） |
| 0x0102 | 录音控制 `record` | 标准可选 | 支持开始 / 暂停 / 停止中的哪些 |
| 0x0103 | 灯光 `light` | 标准可选 | 支持的模式列表（默认 / 关闭 / 柔和 / 厂商预设） |
| 0x0104 | 存储 `storage` | 标准可选 | — |
| 0x0105 | 按键 `button` | 标准可选 | 按键列表 |
| 0x0106 | 对时 `clock` | 标准可选 | 设备是否有掉电保持的时钟 |
| 0x0107 | 识别我 `identify` | 标准可选（**应该**做） | 方式：闪灯 / 响声 / 振动 |
| 0x0108 | 诊断 `diag` | 标准可选（**应该**做） | — |
| 0x0201 | 设置项 `settings` | 厂商扩展 | — |
| 0x8000–0xFFFF | 厂商私有能力 | 厂商扩展 | App 不认识就忽略 |

App 只为清单里有的能力显示界面。

### 5.4 绑定（`BIND op 0x0002`）与认证（`AUTH op 0x0003`）

- **系统加密配对**：TaoEcho 通道必须要求加密。设备**应该**使用 LE 安全连接（LE Secure Connections）。第一次读写时由手机系统弹出配对。
- **BIND**：App 生成 16 字节随机凭证发给设备。设备**必须**要求用户在设备上做一次物理确认：
  - 有按键：提示用户按一下键（设备闪灯提示），按下后保存凭证并回成功；
  - 没有按键：设备闪灯，App 提示“看到设备在闪灯吗？”，用户在 App 里确认后再发一次 `BIND`（带 `confirm=1`）。
  - 30 秒内没确认，回 `BIND_TIMEOUT`。
- **只绑一部**：设备已绑定时，新的 `BIND` 回 `ALREADY_BOUND`。换手机要先在旧手机上 `UNBIND`（`op 0x0004`），或在设备上做出厂重置（长按等，厂商自定，**必须**写进说明书）。
- **AUTH**：之后每次连接，App 先发 `AUTH` 出示凭证。凭证不对回 `NOT_BOUND`。认证通过前，除 `HELLO`、`BIND`、`AUTH`、`IDENTIFY` 外的命令一律回 `NOT_BOUND`，AUDIO / FILE 通道不发任何数据。
- 设备**不得**把凭证通过任何命令读出来。

## 6. 实时声音（能力 0x0001）

### 6.1 格式

| 格式编号 | 格式 | 要求 |
|---|---|---|
| 0x01 | Opus，16 kHz，单声道，每帧 20 ms | **声明实时声音就必须支持**（与 Omi 一致，厂商改动最小） |
| 0x02 | PCM 16 位小端，16 kHz，单声道 | 可选，给压缩不了声音的便宜芯片 |
| 0x03 | PCM 16 位小端，8 kHz，单声道 | 可选 |

不收其他格式（ADPCM、AAC、LC3 等），以免 App 的解码工具箱越堆越大。**只收单声道**：双声道麦克风的设备须在设备端合成单声道后再发。

### 6.2 开始与停止

- `AUDIO_START`（`op 0x0101`，可带格式编号）→ 设备回成功和**实际使用的格式**，随后在 AUDIO 通道持续发包。
- `AUDIO_STOP`（`op 0x0102`）。
- 连接断开即视为停止。设备如果有离线存储，**应该**断开后自动改为存文件，重连后由文件能力补传。

### 6.3 声音包（AUDIO 通道）

每个通知包：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 2 | `seq` | 包序号，小端，逐包加 1，溢出回 0 |
| 2 | 1 | `frag` | 分片号：一帧放不进一个包时从 0 开始递增；bit7 = 1 表示本帧最后一片 |
| 3 | … | 数据 | Opus 帧（或其分片）/ PCM 数据 |

> 与 Omi 的差别只有一处：`frag` 的 bit7 表示最后一片，App 不用等下一帧才知道上一帧结束。

**时间对齐**：设备每 5 秒在 EVT 通道发一次 `EVT_AUDIO_SYNC`（`op 0x8101`）：

| 标签 | 字段 | 说明 |
|---|---|---|
| 0x01 | `seq` | 对应的声音包序号 |
| 0x02 | `samples` | 从本次 `AUDIO_START` 起累计的采样数（8 字节） |
| 0x03 | `utc_ms` | 设备当前时间（8 字节毫秒，未对时则为未知） |

App 用它发现丢包（序号跳了）和计算每段声音的真实时间；设备时间未知时，App 用收到的时刻估算。

## 7. 离线文件（能力 0x0002）

### 7.1 概念

- 一个**录音**是设备上的一段连续录音，有终身不变的 `file_id`（设备内唯一，删除后不复用）。
- 每个录音有三个状态：`recording`（正在写）→ `complete`（已结束，等补传）→ `confirmed`（App 已安全保存，设备可回收）。

### 7.2 列出录音（`FILE_LIST op 0x0201`）

App 可带“从哪个 `file_id` 之后开始”和“最多几条”分页；设备按开始时间从旧到新返回。每条：

| 标签 | 字段 | 说明 |
|---|---|---|
| 0x01 | `file_id` | 4 或 8 字节 |
| 0x02 | `state` | 1 字节：1 recording / 2 complete / 3 confirmed |
| 0x03 | `bytes` | 文件大小 |
| 0x04 | `format` | 同 6.1 节格式编号；离线文件另可用 0x10 Ogg Opus、0x11 WAV |
| 0x05 | `start_utc_ms` | 开始时间（对过时才有，否则未知） |
| 0x06 | `start_boot` | 设备启动编号 + 启动后毫秒数（未对时也能排序、事后换算） |
| 0x07 | `duration_ms` | 时长 |
| 0x08 | `checksum` | 文件完成后才有：CRC32（必须支持）或 SHA-256（可选） |

### 7.3 读取（`FILE_READ op 0x0202`）

- App 发 `file_id`、起始偏移 `offset`（声明了续传才可以非 0）、可选长度。
- 设备回成功和本次传输编号（1 字节），随后在 FILE 通道发数据包：`传输编号(1) + 偏移(4，小端) + 数据`。
- 发完在 EVT 通道发 `EVT_FILE_DONE`（`op 0x8201`），带传输编号、总字节数、校验值。
- App 发现偏移不连续，可以从断点重新 `FILE_READ`。
- 同一时间只进行一个传输；正在实时收音时设备**可以**回 `BUSY_RETRY` 拒绝读取，由 App 安排在停止收音后读。

### 7.4 确认保存（`FILE_CONFIRM op 0x0203`）

- App 把文件写入手机存储、校验值对上之后，发 `FILE_CONFIRM`（`file_id` + 校验值）。
- 设备核对校验值，一致则把状态改为 `confirmed` 并回成功；不一致回 `CHECKSUM_MISMATCH`。
- **只有 `confirmed` 的录音设备才可以回收**（R1）。回收策略由能力参数声明：`auto`（空间不够时自动删最早的已确认录音）或 `manual`（等 App 发 `FILE_DELETE op 0x0204`）。
- `FILE_DELETE` 对未确认的录音**必须**回 `NOT_CONFIRMED`，不删。

### 7.5 存储满

设备**必须**停止新录音，发 `EVT_STORAGE_FULL`（`op 0x8202`），并在有灯光能力时用灯光提示（具体灯效厂商自定）。不得覆盖未确认录音。

## 8. 标准可选能力

### 8.1 电量（0x0101）

- `BATTERY_GET`（`op 0x0301`）→ 每个电池部件一条：部件编号（1 字节：1 主机 / 2 充电盒 / 3–15 其他）、部件名（可选文本）、电量百分比（0–100，未知 0xFF）、是否在充电（布尔，未知 0xFF）、电压毫伏（可选）。
- `EVT_BATTERY`（`op 0x8301`）：电量变化 ≥5% 或充电状态变化时主动推送。
- App 显示每个部件，并注明最后更新时间。

### 8.2 录音控制（0x0102）

- `RECORD_GET`（`op 0x0311`）、`RECORD_SET`（`op 0x0312`，值：1 录音 / 2 暂停 / 3 停止并保存）。
- 回复**必须**带执行后的实际状态（R3）。
- `EVT_RECORD`（`op 0x8311`）：状态因任何原因变化（按键、存储满、低电）都要推送，带原因码。

### 8.3 灯光（0x0103）

- `LIGHT_GET`（`op 0x0321`）、`LIGHT_SET`（`op 0x0322`，值为模式编号）。
- 标准模式：0 默认、1 关闭（常灭）、2 柔和；0x80–0xFF 厂商预设（名称在能力参数里给出）。
- 回复带实际模式。允许“关闭”；App 在用户第一次选择关闭时提示一次录音告知的法律责任。

### 8.4 存储（0x0104）

- `STORAGE_GET`（`op 0x0331`）→ 总容量、剩余容量、未确认录音占用（字节，未知全 0xFF）。

### 8.5 按键（0x0105）

- `EVT_BUTTON`（`op 0x8351`）：按键编号、动作（1 单击 / 2 双击 / 3 长按）。App 可以把按键映射到功能（如开始专题录音）。
- 设备自己处理的按键（如开始录音）也**应该**照样上报。

### 8.6 对时（0x0106）

- `CLOCK_SET`（`op 0x0361`）：UTC 毫秒 + 时区偏移分钟。App 每次连接后**应该**发一次。
- `CLOCK_GET`（`op 0x0362`）：回设备当前 UTC 毫秒（未对时为未知）和启动编号。
- 设备没有掉电保持时钟的，重启后时间未知，靠 `start_boot` 事后换算。

### 8.7 识别我（0x0107）

- `IDENTIFY`（`op 0x0371`，可带持续秒数，默认 5）：闪灯 / 响声 / 振动。**未认证也允许**，用于在同款多台中找出手里这台。

### 8.8 诊断（0x0108）

- `DIAG_GET`（`op 0x0381`）：设备把诊断信息（文本或二进制，厂商自定）当作一个特殊录音（`file_id = 0`）走 FILE 通道传回。App 只保存、供用户导出给厂商，不解析。

## 9. 错误码

| 码 | 名称 | 含义 |
|---|---|---|
| 0 | `OK` | 成功 |
| 1 | `UNSUPPORTED` | 不认识的操作码或能力 |
| 2 | `BAD_ARGS` | 参数缺失或超范围 |
| 3 | `NOT_BOUND` | 未绑定或凭证不对 |
| 4 | `ALREADY_BOUND` | 已绑定其他手机 |
| 5 | `BIND_TIMEOUT` | 绑定等待确认超时 |
| 6 | `BUSY_RETRY` | 忙，稍后再试 |
| 7 | `NOT_FOUND` | 录音不存在 |
| 8 | `NOT_CONFIRMED` | 录音未确认，不能删除 |
| 9 | `CHECKSUM_MISMATCH` | 校验值不一致 |
| 10 | `STORAGE_FULL` | 存储已满 |
| 11 | `LOW_BATTERY` | 电量过低拒绝执行 |
| 12 | `STATE_CONFLICT` | 当前状态不允许（如正在补传时要求开始实时收音） |
| 0x80–0xFF | 厂商错误码 | App 显示为“设备错误（码 xx）” |

**设备只发错误码，不发文字说明。** 文字由 App 按用户语言翻译，以后做多语言也不用改固件。

## 10. 版本与兼容

- 版本号 = 大版本.小版本。0.x 期间可以不兼容地修改；1.0 起：
  - 小版本只新增（操作码、标签、能力、错误码），不改已有含义（R7）；
  - 大版本至少间隔半年，App 至少继续支持上一个大版本一年。
- 握手时取双方都支持的最高版本。
- 收到不认识的标签：跳过；不认识的操作码：回 `UNSUPPORTED`；不认识的事件：忽略。

---

## 11. 厂商扩展：设置项（能力 0x0201）

- `SETTINGS_SCHEMA`（`op 0x0401`）→ 设置项列表，每项：
  - `key`（文本，厂商内唯一）、`type`（1 开关 / 2 数值 / 3 多选一 / 4 只读状态）、
  - 名称（中文、英文各一份文本标签）、当前值；数值类带最小、最大、步长、单位；多选一带选项列表（编号 + 中英文名）。
- `SETTING_SET`（`op 0x0402`，`key` + 新值）→ 回实际值（R3）。
- App 照描述自动画界面，**不做专用界面**。四种格式表达不了的功能，请放在厂商自己的 App 里。
- 两家以上厂商都在用的同类设置项，会被提升为标准能力。

---

## 12. 安全与隐私

- 通道必须加密，必须绑定（第 5 节）。
- 设备**不得**通过 TaoEcho 联网或把录音发给手机以外的地方；这不限制厂商自己的 App 走厂商自己的通道。
- 设备**不得**提供绕过绑定读取录音的“调试命令”。厂商私有能力同样受绑定约束。

## 13. 和已有设备的对照（检查本草案是否够用）

用三款真实设备检查：如果它们按 TaoEcho 重做固件，现有功能能否全部表达。

| 功能 | 飞书录音豆 D3200（PR #30） | 声云 CB08（PR #14～16） | Omi |
|---|---|---|---|
| 实时声音 | Opus 20ms（现为双声道，**需在设备端改为单声道**） | Opus 系 | Opus 10/20ms |
| 握手/身份 | 私有 ECDH 握手 → HELLO + BIND/AUTH 取代 | 无 → HELLO | 无 → HELLO |
| 离线文件 | 有，现为按包序号补传 → FILE_LIST/READ/CONFIRM | 有，列表 / 偏移下载 / 删除 → 完全对应 | CV1 循环记录 / DevKit SD → 需改为录音文件模型 |
| 安全删除 | 现“保留原文件不删” → 可用 `manual` 策略 | 现可直接删 → 必须改为确认后删 | 现自动推进 → 必须改 |
| 电量 | 录音豆 + 充电盒、充电状态 → 两个部件 | 单电池 + 充电 → 一个部件 | BAS → 一个部件 |
| 录音控制 | 开始 / 暂停，带回读确认 → RECORD | 开始 / 停止 → RECORD | 无（订阅即收音） |
| 灯光 | 常灭 / 暖橙常亮 / 默认 → 0 / 1 / 厂商预设 | 无 | 无 |
| 存储 | 总量 / 剩余 → STORAGE | 有 → STORAGE | 部分 |
| 对时 | 有设备时间 → CLOCK | 年月日 7 字节 → CLOCK_SET | 有 |
| 固件版本 | 主机 / 充电盒两个版本 → `fw` 重复两次（部件 1、2） | 有 | 有 |
| 灯控走经典蓝牙 | **iOS 不支持** → 必须改为 BLE 上的 LIGHT_SET | — | — |

结论：三款设备的现有功能都能用本草案表达；需要厂商改动最大的是“确认后才删”（声云、Omi）和“去掉经典蓝牙”（录音豆）。“双声道”和“主机 / 充电盒两个固件版本”两处已在第 14 节定下处理办法。

## 14. 已定与待定问题

已定（2026-11-11）：
1. 双声道：**只收单声道**，设备端合成后再发。
2. 多部件固件版本：HELLO 的 `fw` 带部件编号，可重复多次。
3. 消息内容格式：**保持 TLV**，不改 CBOR（单片机不用多带库）。
4. 自检工具：做成**涛声 App 里的“开发者模式”**（厂商本来就要用手机测；代码放跨平台共用模块，iOS 版自动就有）。

待定：
5. 文件传输吞吐：是否加可选的 L2CAP 通道（安卓 10+、iOS 11+ 支持）提速？参考固件跑通后实测再定，放 0.2。
6. 操作码、标签的最终编号表在参考固件跑通后冻结。
