# 卡 192：本地转写断点续转（鸿蒙后台被打断）+ 旧 24 小时清理退役

基线：main `c03d8e7`（0.4.0 正式版）。执行：Codex（Astra）。工作目录 `~/Developer/TaoSheng-192`，分支 `codex/192-resume`。目标版本 0.4.1。

**本卡不改数据库**（PR #41 将占用 35～37 版），也不碰外放检测 `capture/PlaybackMonitor.kt`。

## 为什么做

鸿蒙用户反馈（#35 及群反馈）：本地转写时切到后台就被打断，一分钟以上的长录音尤其明显；鸿蒙 7.x 收走了“电池管理”“应用启动管理”，用户没法加白名单。

现状（已读代码确认）：

- 本地转写跑在独立进程 `:local_asr`（`transcribe/local/LocalAsrService.kt`），自身没有前台服务，只被主进程 `BIND_AUTO_CREATE or BIND_IMPORTANT` 绑定。鸿蒙很可能按进程冻结它。
- `LocalAsrService.process()` 的流程：读整段 PCM → **整段**区分说话人（`diarizer.turns`）→ `PauseChunks.split(pcm, turns)` 按停顿切块 → 逐块 `decode` → `TimedSentences` 拼出结果，一次性返回。
- 一段录音最长 5 分钟（`CaptureTuning.MAX_SEGMENT_SAMPLES`）。中途被冻结或进程被杀，客户端 `LocalAsrConnection` 超时或断开，这一段**从头再来**，区分说话人和已识别的块全部白做。短录音在被冻结前就能做完，长录音总也做不完。

## 目标

### 1. 断点续转（核心）

在 `LocalAsrService` 里把中间结果落到临时文件，被打断后接着做：

- **进度文件**：放 `noBackupFilesDir` 或 `cacheDir` 下专用目录（例如 `asr-progress/`），一段录音一个文件，原子写入（`AtomicFile` 或写临时文件再改名）。
- **进度键**必须同时包含：段 id（或请求里能唯一对应这段录音的标识）、音频内容指纹（PCM 长度 + 抽样哈希或全量哈希，自定）、后端/模型键（`recognizerKey`）、语言、是否区分说话人、`speakerCount`、热词版本（如有）。任何一项变化都视为不同进度，旧文件丢弃。
- **存什么**：
  1. 区分说话人做完后，存 `turns`（说话人分段）和 `speakerDecision`；续转时直接读，不再重做；
  2. 每识别完一块，追加这一块的结果（足以让 `TimedSentences` 重建的数据：文本、时间、说话人标签、检测到的语言等）和块序号；
  3. 续转时先重建已完成的块，再从下一块开始。`PauseChunks.split` 对同一输入必须是确定的（请确认；不确定就把切块边界也存进进度文件）。
- **结果必须与不中断时一致**：同一段录音，“一次做完”与“任意块之后被打断再续”得到的句子、时间、说话人标签完全相同。加测试证明。
- **清理**：成功返回结果后删进度文件；段被删除、隐私删除、改为云端转写、模型更换时，对应进度文件也要能被清掉（至少：启动或每轮转写开始时清理超过 3 天、或对应段已不存在/已完成的进度文件）。进度文件不进任何备份（在 `PreferenceBackupPolicy` 之外，按卡 190 的规矩确认它不会被备份包带走）。
- **只对本地转写生效**，云端转写（豆包、OpenAI 兼容等）不变。

### 2. 反复被打断就换个时机

- 记录“同一段录音本地转写被打断”的次数（超时 `local-inference-timeout`、进程断开 `local-unbound`、进程死亡等）。这个计数是运行状态，可以放进度文件或现有运行状态里，**不进备份、不改数据库**。
- 同一段**连续被打断 2 次**：后续只在**亮屏或充电**时再转它（有进度就续），其余时候先转别的段。转成功后计数清零。
- 不能让这段永远卡住：被推迟的段在亮屏/充电时必须能被调度到（复用卡 188/189 的亮屏、接电触发 `PipelineScheduler.offer`）。
- 现有失败重试规则（`TranscribePolicy.retryAt`、5 次上限、`Failed`/`Quiet` 状态）的语义不变；被打断且有进度的情况不应消耗“转写失败”的重试次数，若做不到请在交付说明里写清楚现状和影响。

### 3. 诊断

问题记录（现有“自动转写/整理记录”或 `FailureNotes`，按卡 190 规矩）里能看到：哪一段、共几块、续转时从第几块开始、被打断的原因（超时 / 进程断开 / 其他）、是否因连续打断而推迟到亮屏或充电。不记录任何转写文字内容。

### 4. 附带：旧 24 小时清理退役（行为不变）

- `TranscribeRunner.cleanup()` 里“完成 24 小时后删录音”的旧逻辑（`TranscribePolicy.RETENTION_MILLIS`、`canDelete`、`dao.expired`），在 App 中因 `deferAudioCleanup = true` 早已不执行，真正按用户“原声保留天数”删除的是 `LocalOriginalAudio`。确认没有其他生产调用后删除这段旧逻辑和只为它服务的代码；测试里依赖它的改为测 `LocalOriginalAudio` 的实际规则，或一并删除并在交付说明里说明。
- 改正 `TranscribeContract.kt` 里 `SkippedPlayback` 注释“录音 1 天后删除”→ 按用户设置的原声保留天数删除。
- 不改 `originalRetentionDays` 默认值（仍为 3 天）。

### 5. 给界面准备的数据（界面由 Claude 做）
