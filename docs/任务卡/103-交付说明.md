## DigestRunner 缓存与 inflight 核查

现状：`identity(lines, preset)` 将 preset 与整批原话序列化后散列；启动时只接受与当前 preset 匹配的 pending。收到响应后先 `rememberDigest()` 缓存并计用量，再解析、提交事件，最后移除 pending。数据库保存失败时保留进程内 `unsavedReply`；没有缓存但有 inflight 的自动运行会暂停，需手动重试。`thingRevision` 随缓存保存，恢复时回填到提取批次，防止寻物开关重启后提交旧响应。

建议实现方式（尚未修改）：

1. 新缓存键使用带版本前缀的原话批次散列，与尝试过或最终成功的模型无关。一次切换流程共用一个 batch ID 和 inflight 标记。
2. 缓存保存实际模型快照，恢复事件使用缓存模型，不能使用当时设置里的主模型；thingRevision 保持和该响应一起保存、一起恢复。
3. 兼容旧缓存时仍校验来源内容与旧散列，不只比较 ID；候选旧 preset 从已保存配置获取。若旧模型配置已消失，无法验证时应保留并暂停，而不是删掉缓存后自动重新付费请求。
4. 成功响应和对应实际模型用量在同一数据库事务保存，重复恢复只重放本地提交。失败请求若返回用量，也需按独立尝试 ID 去重记账，不能在最终成功时再次累计。
5. 保留现有 inflight 的保守恢复策略：没有已保存响应时，自动任务不擅自重发；用户手动重试才清理该状态。

## 错误分类方案（尚未实现）

| 错误 | 切换与冷却 |
| --- | --- |
| 网络、超时、5xx、408、429、其他 4xx | 切换，冷却 5 分钟；429 文案“请求太频繁” |
| 401 / 403 | 切换，冷却 30 分钟 |
| 402 / 明确额度耗尽 | 新增额度错误类别，切换，冷却 30 分钟 |
| 输入容量超限 | 只试容量更大的备用，不当作服务宕机 |
| Format | 不切换，保留调用方原重试逻辑 |
| CancellationException | 原样抛出，不切换 |

每次最多尝试三个模型，冷却候选后置。全部失败时保留主模型错误并附“备用模型也没成功”；需特别覆盖冷却后主模型不再首先尝试的情况。服务端返回失败用量时也需解析并归属实际模型，不能只处理成功响应。
