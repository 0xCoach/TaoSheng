# 卡 215：邮件推送常报鉴权失败、红米首次加日历失败（Claude 直接做）

## 邮件推送
原因（代码层面）：
1. 每封邮件单独连一次、登录一次，几类推送各自发、有时并发；QQ/163 短时间登录多了以 535 拒绝。
2. 限流和密码错同为 535，原来只看数字，一律说“认证失败：检查账号、授权码”，丢掉服务器原话。
3. 整封邮件总时限 10 秒，带附件/网络慢易超时。
4. Outlook 个人邮箱已不支持账号密码登录、Gmail 需应用专用密码、QQ/163 需授权码，设置页没写。

改法：
- 同一邮箱（服务器+端口+账号+密码）发信加锁排队；发完连接留 20 秒，期间下一封 RSET 后复用，不再登录。复用连接在 DATA 之前失败则丢掉、换新连接重发一次；DATA 之后失败不重发（避免重复投递）。空闲到期发 QUIT 断开。
- 拒绝提示带服务器原话（去掉账号密码，最长 80 字）；原话里有“频繁/limit/too many”等 → “邮箱服务器限制登录频率，稍后自动重试，不用改设置”；其他 535 提示授权码/应用专用密码，并说明偶发多半是登录太频繁。
- 时限：单次读写 15 秒，连接登录合计 60 秒，每封投递 60 秒。
- 设置页“授权码”提示写明 QQ/163/Gmail/Outlook 的要求。

验证：`PushMoreTest.smtpReusesLoginAndExplainsRateLimit`（连发两封只 AUTH 一次、有 RSET；限流文案且不含密码）；原 `smtpLocalAuthDataTlsModesAndMimeAttachment` 以 idleMillis=0 保持原行为通过；push 两个测试类 20 个通过。
真机：配 QQ 邮箱通道，连续触发几条推送（如手动推送回顾+待办提醒），看推送记录是否都成功、无 535。

## 红米首次加日历
代码本身无误（ACTION_INSERT 打开系统日历新建页）。可能原因：小米日历冷启动/首次协议吞掉新建页，或系统“关联启动”首次拦截；未能确证。
顺手改进：弹出面板里的 Context 不是页面本身，原来会加 FLAG_ACTIVITY_NEW_TASK 另开任务；现找回所在页面直接打开，不另开任务。再有反馈时问清首次点时具体看到什么。
