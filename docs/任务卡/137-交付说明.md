**结论：推荐 KMP 共用业务与协议，Android 保留 Compose，iOS 使用 SwiftUI；先把 TaoEcho 的边界做好，再逐步迁移存量逻辑。** iOS 可以实现涛声的主要记忆功能，但不能承诺 Android 的全天保活、跨应用采集和蓝牙行为原样成立。

## 二、路线选择：KMP 共用逻辑，iOS 原生接系统

**结论：选 A，分阶段抽取；B 只适合明确接受两套业务长期各自维护的情形。** 这是根据本仓库耦合情况作出的工程判断，不是官方工期数据。

| 比较项 | A：KMP 逻辑 + Compose / SwiftUI | B：Swift 完全重写 |
|---|---|---|
| 初期工作量 | **中到大**：先清理 JVM/Android 边界，再接 SwiftUI 和原生系统能力；不是拷贝文件即可 | **大**：系统和界面同样要做，还要重写问答、整理、备份、同步、插件协议等规则 |
| 长期维护 | 规则、协议、格式和错误修复只维护一份；仍维护两套 UI/系统适配 | Android/iOS 每次业务变更都需同步实现与核对，容易行为分叉 |
| 对现有 Android 改动 | **中**：新增共用模块、移动逻辑、接口注入；数据层迁移应独立进行，避免同时改整库和录音 | **小**：可以不动 Android，但同一缺陷通常要在 Swift 再修一次 |
| 主要风险 | Kotlin/Swift 的类型、错误、取消和 Flow 桥接；KMP 工具链和原生库打包；抽取时 Android 回归 | 协议、去重、时间、备份和模型预处理重写出差异；两套规则持续漂移 |
| 构建要求 | iOS 编译、链接、模拟器、签名需要 **Mac + Xcode**；可以使用 Mac CI，写通用 Kotlin 不必人人用 Mac | 同样需要 **Mac + Xcode** 构建常规 SwiftUI iOS 应用 |
| 更适合涛声的原因 | 已有大量需要长期一致的规则，TaoEcho 又明确要求协议/插件平台无关 | 若确定 iOS 产品另起路线、功能长期明显不同，才抵消重写与双维护成本 |

KMP 的 iOS 支持、Compose Multiplatform 的 iOS UI 都已被 JetBrains 标为 **Stable**，不应再说 iOS Compose 只是试验品。它可以嵌入 SwiftUI，但不能把当前 2.1 万行 UI 原样视为共用代码。涛声大量页面连接权限、音频、文件分享、系统提醒；本次推荐 SwiftUI 是为了让这些入口贴合 iOS，非因 Compose 不成熟。[官方稳定性](https://kotlinlang.org/docs/multiplatform/supported-platforms.html)、[SwiftUI 集成](https://kotlinlang.org/docs/multiplatform/compose-swiftui-integration.html)。

iOS 构建必须有安装 Xcode 的 macOS 环境；KMP 不会消除这一要求。[KMP 构建要求](https://kotlinlang.org/docs/multiplatform/quickstart.html)。Kotlin 可编译成供 Swift 使用的 framework，现有互操作对 `suspend`、异常和纯 Swift 库有边界；建议暴露少量业务门面，把 Flow 转成 iOS 可取消的观察接口，CryptoKit 通过 Swift/Objective-C 可见包装或平台实现接入。[互操作说明](https://kotlinlang.org/docs/native-objc-interop.html)。

后续实施顺序建议（本卡不执行）：先确认 iOS 录音/蓝牙边界 → 抽 TaoEcho 模型与协议 → 接 Android 适配保持原行为 → 用 iOS 小样验证外设收音/补传 → 再抽 JSON、网络与业务 → 最后独立迁移数据库、备份与完整界面。继续使用 AppGraph 式手工装配，无需为 KMP 引入 Hilt。

## 三、关键依赖：多数有成熟替代，现有 Android 包装不能直接复用

**结论：主要风险在接线、数据兼容与性能验收，不在“iOS 有没有这个库”。** 表中的成熟度指方案本身；没有做过涛声 iPhone 实测的项目均不能视为已验证。

| ECDH、HKDF、ECDSA、AES | **平台 CryptoPort；系统密码库成熟** | Android JCA；iOS CryptoKit P-256 密钥协商/签名、HKDF、AES-GCM，AES-CTR 用 CommonCrypto。不是把 javax.crypto 放 commonMain；Swift CryptoKit 也不是可直接 import 的 KMP 共用库。[ECDH](https://developer.apple.com/documentation/cryptokit/p256/keyagreement/privatekey)、[HKDF](https://developer.apple.com/documentation/cryptokit/hkdf)、[ECDSA](https://developer.apple.com/documentation/cryptokit/p256/signing/publickey)、[CommonCrypto CTR](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/CommonCryptor.h) |
| 备份加密、密钥保存 | **AES-GCM / PBKDF2 + Keychain；成熟** | 现备份用 PBKDF2WithHmacSHA256 + GCM，iOS 可用 CommonCrypto PBKDF2 + CryptoKit GCM，必须保持盐、轮数、头部认证和标签布局；Keystore 密文不能直接搬到 Keychain，迁移走备份口令或重新配置密钥。[当前格式](../../app/src/main/java/app/resound/backup/BackupEncryption.kt)、[GCM](https://developer.apple.com/documentation/cryptokit/aes/gcm)、[CommonCrypto PBKDF2](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/CommonKeyDerivation.h)、[Keychain](https://developer.apple.com/documentation/security/keychain-services) |
| WorkManager / AlarmManager | **BGTaskScheduler、后台 URLSession、本地通知；成熟但不是等价替代** | 任务队列、去重、重试规则放共用；什么时候执行由 iOS 决定。iOS 26 的 BGContinuedProcessingTask 支持前台开始的长任务继续执行，但可取消、可被终止，不是定时常驻服务。[后台策略](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)、[长任务](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask) |
| File、SAF、MediaStore、assets | **Foundation/FileManager + 平台文件插口；成熟** | common 只传文件 ID、字节流、偏移和元数据；iOS 操作沙盒路径或用户授权 URL。配置可用平台键值库，密钥用 Keychain。锁屏时文件保护等级影响录音写入及后续打开，应专门设计。[授权目录](https://developer.apple.com/documentation/uikit/providing-access-to-directories)、[文件保护](https://developer.apple.com/documentation/foundation/fileprotectiontype/completeunlessopen) |
| Java 时间、ByteBuffer、格式化 | **kotlinx-datetime、Kotlin 时间接口、字节工具；成熟** | Epoch 毫秒、时区、日历时间与单调计时分开；字节序显式表达，文本格式由统一函数处理，去掉隐式 JVM API。[日期时间库](https://kotlinlang.org/api/kotlinx-datetime/)、[单调时间](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.time/-time-source/-monotonic/) |

数据库建议保留当前 2.x 稳定路线做单独验证；本次看到的在线 KMP 指南示例已采用 Room3 alpha，不能因此顺手把涛声升级到 alpha。当前 FTS4、动态查询、32 段迁移、事务与旧备份还原的跨端等价性**未验证**；这些应成为迁移卡的验收点，而不是本卡推定已支持。

密码兼容尤其要写清字节约定：PR #30 是 P-256 ECDH、HKDF-SHA256（salt/info 为 `01 02 03`）、AES-CTR；设备卡验签是 P-256/SHA256、SPKI DER 公钥与 DER 签名，并验证原始 JSON 字节。保留原始公钥编码、nonce/计数器端序、tag/AAD 和签名输入；换系统库不能顺手改线协议或先重新序列化再验签。[PR #30 源码](https://github.com/0xCoach/TaoSheng/blob/1a0d2b839b00b420cea26cc3ca0a19a682ff92de/app/src/main/java/app/resound/devices/plugins/d3200/D3200Protocol.kt)、[当前验签](../../app/src/main/java/app/resound/devices/RemoteDeviceCards.kt)。

## 四、iOS 硬限制：可以长录，不能承诺永不停；部分旧结论要加版本条件

**结论：产品应把“正在工作、暂时中断、稍后补传”说清楚，不能把后台权限理解成全天进程保证。** 以下采用 Apple 官方资料；推论单独标明。

### 1. 后台长时间录音

**结论：用户授权后，真实录音可在锁屏/后台继续，但没有官方 24 小时不中断保证。** 使用 AVAudioSession 的录音类别并声明 `UIBackgroundModes=audio`。来电、闹钟、其他不混音会话可中断；中断后可能被挂起，且不保证一定收到“中断结束”。媒体服务重置要重新建音频对象。[record 类别](https://developer.apple.com/documentation/avfaudio/avaudiosession/category-swift.struct/record)、[中断与媒体服务恢复](https://developer.apple.com/library/archive/documentation/Audio/Conceptual/AudioSessionProgrammingGuide/HandlingAudioInterruptions/HandlingAudioInterruptions.html)。

进程终止、用户强退、重启会让本进程的录音代码停止；普通音频后台模式不构成自动拉起麦克风录音的承诺。没有找到 Apple 对涛声这种“全天录音 + VAD + 本地转写”组合的持续时长/恢复时限保证。工程建议：分段及时落盘、记录缺口、恢复时明确状态；不能用静音播放假装录音来维持其他计算。仅收 BLE 数据时，应按蓝牙后台规则设计，不能假定声明 audio 就拥有常驻资格。[后台模式](https://developer.apple.com/documentation/xcode/configuring-background-execution-modes)、[审核 2.5.4](https://developer.apple.com/app-store/review/guidelines/#software-requirements)。

### 2. BLE 后台扫描与状态恢复

**结论：普通后台模式依赖服务 UUID；iOS 26 新增了带条件的例外。**

- 声明 `bluetooth-central` 可在后台处理相应 BLE 事件。普通后台扫描须显式给服务 UUID，重复发现会合并，扫描可能变慢；名称前缀/厂商号只能在收到广播后匹配，不能代替后台服务过滤。[扫描 API](https://developer.apple.com/documentation/corebluetooth/cbcentralmanager/scanforperipherals(withservices:options:))、[后台指南](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html)。
- **iOS 26+ 例外**：已创建 CBManager，且进入后台前启动 Live Activity，可获得文档所述的前台级扫描权限，包括不带服务 UUID 和重复扫描。不能把任务卡里的“后台只能按 UUID”写成无条件硬限制；也不能据此承诺永久常驻。[Core Bluetooth 当前说明](https://developer.apple.com/documentation/corebluetooth)。
- 状态保存/恢复需要稳定的恢复标识和 `willRestoreState` 等接入；系统仅在有待处理的扫描、连接、订阅事件时恢复。TN3115 列明：内存移除/崩溃可以恢复；设置中关闭蓝牙有阻断；重启后有首次解锁条件。其“用户强退、控制中心切换、部分飞行模式”条目带注 5：**iOS 26+ 只有经 AccessorySetupKit 设置配件的 App 才有相应重启例外**。这不是普通录音服务被强退后的恢复通道。[TN3115，含版本脚注](https://developer.apple.com/documentation/technotes/tn3115-bluetooth-state-restoration-app-relaunch-rules)。

对 TaoEcho 的建议：默认要求设备广播稳定的服务 UUID；Live Activity/AccessorySetupKit 是 iOS 能力选项，不能成为所有设备都可用的前提。设备有离线存储时优先靠补传弥补手机离线，恢复租约、下载游标与已导入区间，不能只恢复“已连接”文字。

### 3. 蓝牙地址、MTU、经典 SPP

**结论：设备身份和包大小必须抽象，不能把 Android 的 MAC 与 517 MTU 当作协议事实。**

| 限制 | 官方依据与对涛声的影响 |
|---|---|
| Core Bluetooth 不提供外设 MAC 地址作为连接标识 | 公开身份是系统分配的 `CBPeer.identifier` UUID。共用模型应使用不透明 `DeviceId`，平台保存其检索标识；不能做 MAC 格式校验，也不能假定 Android 和 iPhone 的平台标识相同。跨手机认同一物理设备需协议自报身份或用户重新配对；UUID 永久稳定性不作保证。[identifier](https://developer.apple.com/documentation/corebluetooth/cbpeer/identifier) |
| App 不能像 Android requestMtu 那样指定 ATT MTU | Apple 配件指南 §57.11（2026-10-30 版，页 347）说明由系统按链路/拓扑等请求最佳 MTU；公开接口提供按写入类型查询最大负载 `maximumWriteValueLength`。因此把卡片 `mtu` 解释为 Android 请求偏好，iOS 根据实际写入上限工作；这是结合官方 API 的工程结论，不设固定 185/517。[配件指南](https://developer.apple.com/accessories/Accessory-Design-Guidelines.pdf#page=347)、[最大写入长度](https://developer.apple.com/documentation/corebluetooth/cbperipheral/maximumwritevaluelength(for:)) |
| 非 MFi 的通用经典蓝牙 SPP 串口不可作为 iOS 接入路线 | 公开资料未找到普通 App 直连非 MFi SPP/RFCOMM 的方案，按不支持规划；External Accessory 面向 MFi 配件且须厂商允许本 App 使用其协议。不能扩大成“iOS 完全不支持经典蓝牙”：Core Bluetooth 从 iOS 13 已支持 **GATT over BR/EDR**，它与 SPP 不同。TaoEcho 优先 BLE GATT；纯 BLE/Core Bluetooth 配件通常无需 MFi。[External Accessory](https://developer.apple.com/documentation/externalaccessory)、[Apple 蓝牙入口](https://developer.apple.com/bluetooth/)、[WWDC19 GATT/BR-EDR](https://developer.apple.com/videos/play/wwdc2019/901/)、[MFi FAQ](https://mfi.apple.com/en/faqs) |

包大小适配还不能随意拆命令：现 `DeviceLink.write` 明确要求整命令一次写入。新接口要报告可写长度及写入背压；超限只能采用该设备协议支持的分片或明确报不支持，不能在平台层无声切包。PR #30 的 `mtu=517` 和固定 166 字节音频单位必须分开看：前者是链路偏好，后者是品牌协议单位。

### 4. 文件夹监听与无障碍采集

**结论：不能常驻监视其他 App 私有目录，也不能像 Android 无障碍服务那样自动读微信；但“iOS 完全不能监听文件夹”过于绝对。**

iOS 沙盒隔离第三方 App，只允许通过系统明确提供的服务访问他方数据。用户可通过目录选择器授予目录访问，拿到 security-scoped URL/bookmark；自身或获授权目录在可运行期间可做协调访问。NSFilePresenter 可接收协调写入的变更，但不是所有低级文件写入都会通知，且官方要求后台移除、回前台再加入，不能用它承诺全天自动入库。[沙盒](https://support.apple.com/guide/security/security-of-runtime-process-sec15bfe098e/web)、[授权目录](https://developer.apple.com/documentation/uikit/providing-access-to-directories)、[NSFilePresenter](https://developer.apple.com/documentation/foundation/nsfilepresenter)。

未找到普通 App 可持续读取微信其他应用界面树、输入框和聊天内容的公开 iOS API。工程结论：现 `VoiceInputService` / 自动截图识字跨 App 路径无法原样迁移，改为用户主动分享文字、音频、截图或在涛声内导入；“识别一张已授权截图”本身仍可实现。

### 5. 全天录音、提示灯常灭与 App Store

**结论：全天录音没有查到“一律禁止”的专门条款；隐藏录音提示不能当作可承诺的卖点。**

| 条款 / 事实 | 对涛声的产品含义 |
|---|---|
| 审核 2.5.4 | 后台模式必须用于对应目的；真实录音与 BLE 处理分别说明用途，不能拿音频模式维持无关后台工作 |
| 审核 2.5.14 | 记录用户活动须明确同意，并有清晰的视觉或听觉提示；仅申请麦克风权限不能替代所有录音告知 |
| 审核 2.5.1、2.5.9 | 使用公开 API、尊重系统行为；iPhone 使用麦克风时由系统显示橙色指示。未找到供普通 App 关闭该指示的公开 API，不提供“关闭系统录音指示”功能 |
| 审核 5.1.1、5.1.2 | 说明采集、保留、删除及分享用途；云端转写/大模型涉及个人数据传给第三方，要清楚披露并取得所需明确许可 |
| 外设 LED 的“常灭” | 它与 iPhone 麦克风橙点不是同一件事。BLE 接收录音不等于使用 iPhone 麦克风，不能把没有系统橙点当作录音告知。未找到 Apple 专门针对 D3200 关灯命令的批准/禁止条文；从 2.5.14 推论，若熄灯导致录音不可察觉，存在审核风险，建议首版不提供隐藏录音的常灭模式，保留清晰提示，最终由具体审核决定 |

出处：[App Review Guidelines 2.5 与 5.1](https://developer.apple.com/app-store/review/guidelines/)、[Apple 对麦克风指示的说明](https://support.apple.com/en-gb/108331)。本节是针对发布要求的产品/工程判断，不是已获得 App Store 审核通过的结论。

## 五、外设模块：共用 TaoEcho 语言，插件翻译，系统只运字节

**结论：现有 DeviceLink / FileSourcePlugin 的方向可保留，但“换 iOS 只写 DeviceLink”还不够。** 当前 core 仍有 JVM 依赖，外围还直接持有 MAC、Room、File、时钟和 Android 解码器；PR #30 更把品牌连接、协议会话和平台生命周期放在一起，需要再分层。

### 建议的共用模块划分

| 逻辑模块（名称为建议，未创建） | 共用内容 | 留在平台层的内容 |
|---|---|---|
| `taoecho-model` | TaoEcho 设备描述、Tier、Capabilities、状态/命令/事件、音频块、录音元数据、错误、下载游标 | MAC、CBPeripheral、BluetoothGatt、Uri/File、权限与界面类型均不进入 |
| `taoecho-core` | 设备选择与会话租约、命令/音频/状态分流、重连状态机、序号/CRC、去重、覆盖区间、补传队列、完成后才允许删除的策略 | 系统唤醒、BLE 恢复回调、实际落盘、数据库打开、通知 |
| `taoecho-card` | 卡片字段校验、版本/能力约束、通用分帧、PCM/μ-law 转换、签名表防回退规则 | 资源读取、签名算法实现、远程获取与安全缓存接到平台插口；签名表仍是数据 |
| `taoecho-plugin-*` | 各品牌命令、分帧、握手编排、状态/文件协议，翻译为 TaoEcho 模型 | 不持有 Android/iOS 蓝牙对象，不直接联网、不写手机路径、不拉起界面 |
| Android / iOS adapters | 各平台实现统一插口 | Android GATT / MediaCodec / Room / WorkManager；iOS Core Bluetooth / libopus / Keychain / BGTask / Foundation；UI 分别实现 |

依赖方向：**核心只依赖 TaoEcho 模型和平台无关插口；品牌插件实现翻译，装配层注册插件。** 型号、固件特例只留插件/描述数据；核心不增加 `if (d3200)`。共用逻辑使用普通接口注入，只有平台实现/工厂需要相应源集；这是 KMP 官方支持的方式。[平台边界机制](https://kotlinlang.org/docs/multiplatform/multiplatform-expect-actual.html)。

任务卡提到 1～4 级，但本基线未找到各级最终规范。**不自行定义“第几级等于什么能力”**：先保留 Tier 数据，业务按明确能力（实时、离线文件、断点、删除、校验、控制等）判断；各级定义由负责人定稿。TaoEcho 统一模型也不意味着强制已有品牌固件改讲 TaoEcho 线协议，由插件翻译即可。

### 基于现状的搬迁建议

- [DeviceContract](../../app/src/main/java/app/resound/devices/DeviceContract.kt) 中的模型与 Flow 插口是起点；`FoundDevice.address` 等改成不透明设备标识、`DeviceLink.mtu` 改成实际写入能力属于**后续约定变更建议**，本卡不改签名。
- [FrameCodec](../../app/src/main/java/app/resound/devices/core/FrameCodec.kt)、[CardParser](../../app/src/main/java/app/resound/devices/core/CardParser.kt) 换掉 Java 缓冲和 org.json；`Crc`、`FrameValidation`、`AudioDecoder` 与 `PcmInputConverter` 优先共用。Opus 只通过解码插口。
- [ManagedDevices](../../app/src/main/java/app/resound/devices/ManagedDevices.kt) 保留选择/连接状态机，改协程串行化；扫描参数传服务 UUID，配对表达为“请求系统授权/安全连接”，不要求 iOS 执行 Android createBond。
- [DeviceSync](../../app/src/main/java/app/resound/devices/DeviceSync.kt) 把时间缺口、区间去重、重试与提交顺序留下；Room、RandomAccessFile、fd.sync、SHA、事件日志通过仓储/文件/密码/时钟插口完成。[DeviceSyncStore](../../app/src/main/java/app/resound/devices/DeviceSyncStore.kt) 当前也有 Room 注解和 File 参数，不能直接称为共用存储插口。
- [声云插件](../../app/src/main/java/app/resound/devices/plugins/sonicloud/SonicloudFiles.kt) 的命令和数据解释共用；Java 时间、ByteBuffer、IOException 适配；插件向核心交数据，不自己决定通知、保活或用户文件路径。

| `D3200Protocol` / `D3200Crypto` | 保留命令白名单、校验、序号、166 字节单位、握手和解密编排；ByteBuffer/BigInteger 换字节工具，JCA 密码调用交 CryptoPort，保持原字节向量 |
| `D3200AudioSource`、`D3200Files`、`AudioTimeline` | 保留实时/历史区分、采样时间与缺口、文件下载策略；SystemClock/System、Java 时间和缓冲、异常类型、解码绑定注入；把设备时间与接收时间分别保留 |
| `D3200Connection`、`D3200Coordinator`、`D3200Transport` | 拆为共用会话/租约/消息路由和平台 BLE；当前含 Context、BluetoothDevice/Gatt、CountDownLatch、JVM 队列、SharedPreferences、ResoundApp。iOS 以 Core Bluetooth 回调驱动，不能把阻塞式 Android 传输器直接移植 |
| `D3200Journal`、`D3200Ogg` | 覆盖与入库确认规则、Ogg 页/CRC 规则共用；AtomicFile、RandomAccessFile、目录扫描与哈希交平台文件/存储插口，持久游标和数据提交顺序必须一致 |
| `D3200Opus`、`D3200SettingsActivity`、Manifest / CaptureService / UI 改动 | MediaCodec、Activity、前台服务权限/类型留 Android；iOS 另接 libopus、SwiftUI 和后台模式。新增的逐帧时间、串行补传标志、新文件优先顺序可转成共用模型/能力 |

需保留的行为：刷新回执不能抢走音频；每设备共用会话租约；补传与交互控制互斥；手动暂停不被自动开始覆盖；仅在手机确认持久化/导入后推进完成状态。设备“正在录音”与手机“正在收到声音”分别表达，盒子读数保留时间和新鲜度。PR 说明中的 Android 实测仅作为作者已有证据引用，本卡未复测；其他固件、iOS 长连、盒子实时状态和长历史补传仍未验收。

### 平台插口清单（仅概念职责，无实现）

**结论：让平台提供能力和事实，核心决定规则；接口不泄露 Android 或 Swift 类型。** 下列是未来设计清单，不替换当前 Contract。

| 插口 / 概念操作 | 职责与返回信息 |
|---|---|
| `BleCentralPort.scan(filters)`、`connect(DeviceId)`、`restore()` | 服务 UUID 过滤、权限/蓝牙状态、发现与连接事件；暴露可恢复标识和平台能力，恢复后重接共用状态机 |
| `GattLinkPort.read/write/notifications/close` | UUID 字符串和 ByteArray 收发；区分 write with/without response，提供实际最大写入负载、可写背压、断开原因；平台保持 GATT 操作顺序，协议层决定是否分片 |
| `CryptoPort` | P-256 临时密钥、ECDH、HKDF/HMAC、AES-CTR/GCM、SHA-256、ECDSA 验签、安全随机数；密钥用受控句柄和明确编码，密码实现不散落插件 |
| `OpusDecoderFactory` / `ModelInferencePort` | 每会话创建/释放解码或模型实例；返回 PCM 实际采样率/声道，推理输入输出明确形状，暴露错误和取消 |
| `FileStorePort` | 以不透明文件 ID 进行分块读写、seek、持久化、原子替换、大小与删除；平台处理沙盒、锁屏文件保护、授权 URL，业务不拿 File/Uri |
| `TransferRepository`、`PairingRepository`、`CardStore` | 设备与插件配置、游标、覆盖区间、导入完成凭据、已验签原表及版本持久化；定义原子提交，不将下载完成误当导入完成 |
| `ClockPort`、`DiagnosticPort` | 分别提供墙上时间、单调耗时、时区；记录脱敏事件/错误。协议时间不能临时读系统默认时区后猜测 |
| `BackgroundPort`、`NotificationPort` | 申请/撤销执行机会、报告到期与取消、提醒用户。返回是否支持及当前许可，不承诺到点执行或永久常驻 |
| `MicrophonePort`（或平台 AudioSource） | 权限、开始/停止、实际格式、占用/中断/恢复事件；输出统一 PCM，不能把后台挂起解释为一段静音 |

`DeviceProtocolPlugin` 本身是共用接口：声明匹配条件和能力，通过上述字节/密码/时钟插口执行会话，向核心发 TaoEcho 状态、音频和文件事件；离线下载提供字节流与游标，不持有手机文件系统。插件打包进应用；签名远程卡片只下发受约束数据，不下载 Kotlin/Swift 可执行插件改变功能。[审核 2.5.2](https://developer.apple.com/app-store/review/guidelines/#software-requirements)。

## 六、从现在开始可写入 AGENTS.md 的 10 条建议

**结论：先约束新增代码的依赖方向，不为“未来复用”立即重构整个 Android 项目。** 以下可在负责人认可后写入 AGENTS.md，本卡不修改该文件。

1. 新业务规则、TaoEcho 模型和协议插件使用平台无关 Kotlin；不引用 `android.*`、Android 专属 AndroidX、`java.*`、`javax.*` 或平台推理/蓝牙类型，正文中的全限定名也算依赖。采用 AndroidX/KMP 库前确认其 common/iOS API，而不是一律禁止 AndroidX。
2. 时间、时区、随机数、文件、日志、网络、数据库、密码和模型推理由接口或函数参数注入；构造函数默认值也不能偷偷创建 Android 实现。由 AppGraph/平台装配层提供实例，不引入 Hilt。
3. 跨层模型使用基本值、ByteArray、明确的 ID 和共用数据类；不暴露 Context、Uri、File、BluetoothDevice、CBPeripheral。设备 ID 不假定为 MAC，不假定跨手机一致。
4. TaoEcho 核心只认统一模型和显式能力；品牌、固件特例只放卡片或对应插件。1～4 级依负责人定稿，不用等级代替能力检查；插件不直接操作系统、手机路径、网络或界面。
5. 网络与 JSON 优先使用可用于 common/iOS 的接口或库；现有 OkHttp/org.json 留适配边界。设备卡未知字段、重复字段、签名原字节与协议错误处理规则不得因换库变宽松。
6. 共用并发使用结构化协程、Mutex/串行事件处理与可取消任务；避免 JVM synchronized、线程、阻塞锁和 java.util.concurrent。取消必须释放连接、解码器和文件，并保留可恢复进度。
7. 协议明确单位、字节序、包长度、序号、真实采样率/声道和时间来源；不写死手机 MTU，不按接收回调次数猜音频时长；不支持的分片或后台能力明确报出。
8. 持久队列、重试、去重、覆盖区间与完成凭据放业务层；系统调度器只负责给执行机会。按“可中断、可重复、可续做”设计，不把 WorkManager/前台服务语义当跨平台保证。
9. 新核心功能只保留少量关键正常/故障用例；协议优先用脱敏字节向量核对两端一致。实际引入 KMP 的任务再增加 iOS 编译检查与真机验收，不以 JVM 单测通过宣称 iOS 可用。
10. 既有 `*Contract.kt`、`AudioSource.kt` 签名仍由负责人确认；需要平台无关的新约定时先提出清单与兼容方案，逐步迁移，不夹带改 UI/MainActivity、数据破坏性重建或无关依赖升级。
