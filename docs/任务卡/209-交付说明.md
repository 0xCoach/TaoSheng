# 卡 209 交付说明

本机一天负载中，卡 199 的导入主查询和录音段关联查询占所测重复查询耗时的约 95%。改动后，300 次普通录音写入引起的这两项查询都降到 0 次。普通写入在改动前后都没有引起文件夹扫描。手机后台数据库 CPU 的实际占比和省电幅度仍待实测。

## A · 问题记录

本地提交 `86f01582`。原问题记录导出入口新增“数据库查询来源（最近 6 个 10 分钟）”。每窗按累计耗时列前 10 项，显示 DAO 方法、次数、累计毫秒、遍历行数，随后列出各表收到的失效通知次数。没有样本的时间窗显示“暂无记录”。

- 安卓主库驱动在实际准备和关闭 Room 的读语句时统计，覆盖 Flow 首查、失效重查和显式 suspend 读取。同一 SQL 的不同 DAO 方法可由生成代码的调用帧区分。关联查询另列；相同 DAO 方法的不同调用方合并。
- 耗时取单调时钟，包括结果遍历和映射。Room 的关联读取会重置父游标，子查询时间另计。行数是游标实际遍历次数，同一父行遍历两遍计两行。次数按语句计，导出的耗时是经过时间。
- 表名来自当前 Room schema。失效按 Room 实际送达的通知计数，同事务或合并送达的多次写入可以只记一次。统计存于主库所在进程的内存，重启后重新积累。仅保存方法名、表名和数字；备份临时库不纳入。
- CPU 微测使用本机 JVM、Robolectric 原生 SQLite 和调用线程 CPU 时钟。预热后交错各执行 20,000 次单行查询，原驱动 120.796 毫秒，开统计 187.863 毫秒，差值 **67.067 毫秒，约 3.35 微秒/查询**。这组短查询走通用栈帧归因路径。
- 含真实 Room 写入、读 Flow、显式读取和全表失效观察的另一次对照，每种配置各 600 组，测到进程 CPU 分别为 456 和 312 毫秒。异步调度及 JIT 噪声盖过了差值，无法据此估算每次失效通知的成本或手机耗电。

## B · 改前和改后实测

本地提交 `ddc156f4`。使用 AndroidFolderRecordings、生成的 Room DAO、原生 SQLite 和可控协程时钟。配置一个通话录音目录和 40 条已关联的文件夹录音，每条关联一段录音；其中 39 条已完成，一条转写中。先跑完初始订阅，再在 24 小时内每隔 288 秒写一段普通录音，每次独立提交并处理完失效通知。两次均订阅导入纪要就绪、转写队列、声纹计数作为对照。扫描计数取生产类请求扫描的回调入口，未模拟实际 SAF 遍历耗时。

| folderRecordings.observe | 0 次 / 0 行 | 0 次 / 0 行 |
| imports.observe 主查询 | 300 次 / 24,000 行 / 48 毫秒 | 0 次 / 0 行 |
| imports.observe 的 segments 关联 | 300 次 / 12,000 行 / 569 毫秒 | 0 次 / 0 行 |

初始阶段单独计量。改前两项整表订阅各执行一次，文件夹表读 40 行，导入父游标两遍共读 80 行，关联另读 40 行，启动请求扫描 2 次。改后常驻进度首次只读 1 行聚合结果，启动请求扫描 1 次。表中 24,000 个父游标行对应 12,000 条业务结果。617 / 651 毫秒的占比仅覆盖这次负载所测的重复查询。

- 补转进度用文件夹录音和导入状态聚合，不订阅录音段。最后一条完成后测得整轮进度归零，新增一次完成扫描。清除目录配置后再更新导入状态，聚合查询增量为 0。
- 队列进度给补转执行机会。恢复或变更目录设置、待稳定新文件、到期检查、手动刷新和整轮完成可触发扫描。回前台会检查待稳定文件及到期时间，扫描与设置命令仍在原队列串行处理。
- 时间线按半开时间范围查询；按导入编号取开始时间、编号倒序的第一条。未配置目录时停掉相关常驻订阅，主动查看保留的历史录音时按需读取快照。搜索在被调用时才读取。数据库维持版本 42。
