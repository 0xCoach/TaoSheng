# 卡 070 转写速度修复

## 范围与根因

基于手机所装 0.2.13 对应的 `ea07e2a` 创建独立分支 `codex/070-env-speed`，避免把待审核的 071 数据库迁移一起装入。未修改 UI、MainActivity、Contract、数据库版本或 JNI。手机仍为数据库 23。

1. `EnvSoundModel` 在生成每个浮点采样点时调用 `IntRange.count()`。编译字节码确认调用的是逐项迭代的 `CollectionsKt.count(Iterable)`，导致 O(n²) 开销。手机实际环境音耗时曾达 12.643、152.886、206.283、227.027、380.690 秒；环境音线程持续占一个 CPU 核心。
2. 分类后无条件检查本人声纹，即使普通人声已经判为 Keep。长段会以 5 秒步长扫描最多 10 秒窗口。

## 修改

- `EnvSoundSamples` 用范围端点一次求出长度，线性转换，保留原来的偏移、归一化和最短一秒补零。
- `EnvSoundAnalysis` 仅在本人身份可能改变环境音/媒体判定时调用声纹。预判使用开启过滤的最严格设置，因此途中调整开关也不会漏掉本人保护；普通人声和非法输出直接沿用保守规则。
- 继续由原仓库统一处理错误：分析失败照常转写；疑似环境音、影视、只标记模式仍保留本人保护。
- 进度显示准备音频、识别声音、核对本人声音，并在结束/异常时清除，避免残留上一段的 NPU 文字。
- 诊断拆分解码、加载、采样准备、模型推理、本人检查和总耗时；不记录音频内容、原话或凭据。

## 定向测试

`EnvSound070Test` 12 项、`EnvSoundSpeedTest` 5 项全部通过。新增测试覆盖采样一致性/补零、30 秒全窗及长音频三窗的性能回归、无需声纹时判定等价、各档位的本人保护、失败放行路径与进度清理。未运行全量测试。

使用 JDK 21 离线构建。单测构建 52 秒，Release 与设备测试 APK 构建 77 秒，后续仅重建调整过的设备测试。手机测试包与应用及原安装包签名一致。

三段均无需额外本人检查，均识别出文字。长段耗时包含音频解码；105.584 秒样本中解码约 5.985 秒、模型加载约 1.038 秒、实际标签推理 0.766 秒、采样准备 1 毫秒。测试通过真实 JNI 和 NPU 完成，但不是跨设备性能保证。

首次设备测试的本地识别进程被系统 lowmemorykiller 回收，日志明确记录 oom_score_adj=905；测试改为打开前台 Activity 后识别成功。短样本已成功后，原计划的历史导入长音频因既有清理机制已不存在，故不重复测短样本，改从更新前快照复制两段仍保留的真实长音频至隔离测试缓存；长样本测试完成并返回 `OK (1 test)`。不向用户数据库重复写入这些测试转写。

更新前保存原安装包和 714,337,280 字节完整应用快照（6,865 个文件，包含数据库、设置、录音和模型）。私有材料位于本工作区 `.local/env-speed/`，不进入 Git。

已同签名覆盖安装到手机，保留现有可调试标志以便核对。未提高版本号、未远端发布；本地仍显示 0.2.13/versionCode 32。APK SHA-256：`8a6ee33631c510322db017b4bbf486c82ff8ca3fb23e970f444b9be7b834427e`。

安装/定向测试后数据库 quick_check=ok；原有 5,317 段记录、13,966 条原话、1,193 件事件、255 个条目、71 个声纹样本的 ID 全部保留。环境音、转写方式/NPU/实时、聆听设置一致；13 个 ASR/环境音模型相关文件大小与修改时间一致。

## 构建与交接

常规构建保持仓库原来的 Release 配置。此次手机检查额外用本地 Gradle init 脚本启用 Release debuggable，未把这一开关写入产品构建脚本。

修复应由主工作区合入本分支后进入后续版本，防止其他分支重新安装旧代码。普通生产构建不需要设备测试专用的 debuggable 开关。

仍可优化的部分是每段模型加载和整段解码；本次先解决已证实的重复循环和无必要声纹，未修改这些路径。
