# 卡 124 · 后台本地转写保活交付

## 做了什么

- 已用 `gh issue view 21` 阅读 [issue #21](https://github.com/0xCoach/TaoSheng/issues/21) 全文。
- `LocalAsrConnection` 使用 `BIND_AUTO_CREATE | BIND_IMPORTANT`，让本地推理服务随主进程获得更高优先级。
- `LocalAsrService` 在请求出队、真正开始处理时持有 `PARTIAL_WAKE_LOCK`。成功、失败均由 `try/finally` 释放；客户端超时或取消通过原有 IPC 取消消息立即释放当前请求的锁，服务销毁也释放。排队和模型空闲驻留期间不持锁。
- 唤醒锁使用原有客户端执行预算 `max(5 分钟, 片段时长 × 2 + 1 分钟)`，另以 `CaptureTuning` 最长 5 分钟片段计算硬上限 11 分钟。`acquire(timeout)` 由系统兜底释放，即使 JNI 阻塞、不响应协程取消，也不会无限持锁。客户端原有推理超时和识别结果不变。
- `EARLY_WORK` 加急，配额不足退回普通任务。唯一任务策略、网络约束、30 秒线性退避、周期兜底与空闲解绑时长均保留。
- 新增主进程诊断：绑定丢失、解绑、连接/重建、绑定超时、推理超时；实时任务后台延迟、流水线占用、执行取消。只记录阶段、界面是否前台、进程重建标记、PID 和等待时长，不记录音频、文字、路径或异常内容。
- 通过 Application 生命周期回调采样界面可见状态，所有诊断仍由主进程写入现有 `PipelineTimes`，随问题报告导出，不新增轮询或常驻任务。

## 平台选择与依据

- [Context 官方绑定标志说明](https://developer.android.com/reference/android/content/Context#BIND_IMPORTANT)：`BIND_IMPORTANT` 从 API 14 可用，覆盖 API 29–35；客户端处于前台时，允许被绑定进程提升至前台进程级别。这是进程优先级继承，不是启动另一个前台服务，也不能保证兼容层绝不冻结进程。
- [BIND_INCLUDE_CAPABILITIES](https://developer.android.com/reference/android/content/Context#BIND_INCLUDE_CAPABILITIES) 传递前台状态带来的能力，如后台使用麦克风、相机、定位；本地推理只读已保存音频，不需要这些能力，因此不加。也不使用会使服务比录音主进程更重要的 `BIND_ABOVE_CLIENT`。
- [Android 12+ 后台启动前台服务限制](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)：官方列明可见状态转换、用户操作等豁免，没有给出“已有麦克风前台服务就必然可以再启动 dataSync 前台服务”的独立保证。任务可能排队到录音停止后才执行，兼容层行为亦未验证；按卡中“不确定就不加”的要求，实时模式不增加主动 `setForeground`，避免引入新的后台启动异常风险。
- [WorkManager 加急任务说明](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work#expedited)：Android 12+ 使用加急作业；较旧平台可能通过前台服务执行。本项目现有 `getForegroundInfo()`、通知及 `dataSync` 声明继续供 Android 10/11 使用。配额不足或系统繁忙时加急仍可能被推迟。

## 真机验收步骤

1. 负责人小米 14 Pro：选本地模型、开启实时转写，确认模型就绪；正常开始录音，记下队列积压与电量。
2. 切后台并锁屏 30 分钟，期间持续和间歇说话；确认录音持续、回前台时转写已跟上，而不是回前台才集中开始。对比相近录音负载下的耗电和发热。
3. 安静超过原有 6 分钟空闲期限，再在后台说话，确认解绑后可重建并继续转写。停止录音、等队列完成后应无 `resound:local-asr` 唤醒锁驻留（可用 `adb shell dumpsys power` 检查）。
4. 请 issue 提出者在同一卓易通 anco 容器、同一本地模型设置下重复前台对照、后台锁屏 30 分钟、空闲后再说话三组步骤。记录发生时间、录音是否继续、转写是否积压，并导出问题报告供负责人对照诊断。未代发 issue 评论。

## 诊断解读与遗留边界

- `foreground` 指界面可见，不等于录音前台服务存在。`local-*` 事件的 `processRecreated` 比较上一次观测的推理进程实例；首次未知标为 `unknown`，避免把首次启动误记成重建。空闲正常退出后再次绑定也会记为重建。
- `realtime-delayed` 在后台相关任务开始时回看等待（同一主进程至少 30 秒）；跨主进程重建只能记录恢复迹象，不比较跨进程/重启的单调时钟。此诊断不推断是配额、前序任务还是系统冻结；尚未启动的 Worker 不能主动记日志。`realtime-pipeline-busy` 与 `realtime-stopped` 则记录明确观察到的占用/取消。
- 原生推理阻塞时释放锁不等于强制中断 JNI，继续沿用原有取消和空闲解绑回收机制；本卡不修改模型、分人和推理结果。
- 小米耗电、锁屏持续转写和鸿蒙兼容层效果仍须按上述步骤验收；本地测试不替代真机结论。无界面配合或约定签名变更需求。
