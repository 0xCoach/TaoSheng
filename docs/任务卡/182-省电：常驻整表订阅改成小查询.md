# 卡 182：省电——后台常驻的“整表订阅”改成带条件的小查询

## 背景与证据

预览版 8 的真机问题记录（卡 171 的“各线程 CPU 时间”，7 个 10 分钟采样，未充电、多为熄屏、聆听 / 录音中）显示：主进程平均每 10 分钟用约 134 秒 CPU，其中**数据库线程 19～57 秒**是最大头，运行时（内存回收）10～19 秒、后台协程 8～55 秒跟着高。

负责人手机上 `segments` 表约 2 万行、`env_sounds` 一周新增约 5000 行。代码里有多处**后台常驻**（`SharingStarted.Eagerly` 或 `app.scope.launch { collect }`）订阅整张表；每存一段录音、每转写完一段，这些订阅各把整张表读一遍、建 2 万个对象再丢掉。这是读代码得出的判断，与数据吻合，但各处占比未经实验证实——本卡第一步就是证实。

已发现的常驻整表订阅（路径相对 `app/src/main/java/app/resound/`，开工前自己全局再搜一遍，漏的补进来）：

| 位置 | 现状 | 真正需要的 |
|---|---|---|
| `voiceprint/LocalVoiceprintRepository.kt` 的 `state`（Eagerly） | `observeSegments()` 整表，只为数两个数 | 已处理 / 待处理声纹的段数：两个 `COUNT` |
| `transcribe/RoomTranscriptRepository.kt` 的 `queue`（Eagerly） | `observeSegments()` 整表，只为数 Pending、Failed、有无 Running | 一条聚合查询 |
| 同文件 `init` 里的失败过期 | `observeSegments()` 整表再过滤 `status == "Failed"` | 只查失败的段（或只要最早的 `firstFailedAt`） |
| `topic/TopicAndroid.kt`（约第 83 行，常驻 collect） | `observeSegments()` 整表映射成 (id, status, voiceprintProcessedAt) 再比对 | 只需要“与未完成专题时段相交的段的转写 / 声纹状态有没有变”。没有待整理的专题时完全不需要订阅 |
| `envsound/LocalEnvSoundRepository.kt` 的 `rowUpdates` / `rows` / `eventUpdates` / `presentation`（全是 Eagerly） | `SELECT * FROM env_sounds` 整表常驻在内存 | 按需：界面或整理要某个时间范围时查那个范围；确实要常驻的只留最近一小段 |
| `envsound` 的 `hourly(date)` | `observeSegments()` 整表 | 按那一天的时间范围查 |
| `voiceprint/LocalVoiceprintRepository.kt` 约第 352 行 | `observeSegments().first()` 取整表再过滤 | 带条件的一次性查询 |
| 其他无条件的 `Flow<List<…>>`（`ImportRecordDao.observe()`、`TopicDao.observeAll()`、`SkillDao.runs()`、`ThingDao.observeRecords()`、`MemoryDao.observeUsage()`、`asr_usage` 等） | 逐个查：是否常驻订阅、表会不会随时间无限增长 | 会增长且常驻的照同样办法处理；小表或只在界面打开时订阅的不动，列入交付说明即可 |

## 要做

1. **先量**：写一个可重复的本机基准（Robolectric 或纯 JVM 均可，放 `app/src/test/`），造 2 万行 `segments`、3 万行 `env_sounds`（合成数据），在所有常驻订阅都活着的情况下，模拟“存 50 段 + 各转写完成”这串写入，统计每个订阅被触发的次数、读出的总行数、耗时。给出改前各处占比。这一步的数字写进交付说明。
2. **改**：按上表把常驻整表订阅换成带 `WHERE` / `COUNT` / `EXISTS` / 时间范围的 DAO 查询。新查询写成 `@Query`（挂起函数或 Flow），需要的索引先看现有索引是否够用；**不新增数据库版本、不改表结构**——如果某个查询没有合适索引会全表扫描，在交付说明里列出来，由 Claude 决定是否另开卡加索引，本卡先用现有索引能支持的写法。
3. **去抖 / 合并**：同一批写入（转写一段会连改 `segments`、`transcript_lines`、`asr_attempts` 多次）引起的重复触发，能用 `distinctUntilChanged()` 挡掉的挡掉（聚合结果没变就不往下发）。不要加会让界面明显变慢的延时。
4. **再量**：同一个基准重跑，给出改后数字和前后对比。
5. **行为不变**：每个被改的 StateFlow / Flow 对外的值、更新时机（用户可见层面）不变。`TranscribeQueueState`、`VoiceprintState` 等约定类型不改。专题“原话转写完就整理”的触发不能变迟到用户能察觉。
6. **顺手搬家**：把“什么情况下需要订阅 / 需要哪些聚合”这类纯判断写进 `:shared`（例如专题是否需要盯转写进度）。DAO 仍留在 `:app`（搬 DAO 是卡 176）。

## 数据库访问写法

main 已换成多平台驱动（卡 175）：不要用 `SupportSQLite*`、`SimpleSQLiteQuery`、`openHelper`、`androidx.room.withTransaction`；事务用 `data/DatabaseSql.kt` 里的 `writeTransaction`；**不得在已持有 Room 事务的协程里调用 `readSqlBlocking`**。优先用普通 `@Query`。
