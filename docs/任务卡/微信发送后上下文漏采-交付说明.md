# 微信发送后上下文漏采

## 证据与边界

真机 00:53:38 微信记录有原话、无标题、无 before；上下文设置开启。当时日志已被后续日志覆盖，不能断定该条一定走了哪个采集分支，也不能断定由去重造成。

检查代码发现：输入框已空、改用已发送气泡时，旧的兜底直接返回空上下文和空标题。这是可用合成场景复现的独立缺陷。

## 修改

- 截图解析统一入口：聊天即使输入框已空，也提取标题和气泡前的双方上下文；没有气泡时保留可见上下文作为比较基线。
- 多张截图合成时，若只能从新发气泡取原话，采用该气泡截图的上下文，不再固定取最早的空输入框快照。
- 新增应用包名、上下文行数、有无标题、去重前后行数诊断，不输出聊天内容。
- 保留原有上下文去重、原话去重及采集时机。
- 真机同时发现默认提示实际是 Ask Codex to do anything，含 AsCodex、七o、anyth1ng 等 OCR 变体；补充整句匹配，不匹配包含该词组的其他指令。
- 未回填历史记录，不改界面、约定文件或数据库结构。

## 验证

VoiceInputEmptyBoxContextTest 3 项、VoiceInputTerminalTest 3 项、VoiceInput049Test 21 项通过，assembleDebug 成功。新增场景覆盖发送后保留双方上下文、无气泡基线、多张截图采用新气泡对应上下文。

真机待验：双方存在新消息时用微信语音输入并发送，检查正文、上下文和诊断的去重前后行数。此修复尚不证明 00:53 那一条的唯一根因；如仍漏采，依据新增诊断继续定位。此前错记内容不自动删除。
