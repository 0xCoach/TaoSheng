## 0. 现状与 #60 根因（Claude 已查明）

`TopicEngine.run()`（`topic/TopicGeneration.kt`）会后一次性：等全部录音转写+认人 → `TopicGenerator.generate`：按字数（`TopicProcessingRules.CHARS=2400`）切段逐段“提取要点”（DigestPrompt）→ 再由 `ImportSummary` 按字数切段“整理纪要”→ `summaryGroups` **两两**逐级合并。
进度/缓存 `TopicProcessingSession`：`begin()` 里 `store.read(id)?.takeIf { it.source == source }`，`source` 是**整场所有原话**（含 speakerName/speakerTag）的 JSON。结果：
1. 整理过程中认人改了一句说话人、补转写一段、改了一句原话 → source 变 → **全部已完成段作废，从头再来**；长会议整理慢，期间几乎必然有改动 → 一直“整理中”。
2. 按字数切段，前面多一句，后面所有段边界都变，缓存也对不上。
3. 每段输入里带 `DigestPrompt.withTodoContext(unfinished, ignored)`（全局未完成/已忽略待办），用户在别处勾掉一条待办，输入就变，缓存失效。
4. 两两合并：12 段要 11 次汇总调用，慢。
5. 等待阶段（`waiting()`）只显示“等待原话处理完成”，不说在等什么、没有上限。

## 1. 时间块

- 专题时间线按 **10 分钟**一块（常量 `TopicBlocks.MINUTES = 10`），从第一个 span 的开始时刻起算；暂停的空档不占块（按各 span 拼接后的“会议时间”切）。原话按 `startAt` 落块；跨块的句子归开始所在块。
- 块编号、起止时刻只由 spans 决定，**和原话内容无关**，所以边界稳定。
- 每块整理时，把**上一块最后 3 句**作为“前情”附在输入里（标明“仅供理解，不要提取”），块的结果只算本块原话。
- 单块原话超长（> `CHARS`）时，块内再按现有 `splitText/splitRead` 拆，但缓存仍以“块”为单位组织。

## 2. 每块的工作与缓存

- 每块做两件事（与现在两遍对应，但都按块）：
  1. **提取**：事件要点 + 待办/决定等条目（现 DigestPrompt 那一遍，含 lineId）；
  2. **纪要分段**：会议/培训/访谈等 kind 的分段纪要（现 ImportSummary 那一遍的叶子；口播稿 kind 走 script 那一遍）。
- **缓存键 = 本块内容指纹**：专题 kind、名称、本块原话（id、时间、文字、说话人）、前情 3 句、提示词版本、热词。**不含**全局待办上下文。
- **待办上下文冻结**：第一次整理某块时用的 `unfinished/ignored` 摘要随块结果一起存；之后该块因内容变化重做时用**当时最新**的。块内容没变就直接用缓存，不因别处待办变化而重做。（最终保存时现有的去重 `ImportTodoMerge.same` 等照旧兜底。）
- `TopicProcessingSession` 改：不再用整场 source 判定作废。按块指纹命中就复用；没命中的块重做。旧格式 checkpoint 读不懂就当没有（不报错）。
- 块结果文件随专题删除/重新生成清理；同一专题只保留当前各块最新指纹对应的结果（旧指纹的清掉，防止无限增长）。

## 3. 什么时候整理一块（会中就开始）

- **块“就绪”**：块已结束（会议时间已过块尾，或专题已结束）且与该块时间重叠的录音段都已转写完（`Done/Empty/SkippedEnv/SkippedPlayback`）。
- **认人**：块就绪后若声纹还有待认（`voiceprintPending > 0`），最多等 **5 分钟**；超时先按“说话人 N”整理，认人完成后该块内容变化 → 自动只重做这一块。
- **Running / Paused 期间**就处理就绪块（现在只处理 Ended/Summarizing）。专题状态在会中不改成 Summarizing（UI 仍是“进行中”），块结果只存文件、不写事件/待办（避免会中产生半截待办）。
- **会中转写**：专题 Running 时，这段时间的录音**录完就转写**（不受“每 N 分钟”间隔设置），并在转写队列里排最前（`TranscribeDao` 候选排序把 Running/Paused 专题也算进去）。转写完一段后触发 `TopicWork`。核对现有 `transcribeScheduler`/实时转写开关的实现，找到最小改法；用户关了“仅 Wi-Fi”等限制照旧遵守。
- 会中整理同样走 `TopicWork`（前台通知“正在整理专题”在会中**不要**每 10 分钟弹一次：会中块整理用不弹前台通知的普通 Worker，会后汇总再用前台）。

## 4. 会后

- 结束后：处理剩余就绪块 → **汇总**。
- 汇总只读各块的纪要分段/要点（不读原文）。**扇入改大**：各块结果总长 ≤ 12000 字时**一次调用**出全文纪要；超过时按 6 个一组分组汇总再总汇总（替代两两合并）。
- 事件（`TopicGenerationRules.synthesize`）和待办来自各块提取结果的合并；保存逻辑（`db.writeTransaction` 那段）沿用。
- 保存时若发现原话又变了：现逻辑是改回 Ended 整个重来；改为只重做变化的块 + 汇总（汇总缓存键 = 各块结果指纹列表，块没变汇总也复用）。

## 5. 不卡死、说清楚

- 提供进度（`TopicProgress` 扩展或新数据类，放 `:shared`）：`blocksTotal / blocksDone / blocksFailed`、**正在等什么**（`waitingTranscribe: Int` 段数、`waitingVoiceprint: Int`、`waitingNetwork: Boolean`）、`lastProgressAt`、会中已整理到的时刻、各块可读要点（会中可展开看）。
- **等待上限**：会后等待（转写/认人）**30 分钟没有任何进展**（无新转写完成、无块完成）→ 进度里给出 `stalledReason`（如“还有 2 段转写失败”），并允许用户“先整理（剩下的不等了）”：提供 `suspend fun summarizeNow(topicId)`，把没就绪的块标为“跳过”，用已有块出纪要，纪要末尾注明“hh:mm–hh:mm 这段没整理（原因）”。之后那几块就绪了，用户可点“补上”（`regenerate` 现有入口即可，只会重做缺的块+汇总）。
- **单块失败**：某块提取/纪要失败（重试用现有 `request` 的 2 次）→ 标该块失败，继续其他块；汇总照出并注明缺哪段；`retry` 只重试失败块。
- 会后整理阶段 30 分钟无进展（无块完成、无汇总完成）→ 记 `FailureNotes`，状态转 Failed 并给出原因，不无限转圈。

## 测试（适度，10～15 个）

- 块切分：多 span（有暂停）边界稳定；原话增减不改变块边界。
