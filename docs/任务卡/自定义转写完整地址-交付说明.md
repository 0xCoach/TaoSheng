# 自定义转写支持完整请求地址——交付说明

日期：2026-11-08。分支：`feat/custom-transcribe-full-endpoint`。

本次只提交**配置层与请求层**，不含界面改动。界面入口（选地址写法、完整模式下的热词开关）留待维护者按项目风格实现，文末列出了界面需要的接口。

## 做了什么

### 一、新增 `transcribe/CustomEndpoint.kt`

自定义转写原来只支持 OpenAI 兼容的 `audio/transcriptions` 协议：填根地址，自动补 `/v1` 与 `/audio/transcriptions`。MiniMax 这类不是 OpenAI 兼容的服务，接口路径、请求参数和错误体都对不上，地址配对了也用不了。

本次把「地址怎么写」独立成一个配置项：

- `CustomEndpointMode.Auto`（自动匹配路径）：行为与原来完全一致，填根地址或带 `/v1` 的地址，自动补 `/audio/transcriptions`。
- `CustomEndpointMode.Full`（完整请求地址）：按填写的地址原样请求，一个路径都不补；完整模式只有一条候选地址，不再退回 `/v1` 去试。

`fullEndpoint()` 的校验规则：只认 `http/https` 与主机名；不允许 `user:pass@` 与 `#` 片段；查询参数（`?GroupId=…` 之类）原样保留；结尾多余的 `/` 去掉。允许带查询参数是完整模式相对自动模式的关键差异——自动模式沿用 `OpenAiEndpoint.bases()`，本来就不接受带查询参数的地址。

### 二、`AndroidTranscribeSettings`

- 新增 `endpointMode` 与 `customPrompt` 两项配置，持久化在 `transcribe` 偏好里；`endpointMode` 存枚举名，读到非法值时回落到 `Auto`。
- `saveCustom` / `saveCustomAll` 增加可选参数 `mode`，默认值取当前已持久化的模式。**旧调用点不用改，编译和行为都不变。**
- 校验按模式分流：完整模式走 `fullEndpoint()`，自动模式走 `OpenAiEndpoint.bases()`。
- `ready()` 对自定义服务的判断改用同一套校验，避免出现「能保存却不就绪」。
- `identity()` 带上模式，换写法会让进行中的转写轮次停下重做，不会拿旧地址继续转。

### 三、`ConfiguredAsrProvider`

- 请求地址按模式计算：完整模式一条，自动模式沿用原来的候选列表。
- 完整模式默认**不**发送热词。热词靠 `prompt` 字段送出，部分服务不认这个参数，发过去会报错；设了 `customPrompt` 才带。自动模式照旧一直发热词。
- 响应解析放宽：OpenAI 兼容与 MiniMax 都返回 `{"text": …}`，照旧读取；MiniMax 风格的 `{"base_resp":{"status_code":…}}` 错误体也能看懂——`1004` 提示「鉴权失败，请检查密钥」，其余错误码统一提示「服务返回错误，请检查地址、密钥和参数」，**不回显服务端原文**（沿用本项目只用固定文案的规矩）。

## 界面需要的接口

| 用途 | 接口 |
| --- | --- |
| 读当前写法 | `AndroidTranscribeSettings.customEndpointMode: CustomEndpointMode` |
| 读热词开关 | `AndroidTranscribeSettings.customPrompt: StateFlow<Boolean>` |
| 写热词开关 | `AndroidTranscribeSettings.setCustomPrompt(on: Boolean)` |
| 保存地址与模型 | `saveCustomAll(endpoint, model, key, mode)`，或先设好模式再用旧签名保存 |
| 请求实际地址 | `transcriptionEndpoints(endpoint, mode): List<String>` |
| 校验用户填的地址 | `fullEndpoint(input): String`，抛异常时的消息可直接展示 |

`CustomEndpointMode` 自带 `title` 与 `hint`，可以直接用作界面文案。

## 真机需要注意什么

1. 完整地址模式按填写的地址原样请求，需要自己保证地址是完整可用的请求地址（例如 `https://api.minimax.cn/v1/speech_to_text`，以服务商实际开通的域名与路径为准）。
2. 完整模式不发送热词；如果服务其实支持 `prompt`，需要在界面上打开开关。
3. 完整模式拿不到模型列表，模型名只能手填。
4. 完整模式不区分说话人，多人对话的「谁在说话」仍要靠豆包或本机模型。
5. 换地址写法后，配置标识 `identity()` 会变化，进行中的一轮转写会停下重做，属预期行为。

## 遗留问题

- 除 `1004` 外的错误码没有逐个映射，统一提示「服务返回错误，请检查地址、密钥和参数」；拿到官方错误码表后再补。
- 完整地址模式没有「拉取模型」，模型名只能手填。
- 服务端是否支持 `verbose_json` 的分段与说话人信息，本次没有解析。
- 本次没有发版、没有改版本号、没有改数据库版本、没有改包名与签名配置、没有推送远端；CHANGELOG 未动，等发版卡统一写。
