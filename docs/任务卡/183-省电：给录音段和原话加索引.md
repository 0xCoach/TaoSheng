# 卡 183：省电——给录音段表和原话表加索引（数据库版本 33 → 34）

## 背景

卡 182 把后台常驻的“整表读取”改成了只数个数或只查需要的行（本机基准：读出行数约 963 万 → 356，耗时 17 秒 → 0.64 秒），已随预览版 10 上真机，负责人反馈没有问题。它留下两处仍要扫整张表的查询，因为加索引要升数据库版本，当时没做（见 `docs/任务卡/182-交付说明.md` 的“索引与仍有的扫描”和末尾的 Claude 审核意见）：

1. **录音段表 `segments` 没有按状态的索引。** 转写队列计数（`observeQueueCounts`）、声纹进度计数（`observeVoiceprintCounts`）、失败段（`observeFailedSegments`）每次触发都要扫一遍全表。负责人手机上这张表约 2 万行，每存一段、每转写完一段都会触发。
2. **原话表 `transcript_lines` 没有按开始时间的索引。** “已完成专题有没有迟到的原话”（`TopicDao.observeLateTranscriptIds`）在每次原话表变化时重算，要按时间范围找原话；已完成的专题越多越重。仓库里其他按时间范围查原话的地方也可能受益。
3. （待评估）导入记录 `import_records` 的“待整理”查询没有专用索引。这张表小，是否值得加由数据决定。

## 这张卡的特殊性

**这是近期第一次真的改用户手机上的数据库结构。** 加索引不改数据，但：

- 版本升到 34 后，用户**无法装回**预览版 10 及更早的版本（旧版本不认识版本 34 的库）。
- 迁移在升级后第一次打开 App 时执行，表大的话要花时间，期间 App 打不开。
- 旧备份（版本 33）恢复到新版本时要能自动升级。

所以本卡要求：每个索引都要有数据证明值得加；迁移耗时要量；不值得的不加。

## 要做

### 第 1 步：先量，决定加哪些

1. 把 `app/src/test/observer182_plans.py`（卡 182 的查询计划脚本）和 `TableObservers182Benchmark` 当起点。造合成库：`segments` 5 万行、`transcript_lines` 50 万行、已完成专题 200 个、`import_records` 2000 行，状态分布贴近真实（绝大多数 `Done`，少量 `Pending` / `Failed` / 其他）。
2. 对下列候选索引，分别量“不加”和“加”两种情况下：相关查询的查询计划、单次耗时、在卡 182 那串“存 50 段并转写”写入下的累计耗时；以及**写入变慢多少**（每多一个索引，每次插入 / 更新都要多维护一份）和**库文件大多少**。
   - A：`segments(status, voiceprintProcessedAt)`
   - B：`transcript_lines(startAt, segmentId)`（也评估只建 `transcript_lines(startAt)`）
   - C：`import_records` 上支持“待整理”条件的索引（先看查询的实际条件再定列）
3. 全仓库搜一遍按 `segments.status`、`transcript_lines.startAt` 过滤或排序的查询（不只是卡 182 那几条），列出每条在加索引后的查询计划变化。**不许出现加索引后某条查询变慢的情况**；有的话说明原因并处理（例如优化器选错索引）。
4. 给出结论：每个候选“加 / 不加”及数据依据。**收益不明显（比如相关查询累计耗时降不到一半，或表本身很小）就不加。** 结论和数据写进交付说明后再往下做。如果结论是三个都不值得加，本卡到此结束，状态写 `DONE：未加索引` 并说明。

### 第 2 步：改查询，让索引用得上

- 卡 182 的队列计数是一条 `COUNT(CASE WHEN …)` 聚合，写法本身就要扫全表。加了索引 A 以后改成能走索引的写法（例如按状态分别计数，或 `WHERE status IN (…)` 再分组），**对外结果不变**：`QueueCounts` 的三个值与旧写法在同一批数据上相同；`TableObservers182Test` 里的对照用例必须仍然通过，必要时补充用例。
- 声纹计数、失败段、迟到原话探测同理：能用上新索引、结果不变。
- 用查询计划脚本证明改后的每条查询确实走了新索引（或说明为什么优化器的选择更好）。

### 第 3 步：迁移 33 → 34

- 实体上加 `@Index`（或在 `indices` 里加），索引名用 Room 的默认命名 `index_<表名>_<列名…>`，与迁移里的 SQL **完全一致**，否则 Room 打开时校验会失败。
- `CaptureDatabase.VERSION` 改为 34；在 `CaptureDatabase.MIGRATIONS` 里**只加一条** `33 → 34`，内容只有 `CREATE INDEX IF NOT EXISTS …`。不动任何表、列、数据、触发器。
- 导出 `34.json`。`1.json`～`33.json` 不许变。
- 迁移耗时：在第 1 步的合成大库上实测 33 → 34 的耗时，另外再测一个更大的（`segments` 20 万、`transcript_lines` 200 万）。写进交付说明。如果最大那档超过 5 秒，停下来报告，由审核人决定是否要改成“后台补建”。
- 迁移必须可重复执行（`IF NOT EXISTS`）、中途被杀后再次打开能继续。

### 第 4 步：夹具与对照

卡 175 的夹具（`app/src/test/resources/driver175/`，38 份文本 + 1 个旧备份）记录的是“升到版本 33 后的完整结构和数据”。版本升到 34 后，最终结构会多出新索引，这些夹具不再能逐字比对。处理原则：**旧夹具文件一个字节都不改、不删、不重录**；改的是比对方式，并且比对方式的改动必须是可审核的、最小的：

- 新增一个很小的“版本 34 相对 33 的预期差异”文件，内容只有新索引在 `sqlite_master` 里的那几行（名字和完整 SQL）。
- 对照测试改为：把实际的版本 34 快照里**恰好这几行**去掉后，与原有版本 33 夹具**逐字相同**；并且这几行与预期差异文件逐字相同、一行不多一行不少。表数据部分必须完全不受影响。
- 32 条迁移路径、新装、查询 25 组（查询结果不许变；如果第 2 步改了某条被夹具记录的 SQL 文本，把“SQL 文本变了、结果行没变”作为一条明确列出的预期差异，同样用差异文件表达，不重录）、事务、通知、备份恢复，全部照此处理。
- 旧备份（版本 33 的 `synthetic-backup.zip`）必须能被新版本校验、恢复并自动升级到 34，恢复后数据与原夹具一致、结构多出的只有新索引。
- 新做的备份里数据库版本是 34：确认备份清单里记录的版本、以及“版本比 App 新的备份拒绝恢复”这条既有规则仍然成立（用例）。
- `TriggerHistory181Test`：10 个历史起点升级后仍是 15 个触发器，定义与新装一致；`python3 tools/trigger-audit-181/freeze_history.py --check` 通过。
- 如果基于卡 176 的分支：33.json 的身份校验码对比那条门槛只针对 33.json，本卡不改它。

### 第 5 步：再量

同一个基准、同一套合成数据重跑，给出加索引前后的对比表（查询耗时、写入耗时、库文件大小、迁移耗时）。
