# 卡 059 · “每隔 N 分钟整理”先转写；导出、推送里的时间一律带日期（后端）

App 名叫“涛声”。给用户看的文字一律写“涛声”。
界面里的时间显示由 Claude 做，**本卡不改 `ui/` 和 `MainActivity.kt`**。

## 一、定时整理先转写（已查明的问题）

用户设了每 30 分钟整理一次，但 9:40 整理一次后，到 10:40 都没再整理。
原因：`TranscribeWork.executePipeline` 中 `val transcribe = mode != MODE_DIGEST`，也就是间隔整理（MODE_DIGEST）**不先转写**，只整理已转写好的原话；而转写是另一条周期任务（默认也是 30 分钟），两条各自计时、互不对齐，再加上“说完约 10 分钟后才整理”，实际间隔经常变成两个周期。“按时间点整理”（MODE_TIMED）本来就先转写，没有这个问题。

已定方案：
- MODE_DIGEST 也**先转写再整理**，与 MODE_TIMED 一致。
- 但要**遵守转写自己的条件**：转写来源是云端且设了“只在 WiFi 下转写”时，若当前不是不计流量的网络，这一轮跳过转写、只整理已有的（与现在行为一样），并在 `PipelineTimes` 记一行原因。本机转写不受网络限制。电量低/偏热时沿用 `EarlyTranscribe` 现有的判断（不满足就跳过转写，只整理）。
- 不改周期任务的调度方式和约束（整理任务仍只要求联网）。

## 二、导出、推送里的时间一律带日期

已定方案：**凡是写进文件、导出、推送正文里的时刻，一律带日期**，单看一段也知道是哪天。统一格式（抽一个共用函数，别各写各的）：
- 事件：`10月29日 周三 14:05–14:32`（跨天时结束写全：`10月29日 周三 23:50–10月30日 周四 00:20`）
- 一句原话、一个时刻：`10月29日 14:05`
- 不是今年的：前面加年份 `2025年10月29日 …`

至少改这些（全局再搜一遍 `HH:mm`，推送/文件/导出类的都要覆盖）：
- `push/MemoryFolder.kt`：时间线小标题 `### E123 · 14:05 …` → `### E123 · 10月29日 周三 14:05–14:32 …`；原话 `### L… · 14:05 · 某人` → 带日期；技能卡、提醒段落里的时刻同理。
- `diary/LocalDiaryRepository.kt`（记忆 → 导出 Markdown）：事件时间、原话、技能卡、引用的时刻都带日期。
- `push/DocumentPush.kt:104`：`## 14:05 标题` → 带日期。
- `push/SubscriptionReminders.kt:40`：提醒里的到期时刻带日期。
- 其他推送正文（新事件、待办提醒、技能卡 `SkillCardPush` 等）里如有只写时刻的，同样改。

**不改**：给大模型的提示词和模型输出格式（`DigestPrompt`、`SkillInput` 的 `"at":"HH:mm"` 等）、`AskTools` 已是 `yyyy-MM-dd HH:mm` 的、数据库里存的格式。

注意：记忆文件夹内容变了，增量同步会把所有天的文件各重传一次。坚果云曾因请求太多限流（503），确认现有的分批/余下排队逻辑能扛住（例如一年的文件），必要时在交付说明里写清楚首次同步会分几批完成。

## 三、必测（适度，4～6 个）

- MODE_DIGEST：有待转写的片段时先转写再整理；设了只 WiFi + 当前是流量网络时只整理、不转写。
- 共用时间格式：同一天、跨天、跨年各 1 个。
- `MemoryFolder` 生成的时间线小标题带日期（1 个）。
- 导出 Markdown 的原话行带日期（1 个）。

测试规矩见 `AGENTS.md`：只跑本卡测试，跑通一次就停。编译需 `JAVA_HOME=/opt/homebrew/opt/openjdk@21`。
