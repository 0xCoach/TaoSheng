### 1. 豆包长录音为什么慢
现状：`DoubaoAsrProvider` 用 `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_nostream`（流式输入、整段出结果），`enable_speaker_info` 开、`ssd_version 200`。要查清：
- 耗时拆成：读文件/转码 → 建连 → 发送音频 → 服务端处理 → 收结果。是哪一段随时长线性甚至超线性增长？
- `enable_speaker_info`（说话人区分）对豆包耗时的影响：同一段开/关各测一次。
- 对比豆包**录音文件识别**接口（标准版提交+查询、以及“极速版” flash `api/v3/auc/bigmodel/recognize/flash` 如账号已开通），同一批长音频比耗时和结果质量。用 `arkcli-docs`/官方文档确认参数、时长上限、价格差异（价格要写进报告，负责人要知道费用变化）。
- 切段并发：长录音按静音切成几段并发发送，再按时间拼接——是否可行、对说话人编号连续性的影响。
- 上传格式：现在发什么格式/码率？改成压缩格式（如 opus/ogg 或 mp3）能否显著减少上传时间且识别不变差。
- 是否串行排队：多段积压时是一段一段串行吗？能否 2～3 段并发（注意豆包并发限额）。

### 2. 本地转写为什么慢
- 拆分：解码、环境音判断、区分说话人（diarizer）、ASR 推理（NPU/CPU）、声纹比对各占多少。
- 重复工作：同一段音频是否被解码多次（环境音、本地转写、声纹各解一次）？模型是否每段重新加载？能否共享一次解码出的 16k PCM、模型常驻（注意内存，070 时进程被 lowmemorykiller 回收过）。
- 区分说话人在本地是不是大头；关掉后速度能快多少。

### 2.5 环境音识别的影响（负责人 10-30 追加，必查）
- 环境音判断在转写前对每段都跑一遍（豆包和本地都会经过）。拆出它占每段总耗时的比例：解码（070 实测 105 秒音频解码约 6 秒）、模型加载（约 1 秒/段）、推理、本人声纹核对。
- 同一批音频分别在环境音“关 / 只标记 / 开”下测转写总耗时，说清它拖慢了多少；是否串行挡在转写前面（能否与上传/转写并行）。
- 环境音与本地转写、声纹是否各自解码一次同一段音频；模型是否每段重新加载。
- 070 修过的 O(n²) 与多余声纹核对是否真的已在本分支生效，有没有别的路径还在走老逻辑。
- 对耗电的影响也单独列出。

### 3. 耗电
- 后台转写/整理时的 CPU 占用和唤醒（`dumpsys batterystats`、`top` 采样即可，不用精确）。
- 是否有轮询、频繁唤醒、空转、重复重试；转写是否尽量攒批在充电/亮屏/Wi-Fi 时跑（现有规则是什么，列出来）。

### 4. 质量对照（硬性要求）
- 每个提速方案都要用同一批音频对照：字差异（可按字错率估算，以现方案为基准）、标点、热词命中、说话人分段（如保留）。**质量明显变差的方案直接否掉**，报告里写清对照结果。
- 测试样本：至少 3 段短（<1 分钟）、3 段中（3～10 分钟）、2 段长（≥30 分钟，没有就用多段拼接说明来源）；豆包和本地都要测。

### A. “区分说话人”开关 + “课堂模式”快捷开关（已定）
- 设置里新增“区分说话人与认人”总开关（默认开）。关掉时：

  - 本地：`LocalAsrService` 已支持 `separateSpeakers=false` 跳过 diarizer；同时跳过本地声纹认人。
  - 流水线跳过“识别说话人”这一步（`TranscribeWork` 里 `Stage.Voiceprint`）。
  - 这段录音的原话不显示说话人名字，记 `speakerTag = null`；整理（Digest）提示词里告知“本段未区分说话人”，不要瞎猜是谁说的。
  - 每段录音在数据库里记下“当时是否区分说话人”（以后重做时可选择补做），需要新字段就升数据库 25，迁移只加一条到 `CaptureDatabase.MIGRATIONS`。
- “课堂模式”= 一个临时开关：打开后到设定时间（默认 2 小时，可选 1/2/3 小时/直到手动关）自动关闭；期间等同“不区分说话人与认人”。入口由 Claude 做（首页录音卡 + 通知栏快捷按钮 + 快捷设置磁贴），你只提供：

  - 到点自动结束要可靠（进程被杀后重启也能按时间判断，用存下来的结束时刻判断，不靠定时器）。

## 阶段二：Claude 审核后的定案（10-30，负责人在外，手机连不上）

负责人要求：代码层面先优化并测试，然后发**预览版**，负责人在线更新后反馈。所以本阶段**不碰手机、不用 adb**，真机效果靠负责人反馈；你要把每段关键耗时写进现有诊断（不含音频/原话/凭据），方便负责人导出给 Claude 看。

按顺序做，每项单独提交：

1. **豆包合并后再发**：`AsrAudioReader` 把 OGG 页攒到约 200 ms（官方建议 100～200 ms）再发一帧；PCM/WAV 保持 200 ms。输入字节不变，保留最后一帧标志、取消、背压。用报告里同一批样本（S1～M3，至少再跑 M1～M3 新旧各一次，修好探针 ping 问题）做新旧对照，只跑一次，填表。
2. **环境音少做重复活**：一轮内标签模型只加载一次、批后释放；环境音解出的 16k PCM 写成一个临时文件，同一段的本地转写和声纹直接用，不再各自解码（跨进程传文件路径，不传大 Bundle；该段处理完即删；内存峰值不能比现在高）。判断结果必须与现在逐项一致（同一批样本分数对照）。本人保护、错误放行保持不变。
3. **豆包同时传 2 段**：只对豆包；全局最多 2 路，遇限流/并发报错自动退回 1 路；结果按段回写，顺序、取消、重试计数不乱。本地仍一次一段。过滤模式（环境音“开”）仍必须先判断再上传。
4. **区分说话人开关 + 课堂模式**：按上文 A 节实现（Contract 签名先提交，Claude 审）。豆包关闭时要**主动清空** `speaker_id`（报告发现关了仍回 `0`）。
5. **查清关掉区分说话人后为什么少字**（报告里 S2：豆包 149→75 字、本地 124→79 字）。逐句对齐开/关两份结果，判断是“开着时重复了”还是“关着时漏了”。
   - 若关着漏字：根因修复（如本地关分人时也按停顿切块再识别，与开着时同样的切片方式，只是不认人；豆包查是否别的参数一起变了）。修到同批样本差异接近“开着时自身两次运行的差异”为止。
   - 若开着时重复：记下，属于现有 bug，修掉。
   - 结论和对照表写进交付说明。没查清前，课堂模式也照常发，但交付说明要写明。
6. **诊断**：每段记一行：方式、录音时长、环境音（解码/加载/推理）、上传、等结果、分人、识别、声纹、总计。放在现有“问题记录/诊断导出”里能导出。

不做：换标准版/极速版、降码率、删环境音或本人保护、本地多段并发。

验证：只跑本卡新增单测（5～15 个）与相关受影响测试；`./gradlew assembleRelease` 能过。不升版本号、不发布（发布由 Claude 做）。交付写 `docs/任务卡/073-交付说明.md`，附新旧耗时对照表。
