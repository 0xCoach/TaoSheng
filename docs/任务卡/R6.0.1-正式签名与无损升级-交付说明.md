# R6.0.1 正式签名与无损升级 — 交付说明

范围：正式签名、v3 lineage 无损升级、更新安全核对、深链定性。**签名全部在本机完成，不需要负责人 mac**——build.gradle 读本机 `~/.config/soundsound/signing.properties`，任何机器放置该文件即等价。

## 一、签名方案与产物

- 本机生成 `release.jks`（RSA-4096，30 年）+ `signing.properties`，存放 `C:\Users\50503\.config\soundsound\`，不进仓库（`.gitignore` 已含 `*.jks`/`signing.properties`）
- `apksigner rotate` 生成 `lineage`：debug 证书 → release 证书轮换证明
- 签名命令（每次发版在 gradle 产物上重签一次，保留 lineage 桥）：
  ```
  apksigner sign --ks release.jks --ks-key-alias resound --ks-pass pass:** \
    --next-signer --ks debug.keystore --ks-key-alias androiddebugkey --ks-pass pass:android \
    --lineage lineage --v1-signing-enabled false --v3-signing-enabled true \
    --in app-release.apk --out soundsound-X.apk
  ```
- 结果（apksigner verify）：v3+v3.1 通过；**API 24-32 视 debug 证书为当前签名者（同证书升级），API 33+ 视 release 证书并经 lineage 证明轮换**
- 证书指纹：release `24e5c7b41d01…2522c17`，debug `f044a52ba315…f490c5f8f6`
- **备份要求**：`release.jks` + `lineage` + `debug.keystore` 三件套必须异地备份；丢 release.jks 即失去正式签名身份，丢 debug.keystore 无法再重建 lineage

## 二、App 侧验签适配

`AndroidUpdatePlatform.validateIdentity` 原只比对当前 signer 集合——lineage 包会被自己的更新器拒掉。已改：新包 `signingCertificateHistory` 含当前设备证书时放行（Android 装包时系统再核一遍）。`UpdateAndroidTest` 补 lineage 用例，全绿。

**时序限制（如实）**：82 及更早版本的旧 verify 不认 lineage——**本次过渡（≤82 → 83）必须走系统安装器**（官网下载 / adb install），App 内更新会报「签名不对」。从 83 起新 verify 生效，后续版本恢复 App 内更新。

## 三、真机验证（OPPO PGU110，真实数据）

`adb install soundsound-1.0.5.apk` 覆盖 82（debug 签名）→ **Success**：
- `versionCode=83 / 1.0.5`，`apkSigningVersion=3`，`signatures=[release]` + `past signatures=[debug, release]`（lineage 被系统接受）
- 数据无损：账号绑定 `owner-kan` 完好、事件/待办/设置/预览通道偏好全在；「3→2 事件」是 digest 合并，与升级无关
- manifest `update.json` → 83、302 → GitHub asset（GET 206 实测有字节）
- SHA256 `87fff4cfaef14c4a12b50058291b31a011952200cd75a6939d468e77f4e203ff`，108198815 B

## 四、更新清单安全（P0-4 核对）

- 双源取 `versionCode` 最大者，stable 83 > preview 81 无降级；`newerThan` 判据 + `skipVersion`/`laterUntil` 节流
- 安装前强制校验：包名 = `app.resound`、版本递增且等于 manifest、SHA256+size 双重核对（下载不完整即拒）、签名（同上）
- 预览通道：开发者选项内手动开关，普通用户不接触；preview manifest `preview` 标志防串渠道
- 撤回版本：重发低 code manifest 即回到「已是最新」；缓存 `ready` 文件按 manifest apk.sha256 键控，撤回后不会误装
- Worker→D1 直读，无 CDN 长缓存问题（两次实测 manifest 更新秒级生效，仅 D1 传播约 1 分钟）

## 五、P1-1 深链定性

冷启动、热启动（`--es open todos|followups` 实测）均正确落页——**链路无缺陷**，此前「不跳」是 adb 测试把 `open` 误传为 URI 查询参数（真实通知走 intent extra）。无需修复。

## 五-b、R6.0.1b 检查提速（1.0.6/84，已上线）

用户反馈更新页「正在检查…」要十几秒。根因两条叠加：①设备开了预览通道 → 稳定+预览两个 manifest **串行**请求；②App 启动已触发一次 `checkNow(startup)`（预览通道不受 1 小时节流），进更新页 `LaunchedEffect` 又触发 `check(manual=false)`，两次检查在 `gate` 互斥锁上串行排队。

修复：
- `UpdateRemote.check`：稳定/预览改为**并行**请求（CompletableFuture）
- `UpdateEngine.checkNow`：非手动且非启动的检查加 **10 分钟节流**（SHORT_GAP）；更新页自动检查命中即秒回；手动「检查更新」按钮不受影响
- `setPreviewChannel` 触发检查改为 `manual=true`——切通道是用户操作，应立即生效（也保住 `channelSwitch…` 测试契约）
- 真机验证：进更新页直接显示「已是最新 · 17:17 检查」，不再转圈
- 发布：v1.0.6 GitHub Release + stable manifest 84（**注意：`/admin/release` 必须带 `files` 映射，否则 `/release/<file>` 404**——本次首次漏带已补发）
