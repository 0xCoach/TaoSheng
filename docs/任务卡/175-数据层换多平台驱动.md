# 卡 175：数据层换成多平台 SQLite 驱动（不搬家，行为不变）

## 背景

涛声要做 iOS（KMP 共用逻辑 + SwiftUI，iOS 工程本身暂缓）。0.3.0 已把规则和网络搬进 `:shared`，下一步是数据层。目标是分三步让数据库能被两端共用：

1. **本卡 175**：数据库仍留在 `:app`，只把 Room 的底层从安卓专属的 SupportSQLite 换成多平台可用的 `androidx.sqlite` 驱动写法（`SQLiteDriver` / `SQLiteConnection`），清掉所有安卓专属的数据库 API。
2. 卡 176：实体、DAO、数据库定义搬进 `:shared` 的 commonMain。
3. 卡 177：仓储层和带 `java.time` 的接口搬家。

本卡是三步里风险最大的一步：**用户手机上是真实数据，任何一条迁移、索引、触发器、查询结果都不能变**。做不到等价就停下来报告，不要硬改。

## 现状（已摸过，开工前自己再核一遍）

- Room 2.8.4（`room-runtime`、`room-ktx`、`room-compiler`，KSP 2.2.20-2.0.3）。**不升 Room 3（测试版）、不升 Kotlin/KSP/AGP**。可新增同版本线的 `androidx.sqlite:sqlite-bundled`（或 `sqlite-framework`，见“驱动选择”）。
- `app/src/main/java/app/resound/data/CaptureDatabase.kt`：版本 33，39 张表，19 个 DAO，约 299 条 `@Query`。`MIGRATIONS` 共 32 段，全部写成 `migrate(db: SupportSQLiteDatabase)`；`open()` 里 `Room.databaseBuilder(...).addMigrations(...).addCallback(...)`，回调来自 `SearchIndex.callback`、`ImportRecordSchema.callback`、`ThingSchema.callback`、`PendingDigestSchema.callback`（建触发器、FTS、补索引等）。
- 安卓专属数据库 API 分布（`SupportSQLite*`、`SimpleSQLiteQuery`、`@RawQuery`、`openHelper`、`writableDatabase`、`compileStatement`、`execSQL` 等）：`CaptureDatabase.kt` 约 133 处，另有 `things/ThingData.kt`、`topic/TopicData.kt`、`search/SearchIndex.kt`、`backup/BackupArchive.kt`、`location/Places.kt`、`data/PendingDigest.kt`、`backup/DayVolumeRows.kt`、`redo/RedoEngine.kt`、`redo/RedoData.kt`、`importer/ImportRecordDao.kt`、`ask/AskContext.kt`、`search/EmbeddingStore.kt`、`location/Location.kt`、`ask/AskTools.kt`、`ask/AskChanges.kt`、`search/IdeaMerger.kt`、`data/ReviewDao.kt`、`backup/BackupRestore.kt`、`voiceprint/LocalVoiceprintRepository.kt`、`update/PreUpdateBackup.kt`、`review/RoomReviewRepository.kt` 等。
- 全文搜索：`search/SearchIndex.kt` 三张 `@Fts4` 表（`lines_fts`、`events_fts`、`items_fts`）加 SQL 触发器，查询用 `MATCH`。
- 事务：`withTransaction` / `runInTransaction` 分布在 17 个文件约 83 处。
- 表变化通知：`invalidationTracker.createFlow(...)`、`InvalidationTracker.Observer`（`recordings/RecordingAudioPush.kt`、`context/LocalSituationLookup.kt`、`push/RecordPushWork.kt`、`digest/RoomRhythmStats.kt`，以及卡 174 新加的 `search/EmbeddingWork.kt`、`privacy/PrivacyCleanupWorker.kt`）。
- 备份/恢复（`backup/` 包、`update/PreUpdateBackup.kt`）会直接碰数据库文件或底层连接：检查点、拷贝、恢复后重开。
- 独立进程 `:local_asr` 是否打开数据库，自己查清（多进程访问同一个库会影响驱动选择）。

## 分两段做，第一段做完必须停下来等审核

### 第一段：可行性 + 录“标准答案”（不改产品代码）

1. **可行性结论**（写进交付说明，每条附 Room/AndroidX 官方文档出处；查不到写“未找到”，不要猜）：
   - Room 2.8.4 在安卓上用 `setDriver(...)` 后，哪些 API 不再可用、各自的替代写法（迁移的 `migrate(connection: SQLiteConnection)`、回调的 `onCreate/onOpen(connection)`、`@RawQuery` 改 `RoomRawQuery`、`withTransaction` 改 `useWriterConnection { immediateTransaction { } }` 或仍可用的写法、`invalidationTracker` 哪些接口保留）。
   - **驱动选择**：`BundledSQLiteDriver`（自带 SQLite，两端同一版本，包体变大）还是 `AndroidSQLiteDriver`（用系统 SQLite，安卓行为与现在最接近，但 iOS 那边是另一份）。必须回答：FTS4 及现用的分词器在所选驱动上是否可用、行为是否一致；现有库文件（系统 SQLite 建的、WAL 模式）能否被所选驱动原样打开；包体增加多少；`:local_asr` 等多进程访问有无问题；备份的检查点/拷贝/恢复流程在新驱动下怎么做。给出推荐和理由。
   - 列出全部需要改的位置清单（文件、处数、改法类别），估算工作量；指出做不到等价或有疑问的点。
2. **录标准答案（在改任何产品代码之前，用现在的实现录）**，测试夹具放 `app/src/test/`：
   - **迁移**：仓库里有 `app/schemas/` 各版本结构。对有结构文件的每个旧版本：按该版本结构建库、灌入每张表几行合成数据（覆盖可空列、中文、长文本、带外键的行），用现在的实现升到 `CaptureDatabase.VERSION`，把结果库的完整结构（`sqlite_master` 里全部表、索引、触发器、视图的 SQL，规范化空白后）和每张表的全部数据导出成文本快照，存为夹具。没有结构文件的早期版本说明缺口。
   - **新装**：全新建库后的结构快照（含回调建的触发器、FTS 表、索引）。
   - **查询**：挑动态查询（`@RawQuery`/`SimpleSQLiteQuery` 全部 16 处）和全文搜索，各用固定合成数据录下输入 → 结果行；全文搜索要覆盖中文、多关键词、标点、无结果。
   - **备份恢复**：用现在的实现做一份备份，存为夹具（合成数据，不含任何真实内容和密钥）。
3. 第一段交付：`docs/任务卡/175-交付说明.md` 写可行性结论、驱动推荐、改动清单、夹具清单；提交夹具和录制用的测试代码；**然后停下**，不要开始第二段。
