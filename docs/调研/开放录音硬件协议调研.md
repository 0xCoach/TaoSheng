# 开放录音硬件协议调研

调研日期：2026-11-09。对象：录音卡、吊坠、手表与 DIY 录音板接入安卓 App。本文是调研与设计建议，不是已发布规范，也未进行硬件实测。引用均为官方资料、规范或项目作者维护的源码；“未找到公开资料”表示本次检索未取得证据，不代表绝对不存在。

## 一页结论摘要

**推荐：制定独立、精简的开放应用协议，复用蓝牙官方基础服务；借鉴 Omi 和声云，但不把任何一家现有协议原样定为标准。** 新硬件实现统一协议即可被通用客户端发现和接入；旧设备通过单独兼容层接入，不能承诺无需适配就支持所有存量产品。这是对下述证据的综合判断。

| 决策 | 结论与依据 |
| --- | --- |
| 优先研究谁 | **Omi** 最适合研究开放固件、实时音频与能力声明；**声云**最适合研究国内录音卡控制、断点下载与跨平台接入。两者均有可读协议/实现，但离线数据结构、授权边界与版本处理不同。[Omi 协议](https://github.com/BasedHardware/omi/blob/main/sdks/device/PROTOCOL.md)、[声云仓库](https://github.com/SonicloudTech/sonicloud_opensdk) |
| 是否已有可直接采用的统一标准 | 本次未找到同时覆盖“实时录音、离线补录、安全导入确认、设备授权”，且有跨厂商采用证据的完整开放标准。蓝牙 OTS 已覆盖对象传输的一部分，仍需补录音业务语义。[OTS 规范入口](https://www.bluetooth.com/specifications/specs/object-transfer-service-1-0/) |
| 商业吊坠/录音卡是否封闭 | 需区分：Limitless、Bee 有官方云端数据接口；Plaud 已有官方设备 SDK。它们都不能据此认定为允许任意硬件实现的开放线级协议。[Limitless](https://www.limitless.ai/developers)、[Bee](https://docs.bee.computer/docs/api)、[Plaud](https://dev.plaud.ai/device-sdk) |
| BLE 能否实时传声音 | **压缩语音可行，全天稳定性需实测。** 建议起步参数为 Opus、16 kHz、单声道、20 ms、16–24 kbit/s；离线缓存必须补偿断连。Omi 已有类似实现，蓝牙厂商也提供吞吐测试资料；无线标称速率不能当作手机持续吞吐保证。[Omi](https://github.com/BasedHardware/omi/blob/main/sdks/device/PROTOCOL.md)、[Nordic 吞吐资料](https://docs.nordicsemi.com/r/bundle/sds_s145/page/sds/s1xx/ble_data_throughput/ble_data_throughput.html) |
| 手表是否能统一接入 | 优先选可安装完整安卓应用的国内 OPPO 全智能表做验证；华为走目标型号开放能力与 Wear Engine；小米必须逐型号看表：当前 Vela 录音接口表仅 S5 标为支持，S4/S3、REDMI Watch 5/6 等标为不支持。不能按品牌整体承诺。[OPPO](https://open.oppomobile.com/new/introduction?page_name=wearabledevice)、[华为](https://developer.huawei.com/consumer/cn/doc/doccenter-multi-device/bpta-smartwatch/)、[小米录音支持表](https://iot.mi.com/vela/quickapp/zh/features/system/record.html) |
| 标准怎么推广 | 先交付“公开规范＋参考固件＋通用客户端＋自检工具＋型号/固件兼容表”，再考虑品牌认证。以两个独立硬件实现、两个独立客户端互通作为 1.0 发布门槛。这是借鉴 VIA、IPP Everywhere 与 Matter 的运营建议，非现有要求。 |

**第一版范围建议：** 发现、物理确认绑定与撤销、设备信息和能力清单、录音控制与状态、对时、实时音频、离线文件/记录同步、完整性校验、持久导入确认、错误码、版本与厂商扩展。实时与离线分为可选能力，但只要声明离线同步，就必须遵守安全回收规则。Wi-Fi 大文件传输、固件升级和 LE Audio 放到可选扩展，避免第一版过大。

**最关键的原则：** “蓝牙已发送”“App 收到”“App 安全保存”是三件事。设备只能根据最后一种确认回收相应录音；不得将转写完成或云端成功作为本地安全保存的必要条件。存储满时也要有明确策略，不能悄悄覆盖未确认数据。此为本报告的协议设计建议。

## 1. 现有录音硬件协议：公开到哪一层

### 1.1 Omi（原 BasedHardware/Friend）

**公开程度与许可。** 主仓库包含硬件资料、固件、App、设备 SDK 和 BLE 协议，根许可证为 MIT；使用具体硬件设计、依赖库时仍须检查相应目录的声明。这里的旧仓库名 Friend 指 BasedHardware 项目，不能与独立商业产品 friend.com 混为一谈。[主仓库及许可证](https://github.com/BasedHardware/omi)、[许可证原文](https://github.com/BasedHardware/omi/blob/main/LICENSE)

**BLE 与实时音频。** 自定义服务提供音频通知和编码读取，另复用标准电池服务；设置、能力位、对时也有单独服务。音频通知含 3 字节包头；固件实现为 16 位小端包序号＋1 字节分片序号，后接编码数据，并非绝对时间戳。Opus 编码号 20 对应 10 ms，21 对应 20 ms，不能只写“支持 Opus”就假设帧时长相同。解码输出为 16 kHz、16 位、单声道 PCM。[协议原文](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/sdks/device/PROTOCOL.md)、[传输源码](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/omi/firmware/omi/src/lib/core/transport.c)

**离线同步。** 支持，但各代实现不同：CV1 使用无文件系统的循环存储，每条记录 444 字节，按读写序号同步；DevKit 有独立的基于文件的 SD 实现。因此不能把“支持离线”理解成统一文件列表协议。最新源码出现 INFO、READ、ADVANCE、带存储实例标识的 ADVANCE_ID，以及导入保管能力位；同一快照的 README 仍描述读取发送完成后自动推进、满盘覆盖，并称仅由 App 确认回收属于后续约定。**文档与代码存在演进差异；已发布固件实际启用哪些行为，未在本次实测确认。**[存储说明](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/omi/firmware/readme.md)、[存储源码](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/omi/firmware/omi/src/lib/core/storage.c)、[保管能力声明](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/omi/firmware/omi/src/lib/core/custody.h)

**采用情况。** 可确认官方 DevKit 与 CV1 等实现；未找到经验证的第三方同协议量产品牌/克隆品数量。Omi App 源码同时包含 Bee、Plaud、Limitless 等连接器，但这是分别适配，不能算这些厂商采用了 Omi 协议。[设备类型与连接器](https://github.com/BasedHardware/omi/blob/b00957395ff21b5f6758dd0c57680729b6128d9d/app/lib/backend/schema/bt_device/bt_device.dart)

**判断：** 最值得借鉴，也适合先做兼容验证；不宜直接把其当前固件约定升级为跨厂商标准。尤其应独立明确授权、时间戳、离线对象与安全回收规则。

## 2. 蓝牙官方标准：哪些直接用，哪些留作扩展

| 标准 | 能解决什么 | 对本项目的建议及原因 |
| --- | --- | --- |
| 电池服务 BAS：`0x180F`，电量 `0x2A19` | 标准电量读取/通知。 | **直接复用基础电量字段**；充电与健康等高级项按版本/能力可选。[BAS](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/BAS_v1.1/out/en/index-en.html) |
| 设备信息服务 DIS：`0x180A` | 厂商、型号、固件/硬件版本等。 | **直接复用**；协议能力清单另定义，避免把厂商名当作功能判断条件。[DIS](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/DIS_v1.2/out/en/index-en.html) |
| 当前时间服务 CTS：`0x1805` | 公开当前日历时间。 | 可选复用；实时音频仍应使用单调采样计数，并另有 UTC 映射、误差和重启标识。CTS 本身不是录音连续时间轴规范。[CTS](https://www.bluetooth.com/specifications/specs/current-time-service-1-1/) |
| 对象传输服务 OTS：`0x1825` | GATT 管理对象，经独立 L2CAP 面向连接通道传内容；有偏移读取、对象管理与可选校验。 | **值得做可选文件传输配置，不宜强制第一版。** 安卓 API 29 起有 LE L2CAP 通道，但 App 仍要实现 OTS 状态机；它不自动提供录音时间轴、归属授权、持久导入确认。需测目标手机与固件栈，不可直接断言“安卓不支持”。[OTS](https://www.bluetooth.com/specifications/specs/object-transfer-service-1-0/)、[安卓 L2CAP 接口](https://developer.android.com/reference/android/bluetooth/BluetoothDevice#createL2capChannel(int)) |
| LE Audio | 用 LC3 和等时通道提供音频；含能力发现、流管理、麦克风控制。 | 可作为未来系统音频输入路径；**不是 GATT 上传 Opus**，也不含离线文件同步。手机、控制器、固件与系统音频路由均需支持，不能仅看“蓝牙 5.x”或手机有 BLE 就保证兼容。[官方规范族](https://www.bluetooth.com/learn-about-bluetooth/feature-enhancements/le-audio/le-audio-specifications/) |
| Auracast（广播音频） | 一路音频广播给多个接收端，可用于话筒、公共播音。 | 不作为个人录音同步主路径：广播不提供逐个 App 的接收确认、断点文件和设备归属流程；手机扮演广播助手也不等于能让普通 App 取得录音流。此为依据其广播架构作出的判断。[SIG 架构说明](https://www.bluetooth.com/wp-content/uploads/2024/05/2505_Paper_An-Overview-of-Auracast.pdf) |
| ASHA（助听器音频） | 安卓向助听器输出音频，使用 LE 通道、G.722 16 kHz。 | 不适合：主要方向是手机→助听器，不是外部麦克风→App；也不负责录音文件。[AOSP 规范](https://source.android.com/docs/core/connect/bluetooth/asha) |
| HFP（免提通话） | 手机和耳机/车载免提的通话音频与控制。 | 可用作已有蓝牙耳机的录音输入，但不推荐做全天录音协议底座：走系统通话音频路由，受电话优先级、协商编码及系统限制影响，无文件同步；不能笼统说所有 HFP 都只有 8 kHz，版本/编码能力不同。[HFP](https://www.bluetooth.com/specifications/specs/hands-free-profile/)、[安卓 SCO 行为](https://developer.android.com/reference/android/media/AudioManager#startBluetoothSco()) |

推荐让硬件作为 BLE 外设（提供服务），手机作为中心设备（扫描和连接）。基础传输优先 GATT 通知，OTS/L2CAP、Wi-Fi 均复用同一录音对象标识与导入确认，避免每条传输路线长成一套业务协议。此为设计建议。

## 3. 国内录音卡/录音笔方案

### 3.1 芯片与“公版协议家族”

本次没有取得国内录音卡各芯片的可核实市场份额，不能给出占有率排名。以下区分“芯片有录音能力”“厂商有 SDK”“不同品牌确实共用完整协议”。

### 3.2 声云 sonicloud_opensdk：能否文档化

**能，而且已经部分文档化。** 桌面端目录有 `docs/协议.md`，说明 CB08 的 GATT、命令、CRC、文件列表与真机差异；这比只有 AAR 更便于形成互操作说明。[固定提交的协议文档](https://github.com/SonicloudTech/sonicloud_opensdk/blob/478e54262e5e2a04f2ab397766065cacbb381e83/pnote-web-win%26Mac-demo/docs/协议.md)

已核实的关键点：

- 服务 `0xAE20`；`AE21` 无响应写入，`AE22` 数据通知，`AE23` 按键/状态通知。
- 通用帧：`0x5A + SEQ(1B) + CRC(2B) + LEN(2B) + TYPE/CMD/参数`；CRC 为 CRC-16/XMODEM。帧头用小端，文件列表部分字段用大端。
- 支持录音开始/停止/暂停、时间、电量、容量、文件列表、偏移下载、取消和删除。下载偏移为 4 字节小端。
- 公开记录显示 CB08 文件请求完整帧 36 字节必须单次 GATT 写入，拆为 20＋16 会失败；长文件名、列表完成标志、容量单位还有固件差异。新标准应避免继承这些例外。

以上均来自[CB08 协议原文](https://github.com/SonicloudTech/sonicloud_opensdk/blob/478e54262e5e2a04f2ab397766065cacbb381e83/pnote-web-win%26Mac-demo/docs/协议.md)。README 另说明 SDK 回调音频为裸 Opus，基本参数 16 kHz、单声道、40 字节/20 ms；这是该方案参数，不能把 40 字节固定长度强加给所有 Opus 实现。[接入说明](https://github.com/SonicloudTech/sonicloud_opensdk/blob/478e54262e5e2a04f2ab397766065cacbb381e83/README.md)

**不能直接升级成通用开放标准的原因：** 仓库明确仅示例代码以 MIT 发布；AAR、静态库、HAR、固件、私有协议及部分文档可能专有，商用/再分发范围另有约定。当前公开命令有“删除”，但未找到设备强制执行“App 已持久导入才允许删除”的完整契约。[许可边界](https://github.com/SonicloudTech/sonicloud_opensdk/blob/478e54262e5e2a04f2ab397766065cacbb381e83/README.md)

建议先整理“CB08 已公开互操作说明”，将公开事实、实测差异和待厂商确认项分开；将其协议文字、编号或专有行为纳入对外开放规范之前，应获得权利人的明确开放许可。新标准可以借鉴分层、下载与校验思路，不必继承其 UUID、命令编号和历史兼容包袱。

## 4. 手表：按系统、型号选择路径

“能安装第三方应用”“应用能用麦克风”“能在后台持续录音”“能开自定义 BLE 服务”是四个独立条件。系统内置录音机存在，也不证明第三方拿得到同样能力。

| 先例 | 一手资料中的做法 | 可借鉴点（本项目建议） |
| --- | --- | --- |
| VIA 键盘定义 | JSON 定义描述型号与功能，利用厂商/产品标识匹配；V3 支持模块和自定义菜单。[定义规范](https://caniusevia.com/docs/specification/)、[配置约定](https://caniusevia.com/docs/configuring_qmk/) | 用机器可读能力清单，基本功能由通用 App 自动生成；厂商扩展只增补功能。基础能力直接从设备读，不能依赖联网下载型号定义才能录音。 |

| IPP Everywhere | 规定最低共同能力，并有公开自认证工具、结果提交与型号列表流程。[标准与工具入口](https://www.pwg.org/ipp/everywhere.html)、[自认证工具](https://istopwg.github.io/ippeveselfcert/index.html) | 发布“必需能力＋可选能力”的测试套件和可重复报告，记录具体型号/固件/测试版本；区分厂商自测与独立互测，不用一句“兼容涛声”代替证据。 |
| Health Connect（健康连接） | 按系统/服务可用性检测，以统一数据类型和用户授权共享数据。[官方说明](https://developer.android.com/health-and-fitness/health-connect/availability) | 音频、控制、删除分权限；先查能力，再显示功能；撤销授权立即生效。它是 App 数据平台，不负责硬件发现和 BLE 音频，不能直接拿来接录音卡。 |

建议的具体制度：

1. **版本：** 0.x 为草案；1.x 只做向后兼容的新增字段/能力，破坏性变化升主版本。未知可选字段应忽略，未知必需能力应明确拒绝，编号不得改义复用。
2. **能力：** 分“实时流”“离线同步”“Wi-Fi 加速”等配置。App 根据声明运行，不按品牌分支判断；声明了某能力，就必须通过该能力全部强制测试。
3. **扩展：** 公开厂商命名空间登记表，扩展有长度、版本、权限；不得改变核心命令的含义，不得要求私有扩展才能完成基础导入。
4. **认证/自检：** 工具覆盖发现、授权拒绝/撤销、分包、丢包、断电断点、重复请求、校验失败、导入确认丢失、存储满、多客户端争用。报告应可脱敏分享。自检通过不等于蓝牙 SIG 认证。
5. **治理：** 公开提案、议题和决策记录；1.0 前至少两家独立硬件实现、两个独立 App 互通；由硬件方、App 方共同评审，涛声不保留私有解释权。
6. **许可：** 单列规范文字、参考代码、测试向量、硬件图纸、商标的授权；写明实现/分发权及专利贡献规则。规范阅读免费不等于实现权清楚，参考代码开源也不等于硬件或商标开源。

以上六项为基于前述先例提炼的运营建议，并非这些项目共同采用的原样制度。

## 6. 安卓端关键限制与链路参数

### 6.1 后台连接与前台服务

- **接收外部 BLE 字节：** 长连接优先采用 `connectedDevice`（连接设备）前台服务，或评估 `CompanionDeviceService`（伴生设备服务）。进程被杀后 GATT 会断，WorkManager 不提供永不间断的实时连接保证。[官方后台 BLE 指南](https://developer.android.com/develop/connectivity/bluetooth/ble/background)
- **启动与权限：** Android 12 起限制从后台启动前台服务；Android 14 起要声明对应服务权限和类型。扫描/连接需要相应蓝牙权限；Android 12 以上不应一律额外索取定位权限，`neverForLocation` 是否适用需按实际用途决定。[服务类型](https://developer.android.com/develop/background-work/services/fgs/service-types)、[蓝牙权限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)
- **同时录手机麦克风：** 还要符合 `microphone` 服务类型与 `RECORD_AUDIO` 的使用中权限限制；单纯收 BLE 数据不能自动等同手机麦克风采集。不要把全天 BLE 连接统一登记成 `dataSync`：面向 Android 15 以上的该类型另有时间限制。[服务类型原文](https://developer.android.com/develop/background-work/services/fgs/service-types)

### 6.2 吞吐预算与建议

以下是**估算与初始调参建议，不是实测保证**。取 20 ms 一帧、50 帧/秒：

| 内容 | 净音频速率 | 量级含义 |
| --- | ---: | --- |
| 16 kHz、16 位、单声道 PCM | 256 kbit/s，即 32 KB/s | 对省电链路压力较大。 |
| Opus 16 kbit/s | 40 字节/帧，即 2 KB/s | 若每帧再加 16 字节协议头，约 2.8 KB/s，尚未计蓝牙开销。 |
| Opus 24 kbit/s | 平均 60 字节/帧，即 3 KB/s | 同样假设下约 3.8 KB/s；变码率还须约束最大包长。 |

公式为“采样率×位深×声道”或“编码码率÷8”，不是要求 Opus 帧永远等长。Omi 和声云的公开实现证明该量级具备实践基础；能否在锁屏、遮挡、Wi-Fi 干扰下连续一天稳定运行，仍需手机与固件实测。[Omi 编码约定](https://github.com/BasedHardware/omi/blob/main/sdks/device/PROTOCOL.md)、[厂商吞吐测试条件](https://docs.nordicsemi.com/r/bundle/sds_s145/page/sds/s1xx/ble_data_throughput/ble_data_throughput.html)

建议起点如下，最终以协商结果和功耗测试为准：

- **MTU（单次传输大小）：** 争取 ATT MTU 247，通知可用 244 字节；支持更小 MTU 的分片，控制/发现保留默认 MTU 23 的可用路径。Android 14 起首次请求会由系统请求 517，之后请求被忽略，因此不得硬编码手机一定协商到 247。[安卓 MTU 接口](https://developer.android.com/reference/android/bluetooth/BluetoothGatt#requestMtu(int))
- **连接间隔：** 活跃流先测 15–30 ms，活动传输时外设延迟先取 0；批量同步按需要申请高优先级。不要把 7.5 ms 当作唯一正确值，更短未必更省电或吞吐更高；手机可以调整参数。[Nordic 参数说明](https://academy.nordicsemi.com/courses/bluetooth-low-energy-fundamentals/lessons/lesson-3-bluetooth-le-connections/topic/connection-parameters/)
- **链路：** 支持时启用数据长度扩展和 2M 物理层，必须允许回退 1M；不把 2M 列为基础接入条件。[Nordic 链路说明](https://academy.nordicsemi.com/courses/designing-low-power-bluetooth-le-products/lessons/lesson-7-remote-monitoring-of-bluetooth-le-devices-with-nrf-cloud/topic/key-data-points-for-bluetooth-le-connection-stability-and-power-efficiency/)
- **可靠性：** 实时通知带序号、时间和分片标识；接收落盘与解码解耦；文件传输有窗口/流控和断点。蓝牙链路可靠不等于 App 已落盘，离线副本只按持久确认回收。这是本报告的协议建议。

### 6.3 国内系统影响

| 系统 | 有依据的限制 | 应对建议 |
| --- | --- | --- |
| ColorOS | 存在应用后台活动/电量管理设置；OPPO 官方支持页介绍按 App 管理后台耗电，但未找到面向所有版本的 BLE 永久保活承诺。[官方支持](https://support.oppo.com/en/answer/?aid=2171043) | 按目标版本提供后台权限引导；用锁屏长测判断，不承诺开启一个开关即可全天不断。 |
| HyperOS/小米 | 官方提供后台自启动开关，说明其与后台运行、性能及耗电相关。[小米说明](https://www.mi.com/global/support/faq/details/KA-507608/) | 检查自启动与电池限制，测试进程回收后的恢复；本次未验证小米 14 Pro 上的具体表现。 |
| HarmonyOS | 新系统有独立后台任务体系；官方 BLE 示例明确提到后台冻结造成断连，并通过 `bluetoothInteraction` 长时任务处理。[华为方案](https://developer.huawei.com/consumer/cn/doc/doccenter-industry-solutions/btreconnectdemo-0000002757080811/) | 区分仍能运行 APK 的旧系统和原生 HarmonyOS：后者需原生客户端及其后台能力，不能套用安卓前台服务。对目标版本按官方约束做重连与提示。 |

因此硬件必须能独立录音、断连缓存和重连补传。建议后续验证覆盖锁屏、省电、来电、蓝牙开关、超距、App 被回收与手机重启；当前只调研，未操作手机或进行这些测试。

## 附录 A：第一版协议的建议骨架

以下均为**建议设计，尚未分配 UUID 或冻结字节格式**；不是对现有协议行为的描述。

| 模块 | 建议的最低约定 |
| --- | --- |
| 发现 | 自有 128 位服务 UUID，广播主版本与少量功能位；名称只供展示，不作身份认证。避免照抄厂商短 UUID 当作自有标准编号。 |
| 授权 | 首次绑定需物理按键或设备提供的带外凭据；明确定义配对、链路加密、设备归属与应用授权的区别。无屏设备不能仅因手机连上就开放录音和删除。允许撤销、换机及恢复出厂。 |
| 信息/能力 | 复用 BAS/DIS；核心服务读出协议主次版本、编码/采样率/帧时长/最大帧、实时/离线能力、容量、最大块、并发限制、时钟状态。厂商信息不能替代能力。 |
| 控制 | 独立控制写入、结果/事件通道；请求号、明确错误码、超时重试与幂等语义。分清“开始录音”“订阅实时流”“停止采集”“静音”。 |
| 时间 | 录音会话标识＋启动标识＋单调采样计数，建立 UTC 映射并报告时钟误差。对时不得让正在录音的时间轴倒退；未知时间不能伪造为精确 UTC。 |
| 实时音频 | 基线 Opus 16 kHz 单声道、20 ms；声明可变帧长上限。区分帧序号与分片序号；明确字节序、长度、分片结束、丢帧处理；不把解码缓冲容量当线上帧大小。 |
| 离线对象 | 同时容纳“文件”与“循环存储记录段”，统一不可变对象标识、版本、范围、音频格式、时间、长度和摘要。分页列表必须有明确结束与快照语义，不能用静默超时猜列表完整。 |
| 下载/续传 | 对象标识＋对象版本＋字节偏移＋长度；定义分块校验、流控、取消、并发与错误。文件未封口/内容变化时，旧偏移必须可检测失效。 |
| 完整性/导入确认 | 整体 SHA-256；App 校验长度、摘要与音频结构后，将音频和索引持久保存，再发“已导入”确认。确认绑定设备/对象/版本/摘要；重复确认无害，确认丢失可重发。CRC 可测误码，不替代摘要或授权。 |
| 删除/满盘 | 导入确认使指定对象具备回收资格，删除结果可查询；默认不得回收未确认内容。满盘停止/告警；若提供覆盖模式，必须显式启用并留下缺口记录，且不得宣称无损同步。 |
| 扩展/传输 | 厂商命名空间、可忽略扩展、必需扩展标记；Wi-Fi 复用 BLE 已授权会话，以加密认证通道传同一对象，不能因切 Wi-Fi 而放开访问或绕过确认。 |

建议拆为“公共核心＋实时配置＋离线同步配置”，以便无存储的 DIY 板和只传离线文件的录音卡均可声明兼容；客户端明确展示所支持配置。是否强制所有量产设备同时支持实时和离线，应作为 0.x 草案的产品决策，不在本调研中假定。
