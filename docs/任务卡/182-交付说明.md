## 本机基准

代码：`app/src/test/java/app/resound/data/TableObservers182Benchmark.kt`。Robolectric + 生产 Room DAO / AndroidSQLiteDriver，合成内存库；并存被审计的常驻查询，包括未改的小表和聚合。测的是查询链路，未启动录音、模型、网络和 WorkManager 执行器。首次引导已完成，无打开界面、无待整理专题、无检查点文件；专题有任务 / 迟到原话另由对照测试覆盖。

- 初始 20,000 段、30,000 环境音、100 日 ASR 用量；其余历史表为空。每轮新增一段、保存一条环境音，再在事务内完成转写、写原话 / attempt / 用量，共 50 轮。
- 每次写入后等有关 DAO 查询消费完；不会用调度合并掩盖读放大。次数含首次查询，统计点在 `distinctUntilChanged` 之前。
- `env_sounds.segmentId` 为一对一主键外键，因此正常库不能在 20,000 段下有 30,000 环境音。仅此压力库在种子写入前关闭外键，额外 10,000 条为独立历史压力行；所有行为对照测试保留正常外键。这不是生产数据分布。
- 下表“延迟”为从提交前到 DAO 返回的累计墙钟时间，含等待，多个订阅重叠，不能相加当 CPU 时间。原始报告同时保留各 SQL 的 step 到 close 耗时（含实体映射）。

最终完整基准：返回 **9,626,676 → 356 行**；写入阶段 **17,004 → 644 ms**，减少 **96.21%**。改前 SQL 累计耗时占比：四个 segments 整表读合计 44.32%；环境音整表读 8.03%；ASR 历史用量 5.88%；既有未整理计数 18.42%；既有多人提示 22.64%；其余约 0.71%。这些数值也包含语句存活期间的等待，不能视为 CPU 热点百分比。四个相同 segments SQL 只能共同归因，不能凭该数据分别断言 CPU 占比。

## 索引与仍有的扫描

完整计划见 `182-基准/query-plans.txt`，脚本仅按提交的 schema 33 创建合成内存库，使用本机 SQLite 3.53.4；不是 Android 真机计划。AndroidSQLiteDriver 对 EXPLAIN 的分类不支持此次诊断，已移到独立脚本，未修改驱动或夹具。

| 查询 | 现状 / 后续建议 |
|---|---|
| 队列计数、声纹计数、Failed 筛选 | 缺 status 索引，仍扫描 segments；已消除整表对象构建。建议 Claude 另卡评估 `segments(status, voiceprintProcessedAt)`，队列可改为带 status 条件的聚合后利用该覆盖索引。 |
| ASR 累计用量 | SUM 全部日记录仍扫描 asr_usage；返回一行。覆盖索引只能减轻读列，不能消除累计求和，是否维护累计值另评估。 |
| 近期 Done、日录音、日环境音、事件范围 | 使用已有 startAt 索引。相交查询只有起点上界，仍可能检查较多旧索引项，不能随意加起点下界而漏掉跨日长段。 |
| 专题当前 / 待处理 ID | 使用 topics(status)。 |
| 专题进度 | 显式先取 topic_spans(topicId)，再用已有 segments(startAt) 范围索引，避免优化器为按 ID 排序选择扫整表；未创建新索引。 |
| Done 迟到原话探测 | topics(status)、topic_spans(topicId)、transcript_lines(segmentId) 可用；缺原话 startAt 索引，计划可能构建 status 自动索引，仍可能扫较多行。建议另卡评估 transcript_lines(startAt, segmentId) 及真实负载。 |
| 导入待整理 | import_records 的待处理条件无专用索引，仍扫描记录索引；录音关系使用 segments(importRecordId)。建议另卡评估待处理复合 / 部分索引。 |
| 今日 LLM 用量、环境音音频路径 | 分别使用 llm_usage_v2(day,purpose) 主键前缀和 env_sounds 主键。 |

Room 仍按表失效，聚合可能重新执行；结果相等时不再向下游重算。没有新增 debounce 延迟。同步展示适配仍须维持“事务外调用”的边界；未来若改为挂起导出接口，应由独立卡调整契约。
