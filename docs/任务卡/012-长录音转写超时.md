# 任务卡 012：长录音转写超时 + 真实进度

## 现象（10-23 真机）

- 改用普通麦克风音源后，长片段变多。**≤49 秒的片段全部转写成功；≥约 60 秒的反复“转写超时”**，卡在队首，后面 36 段跟着积压。
- 例：片段 id 93（65 秒、277 KB，已尝试 2 次）、id 132（96 秒、413 KB）。单段上限 5 分钟（`CaptureTuning.MAX_SEGMENT_SAMPLES`）。
- 现行实现：`DoubaoAsrProvider` 把 OGG 按页快速发送到 `bigmodel_nostream`，每请求总超时 90 秒（`DoubaoConfig.timeoutMillis`）。卡 002 实测 40 秒音频约 6.4 秒出结果。
- 进程被杀时片段停在 `Running`，界面一直显示“转写中”，直到下一轮任务才恢复。

## 要做的

1. **复现并定位**（不要用负责人的私人录音）：在 `tools/asr-probe/` 用 macOS `say` 合成 70 秒、150 秒、290 秒三段中文语音，转成与 App 相同的 OGG Opus（16k 单声道，参考 `SegmentEncoder`），用与 App 相同的协议发送，记录：发完用时、收到最终包用时、是否超时、服务端是否按实时速度处理。音频总量控制在 **10 分钟以内**（豆包流式 2.0，约 1 元/小时）。密钥只让脚本从 `/Users/coach/Developer/anti-scam-granny/API Key.md` 读取，不得输出。
2. **修复**（按实测选一种或组合，交付说明写理由）：
   - 超时按音频时长计算（如 `30 秒 + 时长 × 系数`），不要一刀切 90 秒；
   - 若服务端对长音频需要接近实时的节奏，启用 `paceMillis` 合理节流；
   - 或把超过某长度（如 45 秒）的片段在上传时切成几段按顺序识别，再按时间偏移合并句子（保持绝对时间正确、speakerTag 在各子请求内独立，写进说明）。
   修完后 5 分钟片段也必须能转写成功。
3. **超时不该反复耗次数**：同一段因超时失败时，下一轮先处理其他段（不要卡在队首挡住后面），但仍保留重试。
4. **真实进度**：`TranscribeContract.TranscribeQueueState` 已新增 `runTotal` / `runDone`（Claude 已加，不要改签名）。每轮开始时 `runTotal` = 本轮要处理的段数，每处理完一段（成功/没文字/失败）`runDone`+1，结束后两者归 0。
5. **启动时恢复卡住的 Running**：App 启动时（`ResoundApp` 装配后、无转写任务在跑时）把残留的 `Running` 改回可重试状态，避免界面一直显示“转写中”。
