## 数据库及恢复边界

- 数据库版本 **28 → 29**；新增 `digest_pending` 和删除来源时的清理触发器，注册 `MIGRATION_28_29`。已提交 Room schema 29；从版本 1、26 经统一迁移链到最新的两个测试通过。
- `digest_pending` 是本机提交队列，不纳入跨机备份。与 FTS/embedding、撤销快照、文件清理队列一起在表覆盖测试中明确分类；新增用户事实表时，测试要求显式决定备份策略。
- 成功提交会清理响应缓存；原话被删除或快照不再匹配时，旧响应作废，不用旧来源重建结果。新入库原话不会改变已缓存失败批次的边界。
- 恢复清空旧进程的整理进行中标记，避免它套用到恢复后的数据库。失败回滚还原该标记及其余本机设置。
- 回滚副本位于应用私有 `noBackupFilesDir/restore-journal`，包含原始数据库、相关文件和偏好；不上传、不进入导出备份。准备副本失败时，正式数据尚未开始替换。
- 回滚使用同文件系统 rename，成功恢复以 pending → done 为提交点。故障恢复后可继续使用旧数据，失败材料保留在 `backup-restore-failed` 供重新处理；下次失败时替换该材料。

## 仍需注意

1. 旧备份从未保存的环境音纠错，无法靠这次代码从旧文件中恢复；需要手机原数据库仍有该记录。
2. 本地永久无法写入时，没有可靠办法保证收到的结果跨进程保存；当前选择停止自动重发。手动重试可能再发生一次真实模型调用。连接中断、供应商未返回 usage 的实际账单不能由本地缓存完整还原。
3. 字符预算不是精确 Token 计数；超长单条原话保留原文并报错，不静默截断。推理模型保留单独上限，实际节省比例需看日常真实用量。
4. 回滚测试是隔离文件故障注入，不是真机磁盘填满或断电实验。若文件系统损坏到连回滚 rename 都失败，仍会阻止打开混合数据；不能在该情况下冒称已恢复成功。准备回滚副本需要额外存储空间。
5. 尚未安装手机。后续应在真机验收备份含纠错记录的往返、恢复后课堂模式、取消响应、超过五条批量删除、全天录音和后台任务；本轮构建/测试不替代这些验收。
