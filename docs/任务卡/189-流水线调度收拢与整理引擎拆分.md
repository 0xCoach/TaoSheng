## 为什么做

“什么时候转写、什么时候整理”现在有十几条入口，是一张张卡叠出来的：

- WorkManager：`transcribe-periodic`、`transcribe-now`、`transcribe-early`、`digest-periodic`、时间点兜底 `TIMED_GUARD`、时间点补漏 `TIMED_NOW`；
- 闹钟：间隔链、时间点精确闹钟；
- 进程内：心跳、亮屏、接电、打开 App（卡 188）；
- 回顾前整理（`TranscribeWork.beforeReview`）。

`TranscribeWork.kt`（362 行）同时管 Worker、调度器、流水线执行、模式表、跳过规则；卡 188 又加了 `PipelineInProcess`，靠 `app.digestRunner.last.value.second != null` 反推“整理是否需要用户处理”。诊断也有两份：`PipelineTimes`（30 条滚动，会被环境音日志挤掉）和 `PipelineDiagnostics`（7 天 2000 条）。改一处很难确定会不会影响别的路径；这些也是以后 iOS 要复用的核心流程。

`DigestRunner.run()`（344 行）一个方法里串着：读密钥 → 未保存回复重放 → 待整理缓存核对 → 进行中凭据（防重复付费）→ 分段分批 → 逐批调模型 → 保存 → 记录结果，返回值只有一个 `Boolean`。

## 目标

1. **一个调度入口**：所有触发都变成“给一次执行机会”，统一调用同一个入口（例如 `PipelineScheduler.offer(source)`），由 `:shared` 的 `PipelineDue` 决定跑不跑、跑哪种。系统任务和闹钟只负责叫醒，不再各带一套判断。
2. **一个流水线协调器（放 `:shared`）**：“转写 → 声纹 → 整理”的阶段顺序、跳过规则、结果汇总写成平台无关代码，阶段通过接口注入；不引用 `Context`、`ResoundApp`、`AppGraph`、WorkManager。安卓侧只做条件采样（网络、电量、发热）、唤醒锁、前台通知、系统调度。
3. **整理引擎拆分**：`DigestRunner` 的主流程能一眼读出业务顺序；纯规则进 `:shared/digest/core`（复用已有的分批、分段、窗口规则）。新增内部方法返回明确结果类型（例如 `DigestOutcome { Done, NothingToDo, Retryable(原因), NeedsUser(原因), Cancelled }`），`run(force, manual): Boolean` 保留为兼容包装。卡 188 的 `reportDigestBlocked` 反推写法改用这个结果类型。
4. **系统任务合并**：`transcribe-periodic`、`digest-periodic`、时间点兜底这三个周期任务合并成**一个**周期兜底（15 分钟，进程被杀、录音服务没开时用）；`transcribe-now`（手动、加急）和 `transcribe-early`（实时转写按段攒批）职责不同，保留。闹钟合成一条链：下一次闹钟 = 间隔整理与时间点整理里更早的那个到期时间。升级后取消旧的唯一任务名，不留重复。
5. **诊断合一**：一轮执行一行（时间、来源、模式、应到时间、等锁、各阶段耗时、结果、原因），保留 7 天、最多 2000 行；每天汇总一行（各来源次数、平均和最长迟到）。`PipelineTimes` 的 22 处调用改走新记录；环境音等非流水线日志不进这份记录。问题记录导出里只出现一节“自动转写/整理记录”。
6. **去掉卡号命名**：卡 188 尚未发版，现在改名不需要迁移。`pipeline-due-188`、`pipeline-triggers-188`、`periodic188`、唤醒锁 `resound:pipeline188` / `resound:pipeline-handoff188` 等改成按职责命名（如 `pipeline-schedule`、`pipeline-runs`、`resound:pipeline`）。测试文件名可以保留卡号。
7. **文件按职责分开**：`TranscribeWork.kt` 只留 Worker；调度器、安卓适配各自一个文件。不要逐方法拆类、不要造通用任务框架，能少一层就少一层。

## 必须守住（行为不变）

- **已排队的旧任务**：升级时手机里可能还排着旧的 WorkManager 任务（类名 `TranscribeWork`，带 `mode` 输入）。类名、包名不改；旧的 `MODE_*` 输入照常识别并转给新入口。
- 所有入口共用同一把流水线锁；拿锁后再判断一次；周期兜底撞锁直接成功、不退避；手动、实时、回顾前保持原来的重试行为。
- 时间点整理的完成凭据（`pendingTimed` / `completeTimed`，含 generation 隔离）语义不变；同一个时间点不会跑两次，也不会漏。
- 手动“现在整理”的 force / manual 区别不变；手动成功后解除错误锁定（卡 188）。
- 回顾前整理的 10 分钟超时（含等锁）不变。
- 实时转写的加急、攒批、亮屏/接电提升（`resumeWaitingBatch`）不变。
- 整理防重复付费：`inflight` 持久状态、`unsavedReply` 内存重放、`pendingDigest` 缓存核对、崩溃后人工重试例外、模型快照与备用模型实际来源、技能触发时机、事务与状态发布顺序完全不变。不能把“存在”当成“已保存”，取消后不能发布成功，不能新增吞错。
- 取消传播、`PipelineProgress.finish()` 在 finally、声纹稳定结果锁、阶段顺序不变。
- 卡 188 的到期规则（按上次尝试计、可重试失败 5→10→20 分钟封顶为间隔、密钥/余额错误按完整间隔再试、断网和撞锁不算尝试）不变。
- 不改数据库结构/SQL/版本、备份格式、网络层、`*Contract.kt` 与 `AudioSource.kt` 签名、依赖、版本号。
