# 卡 171：省电——各线程 CPU 时间统计（先量后改）

## 背景

负责人 11-12 要求在不影响质量的前提下继续省电。卡 164 已清掉界面外的定时轮询，剩下的开销集中在全天运行的录音主循环。现有耗电估算（`capture/AppPowerEstimator.kt`、`AppPowerEntity`，每 10 分钟一条）只记整个进程的 CPU 时间，分不清是哪条线程花的。本卡让后续省电卡（172 音量拆分、173 熄屏批量读、174 周期任务按需）有前后对比数据。

总原则：**只加统计，不改任何行为**。统计本身必须便宜（每 10 分钟一次，不新增定时器）。

## 要做

1. **采样**：在 `CaptureService.samplePower()` 现有的 10 分钟采样点（不新增循环），读本进程各线程的累计 CPU 时间（`/proc/self/task/<tid>/stat` 的 utime+stime，和 `/proc/self/task/<tid>/comm` 线程名；按时钟节拍换算成毫秒，节拍用 `Os.sysconf(OsConstants._SC_CLK_TCK)`）。读不到时整项留空，不能影响录音服务（全部 runCatching，放 IO 线程）。
2. **归并规则（纯规则，放 `:shared`）**：线程名按前缀归组，避免线程池编号把表撑大。至少分出：`capture-state`（录音状态线程）、主线程、`DefaultDispatcher`、IO 线程池（`DefaultDispatcher-worker` 无法区分 Default/IO 时合成一组并写明）、`AudioRecord`/音频相关、OkHttp、WorkManager、Room/数据库、binder、GC/JIT 等运行时线程（`HeapTaskDaemon`、`Jit thread pool`、`FinalizerDaemon` 等合成“运行时”）、其他。输入“线程名 + 累计毫秒”列表，输出“组名 → 毫秒”；再提供“两次快照相减得到这段时间各组增量”的函数（线程消失/新出现、计数回退都要算对，不出现负数）。放 `shared/src/commonMain/kotlin/app/resound/capture/`，不引用 `android.*`、`java.*`。
3. **存储**：不改数据库结构（不升版本）。把每次采样的分组结果追加到现有诊断/问题记录能带出的地方——先查清 `diagnostics` 包里问题记录是怎么收集文本的（例如 `PipelineTimes.record` 这类按行文件），沿用同一机制新增一个按行文件，每行：`时间戳 是否充电 是否亮屏 录音状态 距上次毫秒 各组增量毫秒`。文件要有上限（保留最近约 7 天或固定行数，沿用现有文件的滚动办法），并确认它会进“导出问题记录”。
4. **会进备份/隐私清理吗**：如果现有同类诊断文件不进备份，这个也不进；照现有同类文件处理，在交付说明里写明。

## 不做

- 不改 `ui/`、`MainActivity.kt`；不改 `*Contract.kt`、`AudioSource.kt` 签名；不改数据库结构；不升依赖。
- 不改录音读取循环、人声检测、切段（那是卡 173）。只在 `samplePower()` 里加一次调用。
- 不做界面展示。需要界面的话在交付说明里提，由 Claude 做。
