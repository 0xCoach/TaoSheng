# 卡 204 交付说明

A 和 B 各项均已实现。白天普通录音和转写引起的额外线索刷新，在本机一天的合成负载中从 600 次降到 0 次。删除前天的事件后，实跑排队的 Worker，测试接收端收到同一日期的新内容，其中已清除该事件。手机实际节电量留给负责人验收。

## A　先量，再改触发入口

改代码前，用库版本 40 的 SQLite 表和生产 DAO 查询做基线。历史放入三天共 900 段，当天再写 300 段，每段分别提交录音、转写，每十段产生一个事件。按两次提交相隔超过原有一秒防抖、上次工作已完成的节奏回放，排除启动校对。旧观察器对两个提交都刷新。600 次线索查询累计返回 1,862,130 行，单次 2,789～3,419 行，累计查询耗时 1.71 秒。手机提醒另读 692,730 行。由此确认，普通写入可以反复触发与本次写入规模无关的全量读取。

下表是第二组验证。在 Robolectric 的实际 Room 数据库按同样规模写入，按旧、新触发策略派发每个独立提交。使用一个已启用的 Markdown 文件夹通道，订阅整理结果和全部原话，关闭通道提醒。实际执行 DayThreadPushWork、SubscriptionRuntime、recordsChanged 和 PhoneReminders，HTTP 请求在本机拦截。历史段与日界线的摆放和首轮 SQLite 回放略有不同，表内两组输入一致。

| 实测指标 | 改前策略 | 改后策略 |
| --- | ---: | ---: |
| 白天普通写入引发的 refresh Worker | 600 次 | 0 次 |

### 普通变化与隐私变化

- 普通写入回到卡 200 之前的五张观察表。写 segments 不再唤醒记录订阅和手机提醒，写原话仍保留这两项原行为。日线索沿用凌晨 04:00 的定稿以及通道正常推送时机，继续使用原有三天修正期、历史确认状态和发送游标。
- 首页事件删除、导入记录删除和原话列表删除分别走 RoomPrivacyActions 的 forgetEvent、forgetSegment、deleteSegments。“这段别记”、指定时段、全量清除走 deleteRecent、deleteRange、deleteAll。它们汇合到 erase，数据库事务成功后明确发信号，覆盖只删录音、没有原话发生变化的情况。首页和条目页仍有直接调用 memory.deleteEvent 的入口，软删除事务提交后也排隐私刷新。
- 整夜删除、删除梦、夜间反馈选“不是”也走隐私队列。使用独立的联网工作链，删除立即排队并等待入队成功。已有任务读过旧快照时，新删除仍有后续执行机会。录音文件清理即使遇到调度异常也会执行。接收端更新时间仍受断网、系统后台调度和远端失败影响。
- 卡 200 原有 18 项测试全部通过，断言未改。新增测试实际写入 300 段和原话，普通观察没有排线索任务。前天的原话补齐并关联整理事件后，下一次 04:00 定稿出现该事件。相同数据的每日 Markdown 改前、改后 SHA-256 均为 `79c719316a5105c221db80b877e24933338c2d87158f674cc8053e659435c49e`。另一个用例先用 Worker 发送前天的事件，再通过真实删除入口提交，联网条件满足后驱动排队任务，10 秒测试时限内接收端完成清除。

### 凌晨高峰

只读核对问题记录。11 月 18 日 04:09 的十分钟采样中 Room 累计约 416 秒，05:09、05:19 已回落到约 10～11 秒，05:29 又升至约 152 秒。04:36 和 05:06 各有一次成功的整理任务。保留的最近 30 次推送均成功，但最早一条是当地 07:11，未覆盖该高峰。现有记录无法还原凌晨定稿的工作编号、重试次数或数据库线程各调用方占比。

排查中另复现一个会持续重试的条件。文件夹定稿会带上夜间周报，但 FolderSync 的路径白名单原先拒绝应用自己生成的“周报/年-W周数.md”，导致整个批次失败。先复现失败，再只放行固定文件名及 01～53 的周数，私有笔记和越界路径仍被拒绝。无法确认当晚已有符合条件的周报。

## B1　夜里按需识别

Full 模式以 2 秒为一窗。当前及前后各两窗都比背景低超过 1 dB，且未受正在进行的鼾声、咳嗽或最近阳性窗口保护时，才跳过 zipformer。邻窗不齐、遇到时间缺口或收尾时保守识别。跳过窗口仍按原时间顺序输入全零类别分数，保留声音包络与事件时钟。Deferred 继续使用原有候选选择和识别。

0 dB 候选在真实床旁样本中跳过了缺少咳嗽分数的窗口，不能通过硬门槛。收紧至 −1 dB 后，在卡 203 两组缺少咳嗽分数的记录中每个窗口都执行识别。用既有模型分数和生产检测器按流比较事件类别、起止时间、顺序及中断检测使用的逐窗鼾声标记，结果一致。

| 数据 | 2 秒窗口 | 跳过 | 事件对照 |
| --- | ---: | ---: | --- |
| 卡 202 连续鼾声、呼吸及背景压力集 | 2,608 | 160（6.13%） | 13 段鼾声，咳嗽 0；所有中断输入标记相同 |
| 卡 203 模拟中断 | 244 | 0 | 6 段鼾声、1 次中断，起止相同 |

合计跳过 160 / 5,483 窗（2.92%）。研究目录的一小时背景也用于卡 202，合计只计一次。卡 202 未保存半秒包络，核对的是所有可能影响中断判定的模型标记；逐条中断边界使用卡 203 的半秒数据验证。上述数字只代表这些评测输入。

## B2　夜里写库与个人判断

| 项目 | 实现与验证 |
| --- | --- |
| 会话 | 仍每 10 秒采集信号、更新内存。常规整份写库改为每 60 秒，进入、确认、结束、取消立即持久化或删除。合成的 18 个 pulse 只在 0、60、90（确认）、150 秒写入。从最后成功检查点到恢复、再到重入合并为一个未知缺口。恢复先于首个 pulse；隐私删除覆盖活动会话尚未写回的尾部。 |
| 声音包络 | 源码实际每个 5 秒点都重压整份。现在每点向 SQLite 追加峰值、中位数、背景三字节，正常结束统一压缩。64 次追加逐点读回均与原字节一致，结束时压缩结果也逐字节一致。当前版本同时能读旧 zlib 和中断时留下的追加格式；进行中新格式不提供降级到旧版读取的兼容保证。 |
| 鼾声中断去重 | 首次遇到中断只读取该夜已有起点，后续在内存判重，写库成功才记入。即时和周期处理重叠时由一条条件插入兜底。实库验证重复插入只留一条。 |
| 个人判断 | 对已整理之夜保存本次权重与反馈的判断标记。输入相同跳过，新增一晚只读新一晚，重新训练或改答后重判。测试中第二次维护读取特征 0 次，新增一晚只读取该晚 1 次。无有效模型时，一次性清理旧否决后直接返回。反馈条数不变但改答，未充电暂缓，下次充电重训。旧权重缺少答案快照时按训练后的新反馈兼容补学。 |
