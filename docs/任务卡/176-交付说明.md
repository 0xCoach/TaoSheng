## 停下来的具体原因与待审核方案

任务卡第 2 步明确要求：**“选一个不引入阻塞等待、不改变判断结果的接法”**，并规定 **“拿不准就停下问，不要用 runBlocking 糊过去”**；“不做”清单同时禁止修改 `*Contract.kt` 签名。这里按该停止条件执行，不是 Room/KSP 配置失败，也不是已经证明任何缓存方案都不可行。

已读到的调用关系：

- `app/src/main/java/app/resound/topic/TopicData.kt:72` 的 SQL 查完整历史时段；排除 Cancelled、Scheduled，但包括已结束、已完成专题；区间右端还可能由计划结束时间或最早时段加四小时决定。
- `app/src/main/java/app/resound/ResoundApp.kt:66` 将查询接到 `AndroidAsrSpeedSettings.topicTraining`；第 151 行另接转写器。
- `shared/src/commonMain/kotlin/app/resound/transcribe/AsrSpeedContract.kt:31` 是同步返回 Boolean 的既有约定。
- `app/src/main/java/app/resound/capture/SegmentFiles.kt:107` 和 `app/src/main/java/app/resound/importer/ImportSegments.kt:51` 通过该同步约定决定要持久化的 `separateSpeakers`；转写器也会重新判断培训归属。这会影响说话人区分结果，不能当作无关显示缓存。
- 既有 `Topic135Test.trainingUsesHistoricalSpansAndTopicSegmentsLeadTranscriptionCandidates` 明确要求：结束培训后，培训中的旧时刻仍返回不区分说话人，结束时刻则恢复正常。该测试本次只阅读，未计入已运行测试。

因此只缓存“当前是否培训”会直接改变历史录音判断。缓存完整历史时段虽能解决时间范围，但还需证明：进程启动首次读取前已加载；专题创建、剪时段、改类型、取消、删除后没有读到旧缓存的窗口；事务失败不会发布未提交数据。只订阅 Room Flow 然后同步读取 `.value` 不能自动提供这些保证。当前 `RoomTopicStore.transaction` 与仓库的通知流程也没有这样的同步缓存承诺。本次没有为回避问题新增常驻全表缓存、阻塞等待或隐含的默认 false。

**建议审核人确认的具体路线：**允许 `AsrSpeedSettings.effectiveSeparateSpeakers` 改为挂起函数；对应安卓实现及转写器接收挂起回调，保留原 SQL，通过原录音开始时间逐次查库。录音保存、导入保存和转写处理目前已有协程调用位置，但这仍涉及明确禁止自行改动的契约签名；`AndroidAsrSpeedSettings` 现有 `@Synchronized` 也不能包住挂起查询，需要另行确定设置快照与查询的顺序。此方案仅为待审核清单，未实施、未宣称等价。

另一条可审核路线是完整历史缓存，但需先明确首次加载屏障、所有写路径的提交与发布顺序及对同步消费者的保证，不能仅批准一个“当前状态”布尔值。请审核人裁定上述路线或提供已确认的接法；当前状态保持 BLOCKED。
