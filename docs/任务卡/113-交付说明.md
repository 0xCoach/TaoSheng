## 所有通道 × 格式核对

下表 `\n` 表示真实换行，`␠␠` 表示两个行尾空格。示例为 `甲\n乙\n\n- 一\n- 二`。这是最终请求的文字示意，客户端实测情况另列，不把请求正确等同于客户端验收。

| PushKind | Text：修前 → 修后 | Markdown：修前 → 修后 | Json：修前 → 修后 |
| --- | --- | --- | --- |
| PushPlus | txt 模板，原生 `\n` → 保持 | 单换行可能挤成一行 → `甲<br/>\n乙\n\n- 一<br/>\n- 二`，保留 Markdown 列表 | json 模板、结构化 envelope → 保持，字符串中的换行由 JSON 编码，不能注入 HTML |
| WeCom | text 原生 `\n` → 保持 | 当前 markdown 子集原生 `\n` → 保持；不塞入 HTML 标签 | 原有 Markdown 回退 → 保持原生 `\n` |
| ServerChan | 去除样式后也由 desp 的 Markdown 渲染，可能合行 → `甲␠␠\n乙` | 单换行可能合行 → `甲␠␠\n乙\n\n- 一␠␠\n- 二` | 原有 Markdown 回退 → 同 Markdown 硬换行 |
| Feishu | text 原生 `\n` → 保持 | interactive 卡片 markdown 组件原生 `\n` → 保持 | 原有 interactive Markdown 卡片回退 → 保持 |
| DingTalk | text 原生 `\n` → 保持 | 单换行可能合行 → 行尾两空格硬换行，空行、标题、列表保留 | 原有 Markdown 回退 → 同 Markdown 硬换行 |
| Telegram | 原生 `\n` → 保持 | HTML 模式：标题加粗、正文转义并保留 `\n` → 保持，绝不加 `<br>` | 原有 HTML 模式回退 → 保持 |
| Email | MIME text/plain 原生换行 → 保持 | 现有逐行 HTML `<br>`、标题/列表块元素 → 保持 | 原有 HTML 邮件回退 → 保持 |
| Notion | 原有分行 block → 保持 | 原有分行 block → 保持 | 原有 Markdown/block 回退 → 保持 |
| MarkdownFolder | 原有 .md 输出 → 保持 | 原始 Markdown 文件 → 保持，不加消息专用标签或行尾空格 | 原有 Markdown 文件回退 → 保持 |
| Webhook | text/plain 原生 `\n` → 保持 | text/markdown 的软换行 → 标准行尾两空格硬换行，按最终字节签名 | application/json envelope / memory 对象 → 保持，按最终 JSON 字节签名 |

补充：Text 延续原有去除 Markdown 样式的行为（含去除项目符号），条目仍逐行，不在本卡改纯文本协议；飞书、企业微信现用的 Markdown 子集不保证原生列表样式，保留 `- ` 作为逐行条目标识；Telegram 正文延续现有转义展示 Markdown 源文的行为，没有扩展格式转换范围。

## 主题覆盖

- 每日回顾：`DailyReview.pushBody` → `PushMessage.rendered` → 统一发送转换，新增用例验证摘要内多行及事项列表。
- 技能卡、普通提醒及测试消息：共用 `PushMessage.body` 发送入口，不依赖 topic 或标题。新增用例遍历 `PushTopic` 全部取值。
- 每周回顾、记录推送：当前订阅在 `MemoryFolder` / `SubscriptionRuntime.sendDocuments` 生成完整 Markdown，走文档通道、附件或 Webhook；原始文件和附件不转换，Webhook Markdown 在最终发送时处理硬换行。没有新增或改变主题路由。
- 待办/约定提醒：订阅的 `sendReminders` 也调用同一 `PushTransport.send`，内含换行同样处理。
- 全量记忆文档：Telegram 的 sendDocument、Email 的 .md 附件保持原字节；Notion/MarkdownFolder 保持原实现；Webhook 的 Markdown 文档在发送前处理硬换行，JSON 文档结构保持。
- 增量记录 JSON：Webhook 的 memory/delta envelope 不改结构。

## 文档依据

- [PushPlus 换行说明](https://www.pushplus.plus/doc/help/line.html)：txt 使用换行，Markdown 支持 `<br/>`。
- [PushPlus 消息接口](https://www.pushplus.plus/doc/guide/api.html)：JSON 可视化模板、异步受理与最终发送结果是不同阶段。
- [企业微信群机器人配置](https://developer.work.weixin.qq.com/document/path/91770)：保持现有 markdown 子集及其换行写法；本次官方站点抓取失败，未据此扩展到 markdown_v2。
- [Server酱格式说明](https://sct.ftqq.com/docs/getting-started/faq/)：desp 支持 Markdown、不支持 HTML。结合 [CommonMark 硬换行](https://spec.commonmark.org/0.31.2/#hard-line-breaks) 使用行尾两个空格，不照搬 SC3 的双回车规则。
- [飞书卡片 Markdown](https://open.feishu.cn/document/common-capabilities/message-card/message-cards-content/using-markdown-tags)（[官方 Lark 同文档](https://open.larksuite.com/document/common-capabilities/message-card/message-cards-content/using-markdown-tags)）：卡片组件支持 `\n`；有别于 post 消息里的 md 标签。
- [钉钉机器人常见问题](https://open.dingtalk.com/document/orgapp/faq-robot)、[钉钉官方 CLI 消息说明](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/skills/mono/references/products/chat.md)：行尾两个空格与真实换行组合。
- [Telegram HTML 模式](https://core.telegram.org/bots/api#html-style)：只用支持的标签，保留原有实体转义与长度处理。
