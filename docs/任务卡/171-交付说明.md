# 卡 171 交付说明

## 做了什么

- `shared/src/commonMain/kotlin/app/resound/capture/ThreadCpuRules.kt`：平台无关线程快照、归组和增量规则。先按 `tid:starttime` 身份相减，再归组；新线程和计数回退从零起算，消失线程不产生负数；线程改名不重复计算历史 CPU。
- `app/src/main/java/app/resound/capture/ProcThreadCpu.kt`：读取本进程 `/proc/self/task/<tid>/stat` 和 `comm`，使用 `Os.sysconf(_SC_CLK_TCK)` 把 utime + stime 换算为毫秒。以 stat 最后一个右括号定位字段，支持名称含空格/括号。主线程按 tid = pid 识别，不依赖其可能为包名的 comm。
- `app/src/main/java/app/resound/capture/ThreadCpuDiagnostics.kt`：IO 调度器内采样、滚动写入；`runCatching` 隔离系统读取、解析和文件失败，协程取消仍正常传播；Mutex 串行保护基线和文件读写，AtomicFile 原子替换。
- `CaptureService.samplePower()` 仅增加一次统计调用及一个服务实例字段。沿用每 10 分钟及原有服务启停采样，没有新增定时器，没有改读取循环、VAD、切段或调度规则。
- `diagnostics/LocalProblemReports.kt` 在已有问题记录文本中追加“各线程 CPU 时间”节，不需要界面配合。

未修改界面、约定签名、数据库结构/版本、依赖或构建配置。

## 文件和每行格式

本机文件：`context.noBackupFilesDir/thread-cpu.tsv`（一般对应应用私有目录 `no_backup/thread-cpu.tsv`）。沿用 `PipelineTimes` 的“追加后保留最近 N 行”方式，保留 **1008 行**；按 10 分钟一次约 7 天，频繁启停会缩短覆盖天数。文件读写沿用现有转写省电诊断的 AtomicFile 方式，单进程内用协程 Mutex。

每行 7 列，用制表符分隔，文件内不带表头；导出问题记录时附表头：

```text
时间戳ms    充电    亮屏    录音状态    距上次ms    各组CPU增量ms    采样状态
1794484800000    false    false    Listening    600005    capture-state=20;DefaultDispatcher/IO=340;运行时=10    ok
```

- 时间戳为 Unix 毫秒；间隔用 `elapsedRealtime()`，含休眠时间，不受改系统时间影响。
- 充电、亮屏为采样时的 `true/false`，未知为空；录音状态为现有 `CaptureState.name`。它们不能证明整个区间一直处于同一状态，启停采样也保持原有调用时的状态。
- 分组值是这段间隔的 CPU 毫秒；键只输出固定组名，不输出原始线程名、tid、包内原话或路径。
- 首次采样/服务重建、失败后首次成功为 `baseline`，增量列留空；正常为 `ok`；线程目录、任何 stat/comm、节拍读取失败或解析失败时整份快照为 `unavailable`，增量列留空，不输出不完整快照。
- 失败时清掉基线；恢复后须再等一次有效采样才能计算增量。写文件失败会丢掉该行并清基线，不影响录音，也不额外重试。

归组包括 capture-state、主线程、DefaultDispatcher/IO、显式 IO 线程池、音频、OkHttp（含 Okio）、WorkManager、Room/数据库、binder、运行时、其他。兼容内核 comm 的 15 字节截断，如 `DefaultDispatch`、`ReferenceQueueD`。Default 与 IO 共用协程线程，无法分别归因；无明确名称的 `pool-N-thread-M` 归“其他”，不猜测它是数据库或 IO。

## 从问题记录读占比

现有导出链路为 `LocalProblemReports.export()` → `CaptureStatsRepository.exportDiagnostics()`（含 `PipelineTimes.dump()` 等）→ 汇总为问题记录 txt。本卡在汇总文本内直接追加 `ThreadCpuDiagnostics.dump()`；仍经过现有隐私脱敏函数。

在“各线程 CPU 时间”节，仅选择 `ok` 行。某组在所选时段的 CPU 占比 = 该组增量总和 / 所有组增量总和；总和为零时无占比。某组占单核墙钟时间比例 = 该组增量总和 / 对应行间隔总和，多线程合计可超过 100%。缺失的组在有效行中视为零；空增量列不能视为零。前后对比须选择相似时长、充电/亮屏状态和业务负载。

这里是 **CPU 时间占比，不是电池耗电占比或 mAh**。不能覆盖麦克风、无线电、GPU/NPU 等能耗，也不包含 `:local_asr` 等其他进程。

## 备份与隐私清理

已检查 `PipelineTimes`、`TranscribePowerDiagnostics`、`BackupArchive`、`RoomPrivacyActions` 和 Manifest：

- 流水线诊断偏好不在 `BackupArchive.safePrefs` 白名单；转写省电文件在 noBackupFilesDir，也不进入应用备份。本文件同样不进入本机/云端应用备份或恢复，未扩大备份白名单。
- Manifest 的 `allowBackup=false`，本文件还位于系统不备份目录。
- 现有按时段/事件隐私清理针对录音、转写、事件及关联特征，不删除此类运行统计。本文件采用相同处理：不随时段/事件删除，按行滚动；清除应用数据或卸载时清除。仅保存固定分组数值和设备/录音状态，不保存原始线程名或内容。
- 用户主动导出问题记录时会带出这些统计；导出的 txt 与既有问题记录一样在 `cacheDir/problem-reports`。

## 开销估计和限制

每个既有采样点读取一次线程目录，每个线程读取两个小文件（约 2T 次打开/读取），归并与相减 O(T)，滚动文件处理最多约 1008 行。没有持续监视、额外唤醒或每帧计时。假设 100～200 条线程，每 10 分钟约 200～400 次小文件读取；假设每行 250～500 字节，常驻日志约 0.25～0.5 MB，每次满量滚动读写这一量级。数值是容量/操作量估计，**不是小米真机耗时或耗电实测**。

10 分钟之间创建又退出的短命线程不可见；已退出线程在上次快照之后的尾段 CPU 不可恢复。因此各组总和可能低于现有进程 CPU 增量。采样不是内核原子快照，遇到线程恰好退出、读不到文件时整项留空。计数回退按当前累计计入，无法知道重置前的尾值。采样自身也消耗少量 IO/CPU，不能从本统计中完全剥离。

## 真机需负责人确认

1. 小米 14 Pro 连续运行至少两次周期采样，分别覆盖亮屏/熄屏、充电/未充电；导出问题记录，核对表头、状态、间隔和分组。服务启动首行是基线，停止时状态可能仍为停止前状态。
2. 核对实际内核线程名称是否被截断/改名，特别是协程、AudioRecord 和数据库线程；未知名称只归其他，不记录原始名称。
3. 检查系统是否允许读取自身 task/stat/comm。若多行 unavailable，优先调查权限或线程退出竞争，不把空值解读成零耗电。
4. 比较加入统计前后的同负载长时录音、丢帧和电量数据，确认统计成本。电脑编译/单测不能替代这项实测。

本卡不操作手机、不安装、不发布；iOS 只验证共用规则可编译，安卓 /proc 采样未提供 iOS 实现。
