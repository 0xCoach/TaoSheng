## 给界面的新接口

入口：`RecordSearch(db).searchAll(ExpandedSearchRequest(...))`，suspend 调用。旧 `search(query)` 与 `SearchHit` 保持原有签名和行为。

请求字段：

- `query`：沿用 words 规则，去重后最多 8 个词，所有词都要命中；空白查询返回空分类页。
- `kind`：`Line / Event / Todo / Memory / Other`；null 查询全部。
- `startAt / endAt`：可空的 epoch 毫秒，区间为 `[startAt, endAt)`，空表示无该侧限制。
- `pageSize`：每类 1～100，默认 100。
- `offsets`：各类独立偏移，缺省 0。加载某类后续页时，传该类和上页 `nextOffset`。换查询、类别范围或时间条件须重置；全类加载时分别保存各类偏移。

返回 `ExpandedSearchResult.categories`，含本次选择的每个类别（零命中也有）：

- `hits`：该类当前页，时间倒序；时间相同按 `source` 枚举顺序、id 倒序，排序稳定。
- `count`：整个查询时间范围内该类命中数，0～100 为精确数，101 表示“100+”；不是当前页条数，也不是剩余条数。
- `countIsLowerBound`：count 为 101 时 true。
- `nextOffset`：下一页偏移，null 表示当前查询已到底。分页到后面仍返回全范围 count。

每条 `ExpandedSearchHit`：

| 字段 | 含义 / 跳转用途 |
|---|---|
| kind | 五大分类，由 source 派生 |
| source | Line、Event、Todo、Memory、Thing、ThingRecord、Topic、Review、AskMessage、AskConversation；与 id 共同组成唯一列表键 |
| id | source 所属表的主键；原话、事件、条目、物品、寻物记录、专题、回顾、消息、会话各自独立 |
| at | 排序与筛选时间，毫秒；具体来源见下表 |
| title | 事件标题、物品/记录名称、专题名称、问问会话标题；其余为空字符串 |
| text | 可见正文合并后的关键词附近片段，复用 RecordSearchRules.snippet；界面用 words 规则自行高亮 |
| eventId | 原话/条目所属事件，事件自身 id，专题关联事件；其他为空 |
| segmentId / speaker | 原话的录音段 id / 说话人；其他为空 |
| itemCategory | 条目原始中文类别；其他为空 |
| status | 条目、寻物记录、专题的原始状态；其他为空 |
| completed | 仅 Todo 且 status=Done 时 true；用于已完成标记 |
| thingId | Thing 自身 id 或 ThingRecord 关联物品 id；待确认的新物品记录可为空，按记录 id 打开待确认入口 |
| reviewDate | daily 回顾 startDate，YYYY-MM-DD，按日期打开回顾 |
| conversationId | 消息所属会话或会话自身 id；AskMessage 可另用 id 定位消息 |

Other 六个来源共同使用该类的 100 条配额。专题只查名称，不重复展开关联事件。条目用 id 打开详情，可用 eventId 回到来源；原话用 segmentId + id 定位。

## 各表可见口径与时间

| 表 | 可见条件与依据 | at |
|---|---|---|
| transcript_lines | 保留原搜索的全原话范围，另排除关联软删除事件的原话（与日记隐藏事件口径一致） | startAt |
| memory_events | deleted=0；查 title、summary、解析后的 pointsJson 字符串 | startAt |
| memory_items | deleted=0、mergedInto IS NULL、关联事件未删除（允许独立条目）、status != Ignored；Done 不过滤 | createdAt |
| things | deleted=0 且至少有一条 Accepted 记录；与 thingCatalog 无历史不出卡一致；查名称与解析后的别名 | updatedAt |
| thing_records | Pending（待确认页）或 Accepted 且关联物品未删除（历史页）；不含 Ignored；查名称、动作中文标题、地点、人、原文 | at |
| topics | 历史页 TopicProcessingRules.history 不排除任何状态，故保留 Cancelled；删除为物理删除；只查 name | createdAt |
| reviews | daily 且 startDate=endDate；按 daily 日期入口可打开，历史搜索不套最近 30 条展示限制；查 brief、非空栏目 title 与 lines，不查 JSON 键或 eventIds | generatedAt |
| ask_messages | 会话存在；用户/回答均查 text，不限 role；删除会话后不出现 | at |
| ask_conversations | 至少有一条消息，与 AskDao.history 一致；查 title | createdAt |

Todo 的实际类别来自 `ItemsScreens.TASKS` 与 MemoryDao：**待办、约定、备忘**。其余类别归 Memory（当前为灵感、关键信息、决定、知识），不将备忘错分到记忆。记忆 Ignored 也遵照本卡“排除已忽略”要求过滤。

事件、原话、条目复用现有 FTS；单汉字和无 token 文字走 LIKE。小表全部 LIKE。LIKE 的反斜杠、%、_ 转义，引号通过绑定参数处理。回顾/别名 JSON 含转义时放宽候选，再解码核对可见原文，以支持 Unicode 转义与引号而不误搜元数据。

## 分页与性能

候选每批 256 条，内部按时间/id 游标继续，逐条 contains 核对后才计入命中。不存在旧接口 FETCH=300 导致真命中被早期误命中挤掉的问题。各来源收集到当前页所需命中及一个探测条目后即停；计数至少探测 101 条。协程批次间检查取消；不写库、不建新索引。

偏移分页保证**数据不变时**不重不漏。录音、删除、编辑同时发生会改变排序与偏移；界面在数据变化后应从首页刷新，不能把跨请求结果理解为冻结快照。后续深分页会重新扫描此前命中，耗时随偏移增长。

按全天采集一年粗估：有效原话 3,000 条/日约 109.5 万条，事件 100/日约 3.65 万条、条目 50/日约 1.83 万条，这三类多字查询使用已有 FTS；单字或极常见词、FTS 大量误命中可能需要较多扫描。

小表按寻物 20 条/日=7,300、专题 1/日=365、回顾 1/日=365、问问 20 轮/日=14,600 条消息估算。桌面 SQLite 3.53.4 内存合成表、单个无命中词、代表性拼接 LIKE + ORDER BY + LIMIT 256 扫描结果：

| 来源 | 条数 | 每条正文字符数 | 扫描耗时 |
|---|---:|---:|---:|
| 寻物记录 | 7,300 | 120 | 3.52 ms |
| 专题 | 365 | 约 30 | 0.11 ms |
| 回顾 | 365 | 2,000 | 2.23 ms |
| 问问消息 | 14,600 | 1,000 | 48.94 ms |

这只是单条 LIKE 扫描成本参考，不是完整接口、真实用户数据库、Android 或 iOS 实测；不含关联查询、JSON 解码、多词与深分页。问问消息体积最值得关注，若手机上明显卡顿，后续独立卡评估全文索引；本卡不加索引。普通 B-tree 不能直接加速前导 `%` 的 LIKE。建议界面取消过期搜索并做输入防抖。
