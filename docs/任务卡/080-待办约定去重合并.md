## 一、问题（负责人真机截图）

“周六周日（10月31日、11月1日）去松江区工会上课”（前天提到，已完成）和“负责人明天后天（10月31日、11月1日）去给松江区工会培训”（昨天提到，未完成）成了两条。

根因有两个：
- 整理时 `unfinished_items` 只用来判断“做完了没有”（done_hints），没有让模型“已有的就别再建”；
- 已完成的条目根本不在上下文里。

灵感已经有合并机制（卡 040，`IdeaMerger` + `mergedInto`），待办、约定、备忘还没有。

## 二、负责人已定的规则

1. **整理时就不重复建（主手段）**：新提到的事和已有某条是同一件，就不新建独立条目，并到那条上。
2. **判断“同一件”**：时间对得上（同一天或同一时段，都没时间时看事情本身），并且做的事、对象、地点、和谁对得上。**按意思判断，不按字面**（“去松江区工会上课”≈“给松江区工会培训”）。
3. **保留最早那条**：以它的状态、你的编辑、强提醒为准。新的一次多出来的信息（原来没时间、这次说了几点）补进原来那条；**原来那条 `editedAt` 不为空时一律不动**，只记一次“又提到”。
4. **已完成的又被提到**：不重建，不改回未完成。除非明显是新的一次（日期不同，比如“下周六还要去上课”），那就是新的一条。
5. **定期重复的事**（每周上课、每月交报表）：日期不同就是不同的一次，不合并。
6. **待确认里不冒重复卡**：并进已有条目的那条不出现在待确认、进行中、提醒、推送里（现有查询都已按 `mergedInto IS NULL` 过滤，确认一下没有漏的路径）。
7. 被用户“拆开”过的（`noMerge`）以后不再自动并回去。

## 三、做法

### 1. 整理提示词与输入（`assets/prompts/digest.md`、`DigestPrompt.withTodoContext`、`DigestRunner`）

- 上下文里加上 **最近 7 天完成的** 待办 / 约定 / 备忘，作为 `recent_done_items`（字段同 `unfinished_items`，再加 `status`）。`unfinished_items` 照旧。数量上限：两者合计最多 150 条，超了按最近优先。
- `items` 每条新增可选字段 **`same_as`**：已有条目的真实 id（只能取自 `unfinished_items` / `recent_done_items`），不是同一件就填 null。
- 提示词写清第二节第 2、4、5 条。**按意图写规则，不写具体例句的关键词。**
- 解析：`same_as` 不在允许的 id 里就当 null；类别不同（待办 ↔ 约定）也允许并，因为同一件事有时被归成不同类别，以原来那条的类别为准。

### 2. 入库

`same_as` 有效时：
- 照常插入这条（保留它自己的原话出处和提取时间），但 `mergedInto = same_as`，状态跟原条目无关、不进待确认；
- 原条目 `dueAt / dueText / who` 为空、新的这次有，且原条目 `editedAt` 为空时，补进原条目；时间补进去后按现有逻辑重排提醒；
- 原条目已删除时当作没有 `same_as`。

### 3. 兜底合并（漏网的）

- 照 `IdeaMerger` 写一个待办 / 约定 / 备忘的合并器，在同一时机（`EmbeddingWork` 生成向量之后）运行；
- 只比较：未删除、`mergedInto IS NULL`、`noMerge = 0`、`editedAt IS NULL`、最近 30 天提取的；
- 候选必须同时满足：
  - **截止日期同一天**（都没时间的不由兜底合并，避免误并）；
  - 向量余弦 ≥ 阈值（先从 0.85 起，用真实数据定）；
- 早的为主，并入的那条 `mergedInto = 早的 id`；
- 早的那条是 Done 或 Accepted、晚的是 Pending 时，晚的并进去，不再出待确认卡；
- **两条都是用户接受过、或都开了强提醒的，不自动并**（宁可漏并，不误并）。

### 4. 现有数据一次性合并

升级后跑一次兜底合并，覆盖现有最近 30 天的条目，用的规则和第 3 点完全相同。不需要数据库升级就不升（`mergedInto`、`noMerge` 都已有）；需要记“已跑过”就用 `SharedPreferences`。
