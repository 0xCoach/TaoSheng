# 卡 067 · 推送订阅：本地数据格式出错不再误报“接收端问题”，坏记录跳过；问题记录补推送诊断（后端）

App 名叫“涛声”。在 `preview-0.2.13` 分支上开发（在卡 065、066 之后）。**本卡不改 `ui/` 和 `MainActivity.kt`。**

## 一、问题（已查明）

用户（0.2.13-preview.4，自定义接口 Webhook）推送订阅失败，提示“服务返回了无法识别的内容：地址可能指向了网页而不是接口”。
- 这句来自卡 060 的 `PushErrors.failure`：**异常链里只要有 `JSONException` 就报这句**。
- **Webhook 的回复涛声根本不读**（`http.execute(..., readBody = kind != PushKind.Webhook)`），所以这个 JSONException 只可能来自**涛声打包本地数据**：如 `PushSync.kt` 的 `RecordDelta.records`（`JSONArray(e.pointsJson)`、`JSONArray(e.peopleJson)`、`JSONArray(c.fieldsJson)`、`JSONObject(c.valuesJson)`、`JSONArray(r.sectionsJson)`）、`PushRecords.select` 的 `JSONArray(c.evidenceJson)`、`MemoryFolder` 的 `sectionsJson`/`pointsJson`、`DailyMemory`、订阅状态 `PushSyncState` 的读写、失败重试快照 `PushMessage.from(json)` 等。
- 而且**一条坏记录就让整次推送失败**，其它正常记录也推不出去。
- 问题记录（`ProblemReports.export`）里**完全没有推送信息**，无法判断是哪一步。

## 二、已定方案（负责人已确认）

1. **分清错误来源**：只有**解析服务端回复**时的 JSONException（PushPlus/企业微信/钉钉/飞书/Server酱/Telegram/Notion 的响应）才映射为“服务返回了无法识别的内容…”。在对应位置单独包一层，抛出明确的“响应解析失败”；`PushErrors.failure` 不再凭 JSONException 一律判为接收端问题。
2. **本地数据坏了：跳过这一条，其它照推**：把上面列出的本地 JSON 解析都改成安全解析（解析失败返回空数组/空对象并记一次计数），或在“逐条生成记录/文档”处 try-catch 跳过该条。推送照常完成，结果文案写“已推送；有 N 条记录格式异常，已跳过”（成功，不算失败）；若因此一条都没有可推的，才算失败并写“本地有 N 条记录格式异常，无法生成推送内容”。
3. **订阅状态/重试快照损坏**：状态 JSON 解析失败时重置该通道的状态并记一行诊断（会导致下次全量重推，交付说明写明）；重试快照解析失败就丢弃这条重试。
4. **从源头查**：搜一遍写入上述字段的地方（技能卡 `valuesJson/fieldsJson/evidenceJson`、事件 `pointsJson/peopleJson`、回顾 `sectionsJson`、整理/编辑事件/卡 062 的 `originalPointsJson` 等），有没有可能写进空字符串或非 JSON（如 `""`、`"null"`、模型原文）；有就改成写合法的空 JSON，并在交付说明列出。
5. **问题记录补推送诊断**（`ProblemReports.export` 增加一节）：
   - 每个推送通道：类型、格式、订阅里推什么（不含地址、密钥、Token、请求头值）、上次结果。
   - 最近 30 次推送日志：时间、通道类型、主题、成功/失败、失败文案（已脱敏）、**阶段**（打包本地数据 / 发送 / 解析回复）、异常类名、跳过的坏记录数及其类别（event/item/card/review/line）。不写任何记录内容。
6. 推送页的失败文案仍走现有日志（`log.error`），不改界面。

## 三、必测（适度，6～8 个）

- Webhook 订阅：一张技能卡 `valuesJson=""` → 推送成功，结果写“有 1 条记录格式异常，已跳过”，其余记录在请求体里。
- 全部记录都坏 → 失败，文案是“本地有 N 条…”，**不是**“服务返回了无法识别的内容”。
- PushPlus 返回网页 → 仍是“服务返回了无法识别的内容…”。
- 订阅状态 JSON 损坏 → 重置并继续。
- 问题记录里有推送通道与最近日志，且不含地址/密钥/内容。
