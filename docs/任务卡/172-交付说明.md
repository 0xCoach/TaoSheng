# 卡 172 交付说明：音量从录音状态里拆出来（省电）

## 根因

`CaptureStatus` 里带着实时音量 `level`，录音服务每 50 毫秒更新一次，于是整条状态流每秒变约 20 次。桌面小组件、桌面长按菜单、体检、快捷开关、语音输入服务都常驻订阅这条状态流，它们只关心“在听/暂停/停了”，却全天被音量叫醒（小组件和长按菜单还在主线程上），醒来后再把音量丢掉。

## 做了什么

- 约定 `CaptureContract.kt`：`CaptureStatus` 去掉 `level`；`CaptureController` 新增 `level: Flow<Float>`（有默认实现，测试里的假控制器不用改）。
- `AndroidCaptureController`：音量单独一条流；状态离开“聆听/录音”时归零（保持原来的显示效果）。没有界面订阅时，更新音量只是改一个值，不叫醒任何协程。
- 界面三处（首页主卡声波、录音与后台状态卡、引导“试一句”）改为单独订阅音量，仍然只在页面可见时订阅（沿用卡 165 的前台订阅）。
- 预览用的 `FakeCaptureController` 同步调整。

行为不变：声波照常跳动；状态、通知、小组件、快捷菜单的更新时机不变。

## 效果（静态估算）

录音中、有环境声、App 不在前台：状态流的变化从约 72,000 次/小时降到只有真实状态变化时才变（聆听↔录音切换、暂停、被占用）；每次变化原本要叫醒 4～5 个后台订阅者。实际省电量要等卡 171 的线程统计在真机上对比。

## 验证

- 新增 `LevelFlow172Test` 2 个：连续 20 次音量变化，状态订阅者 0 次额外触发、音量订阅者全部收到；离开聆听状态音量归零。
- 相关旧用例 `PrivacyCaptureTest`、`Quick147Test` 通过；`:app` 调试版编译通过；`python3 tools/check_shared.py` 通过。本卡未改 `:shared` / `:devices`，未跑 iOS 检查。
- 未跑全量。

## 顺手搬家

本卡碰到的是安卓状态装配和界面，没有可搬的纯规则。`CaptureContract.kt` 仍带 `java.io.File`、`java.time.LocalDate`，留给数据层卡（177）换日期类型时一起搬。

## 真机注意

- 首页主卡、设置→录音与后台、引导页的声波应和以前一样随说话跳动；切到后台再回来立即恢复。
- 小组件、通知按钮、桌面长按菜单在暂停/恢复/开始专题后照常更新。
