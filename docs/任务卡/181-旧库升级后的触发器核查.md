# 卡 181：核查老用户升级后全文搜索等触发器是否齐全（先查清，再定是否修）

## 背景

卡 175 录夹具时发现：按各版本结构文件（`app/schemas/`）建旧库再升级到当前版本（33），最终库里的手写触发器数量比全新安装少——版本 1～17 升上来是 15 个（齐全），18～26 只有 5 个，27～32 只有 2 个；全新安装是 15 个。新旧数据库驱动表现一致，所以不是卡 175 引入的。缺的名单在分支 `codex/175-sqlite-driver` 的 `docs/任务卡/175-证据/第二段/迁移新装逐字核验.tsv`（`git show codex/175-sqlite-driver:<路径>`）。

结构文件不记录手写触发器，所以这个结果**不等于真实手机缺触发器**：真实手机在当初安装的那个版本上由 `onCreate` 回调建过。但也可能真有缺口：某个版本之后新增的触发器只写在 `onCreate`（新装才建），没有在迁移或 `onOpen` 里给老用户补。全文搜索三张表（`lines_fts`、`events_fts`、`items_fts`）靠触发器跟着原表更新，缺了的话老用户搜不到新内容或搜到已删内容。

## 要回答的问题

1. 现行 15 个触发器各自是在哪个数据库版本、哪次提交引入的？建在哪里（`onCreate` 回调、`onOpen` 回调、某段迁移）？用 `git log -S "<触发器名>"` 追。涉及 `search/SearchIndex.kt`、`importer/ImportRecordDao.kt`（`ImportRecordSchema`）、`things/ThingData.kt`（`ThingSchema`）、`data/PendingDigest.kt`（`PendingDigestSchema`）、`data/CaptureDatabase.kt`。
2. 对每个触发器，判断“在它引入之前就已安装、一路升级上来的真实用户”现在有没有它：引入它的那次改动有没有同时在迁移或 `onOpen` 里为老库补建？
3. 用一个**忠实模拟真实历史**的测试验证：对若干有代表性的起始版本，按“该版本当时的 `onCreate` 会建的触发器”建旧库（从 git 历史里取当时的回调 SQL，不是拿现在的），再用现在的代码升级并打开，列出最终缺哪些触发器。起始版本至少覆盖每个触发器引入点的前一个版本。
4. 如果确有缺口：说明对用户的实际影响（哪类数据搜不到 / 哪个功能不更新），给出修法建议——优先“每次打开时幂等补建”（`CREATE TRIGGER IF NOT EXISTS` 放 `onOpen`，不加数据库版本），并说明已有数据是否需要一次性回填索引、怎么做才不重复不漏。**本卡先不改产品代码**，除非缺口确凿且修法只是把已有的建触发器函数挪到 / 同时放进 `onOpen` 这种不改结构、不加版本的小改动；那样可以直接做，并用第 3 条的测试证明修好了。
5. 如果没有缺口：说明为什么夹具里看着少（结构文件不含触发器），并建议卡 175 的夹具是否需要补一组“忠实历史”的来源库。

## 不做

不加数据库版本、不改表结构、不改 `ui/`、`*Contract.kt`；不动数据库驱动（卡 175 在另一分支改，本卡基于 main 的旧驱动写法即可，注意以后合并时回调签名会变，改动越小越好）；不读真实数据库。
