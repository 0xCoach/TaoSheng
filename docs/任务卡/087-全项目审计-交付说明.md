## 已复现问题

### A1 / P1：分卷备份遗漏环境音记录和纠错状态

- 位置：`backup/DayVolumeRows.kt:15–22,35–40,110`，`envsound/EnvSoundDao.kt:8–12`。
- 原因：导出、导入依赖固定的 `dated/global` 表清单，其中没有 `env_sounds`。恢复通过新建数据库再填充白名单表完成，因此遗漏数据不会留在恢复库里。
- 复现：写入一条录音和对应环境音（`restored=true`、`reportedWrong=true`），快照 → 分卷行导出 → 数据库重建。恢复库保留录音，但环境音查询返回空。
- 影响：环境音标签、判断、纠错状态丢失；`ThingDao` 的媒体来源排除也依赖该表。录音已过期时无法完整重新识别，人工纠错更不能靠自动识别还原。恢复前保护快照也使用 `DayVolumes.export`，同样需要修正。
- 建议：把环境音纳入按日持久化清单，保持录音外键关系和纠错字段；补表级备份覆盖检查及完整往返回归。旧备份已遗漏的数据，不能仅靠升级从备份中补回来。
- 测试：`BackupAudit087Test.dayVolumeRoundTripCurrentlyDropsEnvironmentCorrections`。

### A2 / P2：模型返回后的本地异常不计入重试预算，可能持续重复请求

- 位置：`digest/DigestRunner.kt:117–161,203`，`ResoundApp.kt:165`，`transcribe/TranscribeWork.kt:55,113`。
- 原因：模型请求及用量记录先完成，后续环境音查询/写库再执行。普通异常被统一返回为 `LlmError.Format`，却不经过 `failed()`；只有 `LlmException(Format)` 才累计三次失败。普通流水线收到该结果会请求后台重试，原话仍是待整理状态。
- 复现：模型每次返回合法事件，注入持续的环境音数据库读取异常。连续运行四次，请求发生四次、原话仍未整理、失败计数仍为零。
- 影响：在持续本地故障下重复发送同一批内容；错误展示还会把本地问题说成模型格式错误。**这是可触发的重复用量路径，不是对历史账单原因的确认。** 测试没有调用收费接口。
- 建议：区分模型/网络失败与本地落库失败；后者持久化有效响应后只重试本地提交，设置退避和熔断；恢复后重试不应再次调用模型。不能简单把三次失败后的原话标为完成，否则会掩盖未保存的结果。
- 测试：`DigestAudit087Test.localFailureAfterModelReplyDoesNotConsumeRetryBudget`。
- 寻物现状：`DigestThingExtraction` 无 LLM 客户端；物品事实随时间线整理同一次请求提取，本轮没有发现独立寻物请求被重新加回。

### A3 / P2：非流式模型请求读取正文期间，取消不能及时中止 HTTP

- 位置：`digest/LlmClient.kt:37–65,134–140`。
- 原因：取消回调绑定在等待响应头的 continuation 上；收到响应后，在外层 IO 协程中阻塞读取 `body.string()`。此时取消已经不再覆盖整个 HTTP 读取生命周期。流式路径已经采用覆盖正文读取的取消处理。
- 复现：本地假服务立即返回响应头，正文延迟两秒；在进入正文读取后取消协程。250 毫秒内协程未结束，底层 HTTP call 也未被取消，要等正文读取结束。
- 影响：取消/超时不能及时释放连接和流水线等待；后台可能继续接收本次结果。生产默认 call timeout 为 200 秒，实际剩余等待取决于响应和剩余超时。不能据此推断供应商一定继续计费，HTTP 取消本身也不保证免计费。
- 建议：让取消覆盖响应头及整个正文消费过程，确保取消竞态下 Response 被关闭，参考现有流式处理。保留慢正文取消回归测试。
- 测试：`LlmCancellationAudit087Test.chatJsonCancellationCurrentlyLeavesBodyReadRunning`。

### A4 / P2：恢复备份后的转写设置，本次启动仍用旧内存值

- 位置：`ResoundApp.kt:49–62`，`transcribe/AndroidAsrSpeedSettings.kt:17,36–50,63`。
- 原因：先构造 `AndroidAsrSpeedSettings`，再执行 `BackupRestore.applyPending`。前者只在构造时读取历史；`refresh()` 仅刷新现有内存历史，不重新读取已经恢复的偏好文件。
- 复现：备份中关闭说话人分离；按 App 当前启动顺序先构造默认开启的对象再恢复。现有对象仍判断开启，新构造的对象才判断关闭，调用 `refresh()` 也不能纠正。
- 影响：恢复后的说话人分离/课堂模式与磁盘设置不一致，会影响随后录音使用的设置；再次修改设置时，旧内存历史还有覆盖恢复历史的风险。
- 建议：恢复必须先于依赖可恢复配置的对象初始化；统一检查 AppGraph 的构造顺序。优先调整初始化顺序，而非要求用户再重启一次。
- 测试：`BackupAudit087Test.restoringSettingsAfterConstructionLeavesOldHistoryInMemory`。

## 待验证风险

### R1：恢复落地发生 IO 错误时，可能在后续启动反复失败

`BackupRestore.applyPending` 在 Application 初始化中执行，没有恢复失败后的安全启动分支。其清理、配置写入和逐文件替换并非跨全部文件的原子事务；失败后 pending 仍在，下次启动继续尝试。重放有助于正常恢复，但若磁盘满等故障持续，App 可能持续启动失败。

静态路径已确认，未在真机制造磁盘满/进程中断。建议在隔离环境注入恢复各阶段的 IO 错误，验证重放、回滚入口和保护快照；不能只验证正常恢复成功。

### R2：模型调用缺少统一的输入与输出预算

`DigestRunner.MAX_LINES=300` 是行数限制，不是字符/Token 限制；`LlmClient.chatJson` 没有像 `streamChat` 一样设置明确的输出上限。导入总结已有字符分块，普通整理尚未采用同样的预算方式。特别长的原话或异常输出可能导致上下文超限或一次调用偏贵。

这是边界防护缺口，不等于当前每次请求都超量。本轮未使用实际供应商做超长输入计费实验。建议按任务配置输入字符预算、输出上限及累计用量预警，并记录每次输入/输出用量、失败阶段，避免只看总账。
